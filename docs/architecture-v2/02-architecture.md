# 02. Architecture V2: компоненты, ответственности, контракты

Jarvis — локальный слой управления компьютером, который зовёт AI только там, где он нужен. Простое
исполняется детерминированно и мгновенно, сложное получает сильный бэкенд, приватное остаётся
локальным, облако добавляет интеллект, но не обязательно для работы, внешние coding-агенты —
специализированные инструменты, а не ядро.

## 1. Главный ответ: кто решает, как исполнять задачу

**Решает детерминированный Router ядра, а не модель.** Router по запросу, режиму пользователя,
состоянию провайдеров и политике приватности выбирает *стратегию исполнения* и *уровень* и
записывает решение с причинами (`RouteDecision`). Модель может только:

- выбрать следующее действие **внутри** стратегии `AGENT` (инструмент или ответ — по схеме из реестра);
- позже — **попросить** эскалацию (`escalate`): решение о ней снова принимает Router по тем же правилам
  приватности и доступности.

Модель не выбирает провайдера, не решает, может ли что-то уйти в облако, не исполняет действий и не
выбирает стратегию сама. Так Jarvis не превращается в «user → LLM → LLM решает всё».

## 2. Схема компонентов

```
 Клиенты (Intake adapters)     CLI · позже голос, desktop UI, локальный API — равноправные входы
            │  TaskRequest: текст, папка, режим (auto / local_only / smart / coding), разрешения облака
            ▼
 ┌──────────────────────────────── Jarvis core (один процесс) ───────────────────────────────────┐
 │ Task Runtime: машина состояний · runner · бюджеты · аренды · подтверждения · трасса · аудит   │
 │                                                                                                │
 │ ROUTING ──▶ Router (детерминированный, без вызова модели)                                      │
 │             ├─ режимы и подсказки: local_only, «офлайн» — только ужесточение                   │
 │             ├─ L0: грамматика команд + Entity Resolver (приложения, папки, позже проекты)      │
 │             │       + триггеры рецептов                                                        │
 │             ├─ признаки задачи: анализ, код, объём, вставленный код, секреты                   │
 │             └─ таблица решений → RouteDecision {strategy, tier, intent | recipe | specialist,  │
 │                                                  mode, reasons}                                │
 │                                                                                                │
 │ EXECUTING — исполнитель стратегии:                                                             │
 │   DIRECT  ─ прямой обработчик: интент → вызов(ы) инструмента → шаблон ответа (без модели)     │
 │   RECIPE  ─ Recipe Engine: детерминированный workflow, шаги — вызовы инструментов            │
 │   AGENT   ─ агентный цикл 1–N шагов: Model Gateway ⇄ Tool Runtime, проверка ответа            │
 │   DELEGATE─ передача задачи внешнему агенту: вызов инструмента-делегата через Tool Runtime   │
 │   CLARIFY ─ уточняющий вопрос (шаблон)                                                         │
 │                                                                                                │
 │ Model Gateway (единственный путь к моделям)       Tool Runtime (единственный путь к эффектам) │
 │   план кандидатов: уровень → цепочка провайдеров    preview → Policy → подтверждение → execute │
 │   фильтры: режим, Privacy Gate, состояние           → verify → трасса, аудит                    │
 │   ограниченный fallback, журнал вызовов               │                                         │
 │        │            │                                 ├─ инструменты HOST (fs, процессы, запуск)│
 │   локальная     удалённая                             ├─ делегат → SpecialistAgent (порт)      │
 │   модель        модель (облако)                       └─ позже MCP-инструменты (адаптеры)       │
 │                                                                                                │
 │ Privacy Gate (CloudPrivacyPolicy): что может выйти за пределы компьютера — для Gateway и делегата│
 │ Provider Availability: состояние провайдеров (READY, RATE_LIMITED …) с коротким сроком          │
 │ Skill Provider (Null → позже AI-Dev-System по MCP) · Project Resolver (позже)                  │
 └────────────────────────────────────────────────────────────────────────────────────────────────┘
        │ HTTP loopback               │ HTTPS                          │ процесс (argv, без shell)
   llama-server (Qwen3-8B)      облачные API моделей            внешний агент (coding CLI)
```

Отличия от гипотезы из задания (и почему):

- **Intent Router, Task Classifier и Execution Strategy — один компонент Router.** Это одно
  детерминированное решение по одним входам; три слоя дали бы три места, где решение могут
  принять по-разному. Внутри Router — шаги (L0, признаки, таблица), но наружу — один объект решения.
- **LOCAL_AGENT и REMOTE_AGENT — одна стратегия `AGENT` с разным уровнем.** Цикл, инструменты,
  политика и проверка у них одинаковые; различается только провайдер модели. Fallback «облако →
  локальная» происходит *внутри* задачи на каждом вызове модели — как отдельные стратегии это
  потребовало бы перезапуска задачи.
- **Model Router — часть Model Gateway**, а не отдельный слой: выбирать провайдера и исполнять вызов
  с fallback должен один компонент, иначе журнал попыток и состояние провайдеров расходятся.
- **SpecialistAgent — отдельный порт, но вызывается через Tool Runtime**, а не через Model Gateway:
  внешний агент читает файлы и может их менять — это побочный эффект и выход данных, а значит,
  preview, политика, подтверждение и аудит (ADR 0029).
- **L1 «tiny 3B/4B» не является обязательным уровнем** (§6).

## 3. Router и стратегии исполнения

### Стратегии

| Стратегия | Когда | Кто думает | Модель | Пример |
| --- | --- | --- | --- | --- |
| `DIRECT` | L0 распознал команду и разрешил сущности с высокой уверенностью | никто: код | нет (бюджет `direct`: 0 вызовов модели) | «Открой браузер», «Покажи Downloads», «Какие Python процессы работают?» |
| `RECIPE` | сработал триггер рецепта | рецепт (данные) | нет или точечно (слот) | «Подготовь рабочее окружение проекта» |
| `AGENT` | нужно понять, выбрать инструменты, прочитать и ответить | модель уровня `tier` | Model Gateway | «Найди файл и расскажи, что внутри» (LOCAL); «Сделай глубокий анализ архитектуры» (SMART) |
| `DELEGATE` | задача над кодовой базой, есть доступный и разрешённый специалист | внешний агент | его собственная | «Исправь ошибки в кодовой базе» |
| `CLARIFY` | несколько равных кандидатов, нет обязательной сущности | — | нет | «Открой его» без контекста |

`Route` в `domain/task.py` и есть стратегия: `DIRECT`, `AGENT`, `CLARIFY` уже есть, добавляются
`RECIPE` и `DELEGATE`, а `CHAT` сливается с `AGENT` без инструментов.

### Уровни (для `AGENT` и выбора провайдера)

| Уровень | Смысл | Цепочка по умолчанию | Облако |
| --- | --- | --- | --- |
| `fast` | короткая свободная команда, которой нет в L0 | как `local` (маленькая модель — только если бенчмарк докажет пользу) | никогда |
| `local` | обычная задача агента, приватное, офлайн | Qwen3-8B | никогда |
| `smart` | глубокий анализ и рассуждение | облачные провайдеры по порядку → Qwen3-8B | по политике |
| `coding` | работа с кодом без делегирования | облачные модели с сильным кодом → Qwen3-8B | по политике |

### Таблица решений Router

```
1. Отмена/стоп, ответ на вопрос задачи                       → обработать первыми (позже, с сессиями)
2. Режим: параметр запуска / сессия / конфиг; подсказка «офлайн, без облака» → local_only (только ужесточение)
3. L0: грамматика + сущности, уверенность ≥ порога риска      → DIRECT(intent) | RECIPE(recipe)
   средняя уверенность                                         → CLARIFY или подсказка агенту
4. Признаки задачи (детерминированно, расширяемые правила; проверяются по порядку):
     операция над кодом / вставленный код / репозиторий + анализ → класс codebase
     короткая команда-императив без глагола анализа               → класс command
       («покажи файлы большого проекта» — команда: масштаб сам по себе её не меняет)
     сильный глагол анализа, масштаб, объём, длинный запрос       → класс analysis
     иначе                                                         → класс task
5. Класс × режим × доступность × приватность:
     command  → AGENT(fast)
     task     → AGENT(local)
     analysis → AGENT(smart); анализ всей кодовой базы и есть специалист — DELEGATE(read_only);
                при local_only — AGENT(local) с честным ограничением
     codebase → DELEGATE(специалист), если доступен, папка — рабочая и данные разрешены (или
                человек согласился); иначе AGENT(coding) → иначе AGENT(local)
6. Режим smart/coding/fast задаёт уровень явно; local_only ограничивает smart/coding до local
```

Правила признаков — данные с ID (`rule.analysis`, `rule.code_op`, `hint.offline`…), а не `if "python"
in text`: слова языков программирования признаком кода не являются («Какие Python процессы работают?»
— команда). Каждое сработавшее правило попадает в `RouteDecision.reasons` и в трассу. Неоднозначный
запрос не стоит отдельного вызова модели: он идёт в `AGENT(local)`, и первый шаг 8B — уже работа, а
не классификация.

### `RouteDecision`

```python
class RouteDecision(BaseModel, frozen=True):
    strategy: Route                  # DIRECT | RECIPE | AGENT | DELEGATE | CLARIFY
    tier: RoutingTier | None         # для AGENT: fast | local | smart | coding
    mode: RoutingMode                # auto | local_only | fast | smart | coding (действующий)
    intent: Intent | None            # DIRECT: ID интента и разрешённые слоты
    recipe: str | None               # RECIPE
    specialist: str | None           # DELEGATE
    request_data: list[DataClass]    # что в самом запросе: вставленный код, секрет
    reasons: list[str]               # ID правил: почему так
```

Хранится в задаче (`tasks.routing_json`), пишется событием `route.decided`. Ответ на вопрос «почему
облако / почему не облако» — отсюда и из `model.routed`.

## 4. Ответственности компонентов

### 4.1 Intake

| | |
| --- | --- |
| Ответственность | Превратить вход клиента в `TaskRequest`: текст, рабочая папка, режим, разрешения облака, источник |
| Входы | CLI-аргументы; позже — расшифровка голоса, событие UI, вызов локального API |
| Выходы | `TaskRequest` → `TaskService.submit` |
| Зависимости | `TaskService` |
| Не должен | классифицировать, вызывать модель, решать про облако; голос — только ещё один адаптер Intake |

### 4.2 Router (стадия ROUTING)

| | |
| --- | --- |
| Ответственность | Решить стратегию, уровень и режим; разрешить сущности L0; объяснить решение |
| Входы | `TaskRequest`, конфиг (`models.routing.mode`, `cloud`), инвентарь сущностей, каталог рецептов, состояние провайдеров и специалистов, зоны приватности |
| Выходы | `RouteDecision` в задаче, событие `route.decided` |
| Зависимости | порты инвентаря (приложения, позже проекты), каталог рецептов, `ProviderAvailability`, `CloudPrivacyPolicy` |
| Не должен | вызывать модель по умолчанию (бюджет `routing` — 0 вызовов); исполнять действия; ослаблять режим по тексту запроса |

### 4.3 Direct path (стратегия DIRECT)

| | |
| --- | --- |
| Ответственность | Исполнить распознанную команду: интент → вызов(ы) инструмента → шаблон ответа |
| Входы | `RouteDecision.intent` |
| Выходы | вызовы через Tool Runtime, ответ по шаблону, `VERIFYING` по исполненным вызовам |
| Зависимости | Tool Runtime |
| Не должен | вызывать модель; обходить политику; угадывать при неполных слотах (тогда CLARIFY или AGENT) |

### 4.4 Recipe Engine (стратегия RECIPE, после V2.1)

| | |
| --- | --- |
| Ответственность | Исполнить детерминированный workflow: шаги, проверки, откат, эскалация в AGENT при сбое |
| Входы | рецепт (данные: YAML пользователя или проекта из реестра), слоты |
| Выходы | вызовы инструментов, итог с доказательствами |
| Зависимости | Tool Runtime, каталог рецептов |
| Не должен | иметь собственный доступ к ОС; исполнять текст навыка как команды |

### 4.5 Agent loop (стратегия AGENT)

| | |
| --- | --- |
| Ответственность | Короткий цикл «решение модели → вызов инструмента → наблюдение» до ответа; проверка ответа по исполненным вызовам |
| Входы | задача, `RouteDecision.tier`, разрешения облака, видимые модели инструменты |
| Выходы | шаги в рабочей памяти, ответ |
| Зависимости | Model Gateway, Tool Runtime |
| Не должен | выбирать провайдера; планировать длинные процессы; видеть инструменты, скрытые от модели; исполнять что-либо мимо Tool Runtime |

Бюджет уровня `local` короче нынешних 20 шагов (архитектура B: 1–3 шага по делу, запас на ремонт и
отказы) — значение подбирается по бенчмарку, не наугад.

### 4.6 Model Gateway (+ выбор провайдера)

| | |
| --- | --- |
| Ответственность | Единственный путь к моделям: план кандидатов, structured output, ремонт, fallback, журнал |
| Входы | роль, промпт с классами данных, схема ответа, маршрут (уровень, режим, разрешения) |
| Выходы | проверенное значение; `model_calls`, события `model.routed`, `model.called`, `model.fallback` |
| Зависимости | порт `ModelBackend` (локальные и удалённые адаптеры), `CloudPrivacyPolicy`, `ProviderAvailability` |
| Не должен | знать поставщиков и имена моделей; вызывать провайдера вне компьютера без разрешения политики; повторять бесконечно |

### 4.7 Privacy Gate (CloudPrivacyPolicy)

| | |
| --- | --- |
| Ответственность | Чистая функция: может ли этот промпт / эта рабочая папка уйти за пределы компьютера |
| Входы | промпт с классами данных секций, `cloud.*`, разрешения на задачу |
| Выходы | `PrivacyDecision{allowed, found, blocked, rules, reason}` |
| Зависимости | нет (домен) |
| Не должен | решать по тексту модели; разрешать секреты и `private_roots` ни при каких настройках |

### 4.8 Provider Availability

| | |
| --- | --- |
| Ответственность | Состояние провайдеров по итогам вызовов, со сроком; отдавать его плану |
| Входы | ошибки и успехи вызовов (модели и специалисты), позже — фоновые пробы резидентного процесса |
| Выходы | `ProviderStatus{state, reason, until}` |
| Зависимости | `Clock` |
| Не должен | ходить в сеть перед каждым запросом |

### 4.9 Tool Runtime + Policy + Approvals

| | |
| --- | --- |
| Ответственность | Единственная граница побочных эффектов: preview → политика → подтверждение → execute → verify → трасса и аудит |
| Входы | вызов от стратегии (прямой обработчик, рецепт, агент, делегирование) и **кто вызывает** |
| Выходы | `ToolOutcome`, класс данных результата |
| Зависимости | порт `Tool`, зоны, хранилище |
| Не должен | доверять модели; давать модели shell; разрешать побочный эффект, предложенный моделью, без человека |

### 4.10 Specialist delegation

| | |
| --- | --- |
| Ответственность | Передать задачу внешнему агенту в изолированной копии рабочей папки, вернуть итог и патч |
| Входы | цель, рабочая папка (только из рабочих папок политики), доступ (`read_only`, позже `write_copy`) |
| Выходы | `SpecialistResult{status, state, summary, patch?}` — недоверенные данные |
| Зависимости | порт `SpecialistAgent` (адаптеры CLI), Tool Runtime, Privacy Gate |
| Не должен | писать в рабочую папку пользователя напрямую; получать окружение Jarvis целиком; работать без таймаута и подтверждения |

### 4.11 Task Runtime (без изменений по сути)

| | |
| --- | --- |
| Ответственность | Жизненный цикл задачи: машина состояний, такты стадий, бюджеты фазы маршрута, аренды, отмена, восстановление, подтверждения как состояние |
| Входы | `TaskRequest`, итоги стадий (`StageOutcome`), решения человека |
| Выходы | контрольные точки (задача + события одной транзакцией), `TaskSnapshot` клиентам |
| Зависимости | хранилище (порты), `Tracer`, `Clock`, стадии по состояниям |
| Не должен | знать о моделях, провайдерах и облаке; решать маршрут (это Router); исполнять эффекты |

### 4.12 Хранилище, трасса, аудит

| | |
| --- | --- |
| Ответственность | Задачи, трасса, вызовы моделей, подтверждения, аудит, аренды — атомарно (SQLite WAL, оптимистическая единица работы) |
| Входы | записи runner'а, Tool Runtime, Gateway, Router |
| Выходы | история для CLI, `jarvis trace`, метрики, replay |
| Зависимости | — |
| Не должен | хранить ключи и заголовки авторизации, содержимое секретов, рассуждения моделей |

### 4.13 Skill Provider, Project Resolver, MCP — места в V2

- **Skill Provider** (ADR 0007): знания для модели — всегда недоверенный текст; источник в агентный
  цикл (Context Builder). `NullSkillProvider` по умолчанию; AI-Dev-System — адаптер по MCP позже.
- **Project Resolver** (позже): сущность «проект» для L0 и Router («запусти GOFRA»), рабочая папка и
  рецепты проекта, проектные навыки, недавние ошибки. Порт в `ports/projects.py`, реестр — YAML
  пользователя (ADR 0003, 0018). Router — потребитель, агент получает контекст проекта.
- **MCP** (позже): MCP-инструменты — адаптеры за портом `Tool` в Tool Runtime с объявленными эффектами
  (описания инструментов MCP — недоверенные); MCP-навыки — адаптер `SkillProvider`. Прямого пути от
  модели к MCP-серверу нет.

## 5. Провайдеры моделей и маршрутизация (ADR 0027)

### Виды провайдеров

| Вид | Пример | Порт | Данные уходят |
| --- | --- | --- | --- |
| `LOCAL_MODEL` | llama.cpp `llama-server` (Qwen3-8B), Ollama | `ModelBackend` | нет (только loopback) |
| `REMOTE_MODEL_API` | OpenAI-совместимые API облачных моделей | `ModelBackend` | да — через Privacy Gate |
| `EXTERNAL_AGENT` | coding-агенты с CLI | `SpecialistAgent` | обычно да — через Privacy Gate и подтверждение |

Ядро не знает брендов: провайдер — ID из конфига, вид и возможности. Особенности поставщика
(`extra_body`, режим JSON, коды квоты) — в конфиге и адаптере.

### Конфигурация (стиль существующего конфига)

```toml
[models.endpoints.main]                 # LOCAL_MODEL, как сейчас: только loopback
base_url = "http://127.0.0.1:8080/v1"
model = "local"
[models.endpoints.main.capabilities]
structured_output = true
context_window = 16384

[models.remote.cloud-a]                 # REMOTE_MODEL_API: только https, ключ — ссылка
base_url = "https://api.provider-a.example/v1"
model = "<имя модели у провайдера>"
api_key = "env:JARVIS_PROVIDER_A_KEY"   # сам ключ — в переменной окружения или хранилище ОС
json_object = true                      # провайдер не применяет JSON Schema, но умеет JSON-объект
[models.remote.cloud-a.capabilities]
structured_output = false
context_window = 131072
max_output_tokens = 16384               # максимальный вывод эндпоинта за один ответ
reasoning_behavior = "shares_output"    # «думающая» модель: рассуждения расходуют тот же лимит вывода
reasoning_budget = 8192                 # необязательно: сколько из лимита отдать рассуждениям
# [models.remote.cloud-b] — так же, со своей ссылкой на ключ

[models.roles]
executor = "main"

[models.routing]
mode = "auto"                           # auto | local_only | fast | smart | coding
smart = ["cloud-a", "cloud-b"]          # основная локальная добавляется последней автоматически
coding = ["cloud-b", "cloud-a"]
max_providers = 3

[cloud]
enabled = true                          # по умолчанию false
allow_local_metadata = true
allow_file_content = false
allow_source_code = false
allow_personal_data = false
allow_secrets = false                   # только false: секреты не уходят никогда
private_roots = ["C:/work/commercial"]
max_prompt_tokens = 32000
```

Цепочки `fast` и `local` принимают только локальные эндпоинты (ошибка конфига иначе): простой
запрос в облако не ходит по построению.

### Выбор провайдера: возможности и политика, а не только порядок

```
кандидаты = цепочка уровня (+ основная локальная последней)
  − всё вне компьютера, если режим local_only или cloud.enabled = false
  − всё вне компьютера, если Privacy Gate запрещает этот промпт (классы данных, объём)
  − провайдеры в состоянии ≠ READY, пока не истёк срок (локальный — только при MISCONFIGURED)
  − не подходящие роли по возможностям (лимит вывода меньше ответа роли, промпту не хватает окна)
  ограничение: не больше max_providers попыток, последняя — локальная
порядок оставшихся = порядок цепочки; DEGRADED — в конец
```

Порядок цепочки — это и есть предпочтение по качеству, цене и задержке, заданное человеком.
Автоматическое упорядочивание по измеренной задержке и цене — позже и только если появятся данные.

### Состояния провайдера

| Состояние | Признак | Срок | Поведение |
| --- | --- | --- | --- |
| `READY` | успешный ответ | — | кандидат |
| `DEGRADED` | медленно (p95 выше порога) или прерывистые сбои | 5 мин | в конец цепочки, не исключается |
| `UNAVAILABLE` | нет соединения, DNS, 5xx, таймаут | 30 с | пропуск; локальный не исключается |
| `AUTH_REQUIRED` | 401/403; агент не вошёл в аккаунт | 1 ч / до исправления | пропуск, подсказка человеку |
| `RATE_LIMITED` | 429 без признаков квоты | Retry-After или 60 с | пропуск |
| `LIMIT_EXCEEDED` | 402; 429 с признаком квоты/баланса; лимит подписки агента | 1 ч или до времени сброса | пропуск, подсказка |
| `MISCONFIGURED` | нет ключа в окружении, 404 модели/адреса | до перезапуска | пропуск, подсказка |

Состояние выводится из вызовов, а не из проб перед запросом. Хранится в процессе; для CLI без демона
— кандидат на короткую запись в SQLite, чтобы следующая команда не била в провайдера с исчерпанным
лимитом (решается в реализации, 04 §6).

### Fallback

- **Ограниченный:** не больше `max_providers` попыток на вызов модели; каждая попытка — тот же бюджет
  `model_calls` задачи; циклов «туда-обратно» нет — план строится один раз на вызов.
- **Детерминированный:** порядок — цепочка после фильтров; одинаковое состояние → одинаковый план.
- **Наблюдаемый:** `model.routed` (все кандидаты с вердиктом и причиной, решение приватности),
  `model.fallback` (с кого, на кого, категория ошибки, новое состояние), `model.called` (провайдер,
  вид, `remote`, модель, уровень, токены, задержка).
- **Что не ведёт к fallback:** ответ не по схеме после ремонта (это обратная связь задаче), окно
  переполнено (исполнитель сокращает промпт), отмена.
- Промпт строится под самое маленькое окно среди кандидатов — fallback на локальную модель не требует
  перестройки. Большие окна облака — позже, сборкой промпта под кандидата.

### Подписка ≠ API

Удалённая модель — это ключ API и OpenAI-совместимый HTTP. Внешний агент — это CLI со своим входом в
аккаунт (часто по подписке) и своими лимитами. Jarvis не извлекает токены подписки для API и не
считает одно заменой другого: это разные провайдеры с разными состояниями.

### Провайдеры при недоступности части сервисов в РФ

Архитектура не зависит ни от одного поставщика, поэтому выбор — конфиг. Что учесть:

- **Один адаптер на всех:** по документации поставщиков OpenAI-совместимый HTTP есть у Moonshot
  (Kimi), Zhipu (GLM, международный вход Z.ai), DeepSeek, Alibaba DashScope (Qwen, есть международный
  endpoint), MiniMax; из российских — у Yandex AI Studio (YandexGPT); GigaChat требует своего обмена
  OAuth-токена — небольшой адаптер аутентификации, не изменение ядра. Точные адреса, модели, условия
  регистрации и оплаты из РФ нужно проверить на ПК: из контейнера разработки этого не проверить.
  Обход региональных ограничений сервисов архитектура не предполагает: в цепочках — те провайдеры,
  которыми пользователь может пользоваться законно.
- **Различия — в конфиге:** многие из них не применяют JSON Schema, но поддерживают
  `response_format: json_object` (`json_object = true`, схема — в промпте с ремонтом); лимит вывода —
  `max_output_tokens`; «думающие» модели, чьи рассуждения расходуют тот же лимит, — `reasoning_behavior =
  "shares_output"` и, если известен, `reasoning_budget`; выключение рассуждений и прочее — `extra_body`;
  коды квоты (402, 429 с «balance/quota») — общий разбор в адаптере.
- **Приватность важнее:** данные у таких провайдеров обрабатываются по законам их юрисдикции, а
  условия могут разрешать использование данных. Поэтому исходный код и файлы по умолчанию не уходят
  (`allow_source_code = false`), коммерческие репозитории — в `private_roots`.
- **Coding-специалист тоже не должен зависеть от одного сервиса:** порт `SpecialistAgent` с
  профилями разных CLI-агентов (часть из них работает с любым OpenAI- или Anthropic-совместимым
  endpoint), а не код под один продукт.

## 6. Нужна ли локальная модель 4B

**Нет — не в runtime по умолчанию.** Решение и его проверка:

- VRAM 8 GB уже занята 8B (≈7,5 GiB при окне 16k, часть буферов вне VRAM). 4B рядом на GPU не
  помещается; на CPU (i5-12400) обработка промпта роутера в 1–2 тыс. токенов занимает секунды — это
  медленнее, чем тёплая 8B на GPU (тёплый запрос 238 мс, ≈48 ток/с).
- Чаще всего «быстрота» нужна командам, которые L0 закрывает без модели вовсе (миллисекунды).
- Неоднозначные короткие запросы идут прямо в `AGENT(local)`: отдельный вызов классификации был бы
  лишним вызовом модели.
- Уровень `fast` остаётся в конфиге: его цепочка по умолчанию — основная локальная. 4B становится его
  первым кандидатом, **только если** бенчмарк на наборе фраз роутера и коротких команд покажет
  выигрыш с учётом переключения модели (или в профиле «мало VRAM», например во время игры).

## 7. Граница приватности облака (ADR 0028)

### Классы данных

| Класс | Откуда | По умолчанию в облако |
| --- | --- | --- |
| `local_metadata` | имена файлов, пути, список процессов | да (`allow_local_metadata`) |
| `file_content` | содержимое файлов (не код) | нет — настройка или разрешение на задачу |
| `source_code` | содержимое файлов кода; код или трассировка, вставленные в запрос | нет — настройка или разрешение |
| `personal_data` | данные из личных папок (Документы, Рабочий стол, Загрузки, Изображения…) | нет — настройка или разрешение |
| `private` | всё из `cloud.private_roots`; задача, начатая в такой папке | **никогда** |
| `secrets` | зона секретов (`.ssh`, `.env`, `*.pem`, профили браузеров, менеджеры паролей…); найденные ключи, токены, пароли | **никогда** |

Классы ставит Jarvis там, где данные входят в задачу: запрос (поиск секретов и кода), результат
инструмента (объявленный вид результата + пути из preview + зоны). Проверяется каждый вызов, уходящий
за пределы компьютера, — ровно то, что уходит. Поиск секретов по тексту (ключи API, `Authorization`,
JWT, пароли в присваиваниях и строках подключения, приватные ключи) — вторая линия, а также
маскирование текстов ошибок провайдеров в журналах.

### Что можно, что нельзя, что требует согласия

| | |
| --- | --- |
| Можно без вопросов (при `cloud.enabled`) | запрос пользователя без секретов и кода; метаданные; то, что разрешено настройками |
| Только с согласием человека | файлы, код, личные документы — если настройка выключена: разрешение на задачу (`--allow-cloud source_code` или вопрос) |
| Никогда | секреты; `private_roots`; данные браузерных профилей и сессий; любые данные в режиме `local_only` |

**Согласие — через существующие подтверждения**, второго механизма нет. Когда Router выбрал облачный
уровень (`smart`, `coding`) или делегирование, а Privacy Gate запрещает вызов только потому, что не
разрешён класс данных (не секреты и не `private_roots`), исполнитель создаёт вызов скрытого от модели
инструмента `cloud.share` (эффект «выход данных к провайдеру X, классы Y»); политика требует
подтверждения; одобрение даёт разрешение на этот класс до конца задачи, отказ — задача продолжается
локально. На уровнях `fast` и `local` согласие не спрашивается никогда: облака там нет. Разрешение
можно дать и заранее параметром запуска (`--allow-cloud source_code`) — это тоже явное решение человека,
записанное в задаче.

**Аудит выхода данных:** каждый вызов провайдера вне компьютера — запись аудита (провайдер, классы
данных, размер, хеш промпта; без содержимого). Трасса показывает облачный вызов явно (`remote: true`).

## 8. Внешние агенты-специалисты (ADR 0029)

```python
class SpecialistAgent(Protocol):                 # ports/specialists.py
    @property
    def info(self) -> SpecialistInfo: ...        # id, уровни, off_device, доступ, таймаут
    async def run(self, request: SpecialistRequest) -> SpecialistResult: ...
```

Вызов — только через Tool Runtime, инструментом `specialist.delegate`, скрытым от модели (вызывает
стратегия `DELEGATE`):

1. **Preview:** рабочая папка должна быть в `policy.workspace_roots` (позже — проект из реестра);
   эффекты: `READ <папка>`, `NETWORK specialist:<id>` (если агент облачный), позже `WRITE` только в копию.
2. **Изоляция:** агент работает не в папке пользователя, а в **копии**: `git worktree` с
   отслеживаемыми файлами (неотслеживаемые `.env` и прочее туда не попадают), из копии удаляются файлы
   по шаблонам секретов; если что-то из зоны секретов отслеживается — отказ.
3. **Политика:** выход данных к специалисту — подтверждение человека (показывает папку, провайдера,
   классы данных, доступ); секреты в копии — запрет; `private_roots` — запрет.
4. **Процесс:** структурированный argv из профиля (без shell и без склейки строк), задача — через
   stdin (не флаг и не длинный argv), явная рабочая папка, окружение по allowlist + только то, что
   нужно самому агенту, таймаут, отмена с завершением дерева процессов (Job Object на Windows),
   ограниченный захват stdout/stderr, код выхода → состояние (`AUTH_REQUIRED`, `LIMIT_EXCEEDED`…).
5. **Результат:** итог и патч — недоверенные данные. Изменения попадают в рабочую папку только как
   патч через Tool Runtime (`WRITE` в рабочей папке → подтверждение с diff), затем детерминированная
   проверка (тесты — рецептом или разрешённой командой).
6. **v1 — только чтение** (анализ, предложение исправления); запись в копию с импортом патча — v2.

Сеть специалиста Jarvis на Windows ограничить не может (нужен брандмауэр или песочница ОС): поэтому
агенту не дают ничего, кроме копии без секретов, а сетевой доступ самого агента — настройка его профиля
(например, песочница агента без сети при записи).

## 9. Политика: прямые действия и запуск (ADR 0030)

Сейчас `PROCESS_CONTROL` — запрет, поэтому «Открой браузер» невозможна. V2 добавляет эффект `LAUNCH`
(запустить приложение из инвентаря, открыть http(s)-URL в браузере по умолчанию, открыть папку в
проводнике) и **исполнителя вызова** во входах политики:

| Эффект | Исполнитель `direct` (команда пользователя, распознанная L0) | Исполнитель `model` (агент) |
| --- | --- | --- |
| `LAUNCH` приложения из инвентаря, http(s)-URL, папки | ALLOW | REQUIRE_APPROVAL |
| `LAUNCH` произвольного пути/команды, не-http схемы | DENY | DENY |
| `PROCESS_CONTROL` (завершить процесс) | REQUIRE_APPROVAL | REQUIRE_APPROVAL |

Инвариант «побочный эффект, предложенный моделью, без человека не исполняется» сохраняется, поэтому
признак `tainted` по-прежнему не нужен; он обязан появиться вместе с первым ALLOW для исполнителя
`model` (ADR 0006, 0023).

### Браузер

Не GUI-автоматизация по зрению, если задачу решает: открыть URL (`LAUNCH`), HTTP-запрос (инструмент
`http.fetch` с эффектом `NETWORK` и политикой), API сервиса, протокол браузера (CDP/Playwright для
взаимодействия со страницей), deep link приложения. Зрение и UIA — последний запасной путь (Stage 6).

## 10. Хранилище, трасса и метрики

- `tasks.routing_json` — `RouteDecision` (миграция 004).
- События: `route.decided`, `model.routed`, `model.fallback`; `model.called` + провайдер, вид, `remote`,
  модель, уровень; запись `model_calls` + вид провайдера и уровень.
- Аудит: выход данных к провайдеру и специалисту.
- Метрики: вызовы модели вне компьютера, переходы fallback; в отчёте `jarvis run` — индикатор облака.
- Никогда в журналах: ключи, заголовки авторизации, содержимое секретов; тексты ошибок провайдеров —
  с маскированием.

## 11. Чего V2 сознательно не делает

Микросервисов внутри desktop-приложения нет: один процесс Jarvis, рядом `llama-server` и
процессы-специалисты на время задачи. Нет LLM-планировщика, менеджера резидентности моделей,
нескольких резидентных моделей, MCP, голоса, UI и реестра проектов — им оставлены места (§4.11).
