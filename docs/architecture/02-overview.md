# 02. Архитектура верхнего уровня

## 1. Целевая платформа и железо

Железо — не деталь реализации: оно определяет, какие модели живут одновременно, где работает
голос и насколько дорог каждый вызов LLM.

| Параметр | Значение | Следствие |
| --- | --- | --- |
| ОС | Windows 11 (по скриншоту AMD Adrenalin; подтвердить — Q1) | UI Automation, PowerShell, WSL2, Docker Desktop; рантайм — процесс в сессии пользователя, не служба |
| GPU | AMD Radeon RX 7600, 8 ГБ GDDR6, RDNA3 | Нет CUDA; LLM через llama.cpp с Vulkan-бэкендом (или LM Studio / Ollama); на GPU помещается одна LLM 7–9B |
| CPU | Intel Core i5-12400, 6 ядер / 12 потоков | Голос (wake word, VAD, STT, TTS), эмбеддинги, реранкер — на CPU через ONNX Runtime с ограничением потоков |
| RAM | 32 ГБ | «Тяжёлый режим» (MoE-модель с экспертами на CPU) возможен, но конкурирует с Docker/WSL2, IDE и браузером |

### Размещение моделей (профиль `rx7600-8g`)

| Роль | Где | Класс модели (примеры на момент написания) | Комментарий |
| --- | --- | --- | --- |
| Основная LLM (planner, executor, verifier, ответы) | GPU, резидентно | 7–9B instruct, Q4_K_M/IQ4, контекст 12–16k с KV-кэшем q8_0 | ≈5–6,5 ГБ VRAM; остаток — запас для Windows |
| Роутер | — | Правила + основная LLM в «режиме роутера» | Отдельная модель — только если замеры потребуют, и тогда на CPU |
| Vision | GPU, по требованию | Мультимодальная 7–8B (семейства Qwen-VL и аналоги) | Либо основная модель сама мультимодальная (один резидент), либо подгрузка со swap'ом (секунды) |
| Тяжёлый режим (опция) | GPU + CPU | MoE ~20–30B с ~3B активных параметров, эксперты на CPU | Только для фоновых или трудных задач и только при свободной RAM |
| STT | CPU | GigaAM (русский) / faster-whisper small–medium int8 / Vosk | Выбор — по eval на ваших записях (Stage 3) |
| TTS | CPU | Piper (русские голоса) или аналог | Проверить лицензии моделей и голосов |
| Wake word, VAD | CPU | openWakeWord, Silero VAD | Десятки мегабайт, миллисекунды |
| Эмбеддинги, реранкер | CPU | Мультиязычные класса BGE-M3 / multilingual-e5 | AI-Dev-System уже запускает BGE-M3 через ONNX на CPU |

Конкретные модели меняются каждые несколько месяцев. Документ фиксирует классы и способ выбора
(eval-набор, [11-quality.md](11-quality.md)), а не названия.

### Следствия для архитектуры

1. **Одна LLM на GPU.** Model Gateway знает о резидентности и стоимости переключения моделей и
   не допускает «пинг-понга» между основной моделью и VLM ([03-agent-core.md](03-agent-core.md#5-model-gateway-model-router)).
2. **Рабочий контекст 12–16k токенов.** Context Builder распределяет бюджет по секциям, большие
   выводы уходят в артефакты, стабильный префикс промпта переиспользует KV-кэш между шагами.
3. **CPU делится между голосом, эмбеддингами, Docker и системой.** Потоки ONNX Runtime
   ограничиваются (например, 4 потока на STT), иначе голосовой отклик будет «плавать».
4. **Vision дорог** (секунды на шаг, возможный swap). Отсюда UIA-first и vision только как fallback.
5. **WSL2 нужно ограничить** через `.wslconfig` (`memory=…`): по умолчанию WSL2 может занять до
   половины RAM, и тогда тяжёлый режим или даже основная модель упрутся в память.
6. **Игровой режим.** Судя по оверлею Adrenalin, на этой машине играют. При полноэкранном
   приложении Jarvis выгружает модель из VRAM и остаётся в режиме «fast path + CPU-STT»: команды
   вроде громкости и запуска приложений продолжают работать.
7. **Апгрейд, если когда-нибудь будет:** для локальных LLM важнее всего объём VRAM (16 ГБ заметно
   расширяют выбор моделей). Архитектура от этого не меняется — меняется только конфиг ролей.

### Ориентиры производительности

Это гипотезы для проверки бенчмарком в Stage 0, а не обещания.

| Операция | Ориентир |
| --- | --- |
| Генерация 8B Q4 на RX 7600 (Vulkan) | десятки токенов в секунду (порядка 30–50) |
| Простая голосовая команда от конца фразы до действия | ≈1–1,5 с |
| Шаг агентного цикла (переиспользованный префикс, вывод 100–200 токенов) | ≈2–6 с |
| Типичная диагностическая задача из 10–20 шагов | 1–2 минуты |
| Шаг VLM со скриншотом | ≈2–5 с, плюс секунды на подгрузку при swap |

```
├──────────────────────────────────────────────────────────────────────────────┤
│ Доменные сервисы     навыки и рецепты · память · проекты · управление GUI    │
├──────────────────────────────────────────────────────────────────────────────┤

│                      MCP bridge                                              │
```

Security формально лежит в kernel, но физически встроена в Tool Runtime: каждый побочный эффект
проходит через Policy Engine. Это главная архитектурная «точка сжатия».

```
┌─────────────────────────────────────── Клиенты ───────────────────────────────────────┐
│  CLI / TUI              Desktop UI (Tauri, позже)          jarvis-voice (процесс)     │
└──────┬───────────────────────────┬─────────────────────────────────┬──────────────────┘
       │        JSON-RPC + события · WebSocket · 127.0.0.1 · токен   │
┌──────▼───────────────────────────▼─────────────────────────────────▼──────────────────┐
│ jarvisd                                                                               │
│ ┌─ Runtime API ─────────────────────────────────────────────────────────────────────┐ │
│ │ сессии · запросы · подтверждения · вопросы пользователю · подписки на события     │ │
│ └────────────────────────────────────────┬──────────────────────────────────────────┘ │
│ ┌─ Agent Core ───────────────────────────▼──────────────────────────────────────────┐ │
│ │ Task Manager: статусы, бюджеты, очереди, планировщик, блокировки ресурсов         │ │
│ │ Intake → Entity Resolver → Intent Router (L0 правила · L1 рецепты · L2 LLM)       │ │
│ │ Dispatcher: direct │ recipe │ chat │ clarify │ agent                              │ │
│ │   agent = Planner ⇄ Executor ⇄ Verifier (цикл с живым планом)                     │ │
│ │ Context Builder · Responder                                                       │ │
│ └─────┬────────────────┬──────────────────┬───────────────────┬─────────────────────┘ │
│ ┌─────▼────────┐ ┌─────▼──────────┐ ┌─────▼─────────┐ ┌───────▼─────────────────────┐ │
│ │ Skill Engine │ │ Memory, Recall │ │ Projects      │ │ Model Gateway               │ │
│ │ рецепты,     │ │ факты, эпизоды │ │ реестр,       │ │ роли → endpoints, очередь,  │ │
│ │ руководства  │ │ ошибки, диалог │ │ контекст      │ │ резидентность, схемы        │ │
│ └─────┬────────┘ └────────────────┘ └───────────────┘ └───────┬─────────────────────┘ │
│ ┌─────▼─────────────────────────────────────────────────┐     │                       │
│ │ Tool Runtime — единственная точка побочных эффектов   │     │                       │
│ │ validate → policy/approval → audit → execute →        │     │                       │
│ │ normalize → postcheck → effects journal               │     │                       │
│ └─────┬─────────────────┬───────────────────┬───────────┘     │                       │
│ ┌─────▼────────┐ ┌──────▼──────────┐ ┌──────▼──────────┐      │                       │
│ │ Tool packs   │ │ Computer use    │ │ MCP bridge      │      │                       │
│ │ fs, proc,    │ │ UIA, экран,     │ │ внешние         │      │                       │
│ │ shell, app…  │ │ ввод, grounding │ │ MCP-серверы     │      │                       │
│ └─────┬────────┘ └──────┬──────────┘ └──────┬──────────┘      │                       │
│ ┌─────▼─────────────────▼──────────┐        │                 │                       │
│ │ Platform: windows │ linux │ fake │        │                 │                       │
│ └──────────────────────────────────┘        │                 │                       │
│ Kernel: SQLite + blobs · bus + трасса · config · security (policy, audit, secrets)    │
└─────────────────────────────────────────────┼─────────────────┼───────────────────────┘
                                              │ MCP (stdio)     │ HTTP, OpenAI-совместимый
                                ┌─────────────▼─────────┐ ┌─────▼──────────────────────┐
                                │ AI-Dev-System (Node)  │ │ llama.cpp / LM Studio /    │
                                │ и другие MCP-серверы  │ │ Ollama · GPU (Vulkan)      │
                                └───────────────────────┘ └────────────────────────────┘
```

Что важно на диаграмме:

- **Skill Engine исполняет рецепты только через Tool Runtime** — у рецептов нет «своего» доступа к ОС.
- **AI-Dev-System подключён через MCP bridge**, но доменные адаптеры (источник руководств, контекст
  проектов, жизненный цикл dev-задач) живут в Skill Engine и Projects, а не в самом мосте.
- **Model Gateway — сервис, а не модель:** к нему обращаются роутер, планировщик, исполнитель,
  верификатор, Recall (эмбеддинги) и Computer use (vision).
- **Память и контекст проекта читаются до планирования** (Context Builder) и пишутся после проверки.

## 4. Процессы

```
Windows 11 · интерактивная сессия пользователя (не служба Windows!)

┌───────────────┐   WS    ┌─────────────────────────────┐  HTTP   ┌──────────────────────────┐
│ CLI           │◄───────►│ jarvisd (Python, asyncio)   │────────►│ llama-server / LM Studio │
└───────────────┘         │                             │         │ GPU: RX 7600, Vulkan     │
┌───────────────┐   WS    │ • ядро агента, инструменты  │         └──────────────────────────┘
│ Desktop UI    │◄───────►│ • политика, аудит, память   │  stdio  ┌──────────────────────────┐
│ (Tauri)       │         │ • SQLite, blobs, трассы     │────────►│ AI-Dev-System (Node 22)  │
└───────────────┘         │ • MCP-клиенты               │         │ и другие MCP-серверы     │
┌───────────────┐   WS    │ • планировщик               │         └──────────────────────────┘
│ jarvis-voice  │◄───────►│                             │  spawn  ┌──────────────────────────┐
│ CPU: wake,    │         │                             │────────►│ дочерние процессы команд │
│ VAD, STT, TTS │         └─────────────────────────────┘         │ (Job Objects, лимиты)    │
└───────────────┘                                                 └──────────────────────────┘
```

| Процесс | Почему отдельно |
| --- | --- |
| `jarvisd` | Долгоживущее состояние, фоновые задачи, единая точка политики. Запускается при входе пользователя (Планировщик заданий «при входе» или трей-приложение), **не службой**: служба работает в сессии 0 и не видит рабочий стол |
| `jarvis-voice` | Аудио в реальном времени не должно зависеть от пауз ядра; свои зависимости (PortAudio, ONNX-модели); падение голоса не роняет агента; в будущем — «сателлит» на другом устройстве |
| Desktop UI | Обычный клиент API; может перезапускаться независимо |
| Сервер моделей | Внешний процесс (llama.cpp / LM Studio / Ollama); Jarvis не обязан им управлять в v1 |
| MCP-серверы | Процессная изоляция чужого кода; AI-Dev-System стартует один раз при запуске `jarvisd` и остаётся «тёплым» |
| Дочерние процессы | Каждая команда — в Job Object: лимиты памяти и CPU, уничтожение всего дерева при отмене |
| `Jarvis.exe` (launcher, трей, update-helper) | Стабильная маленькая программа, которая меняется редко: запускает активную версию и держит трей; по согласию пользователя переключает версию при обновлении и откатывает её, если новая не стартовала ([10-platform.md](10-platform.md#6-дистрибуция-и-обновления)) |

В Stage 0 CLI работает с ядром в одном процессе через тот же фасад `RuntimeAPI`, что потом будет
выставлен по сети. Вынос в демон (Stage 2) — механическое изменение, а не переписывание.

Права: `jarvisd` всегда работает **без повышения привилегий**. Действия, требующие прав
администратора, идут через отдельный путь с запросом UAC — сам запрос UAC служит естественным
подтверждением ([09-security.md](09-security.md#8-изоляция-исполнения)).

## 5. Модули и границы ответственности

| Модуль | Отвечает за | Не отвечает за | Зависит от |
| --- | --- | --- | --- |
| `kernel` | Базовые типы и ошибки, идентификаторы, часы, event bus, запись трасс, конфиг, SQLite и миграции, blob-хранилище | Любую предметную логику | — |
| `protocol` | Схемы Runtime API и событий (pydantic → JSON Schema → TypeScript) | Реализацию | — |
| `security` | Policy Engine, классификаторы риска (AST команд, зоны путей, хосты), подтверждения, grants, аудит, секреты, taint | Исполнение действий | kernel |
| `platform` | Порты ОС и адаптеры: приложения, окна, процессы, аудио, уведомления, буфер обмена, ввод, экран, UIA, индекс файлов, среды исполнения | Решения о риске и выборе действия | kernel |
| `models` | Протоколы моделей, провайдеры, Model Gateway, structured output (схемы, ремонт, повтор), шаблоны промптов | Решение, что спрашивать у модели | kernel |
| `tools` | ToolSpec, реестр, Tool Runtime, встроенные наборы инструментов, артефакты, журнал эффектов | Выбор инструмента | kernel, security, platform |
| `integrations.mcp` | Жизненный цикл MCP-клиентов, транспорты, мост MCP-инструментов в Tool Runtime | Доменную логику конкретных серверов | kernel, tools |
| `memory` | Факты, разговоры, эпизоды, ошибки; FTS5 и векторные индексы; Recall | Решение, что запоминать (это политика записи в `agent` и подтверждение пользователя) | kernel, models |
| `computer` | Стратегии GUI (UIA → vision), GUI-драйвер «наблюдение → действие → проверка», grounding; публикует инструменты `ui.*` | Низкоуровневые вызовы ОС | tools, platform, models |
| `skills` | Формат и движок рецептов, источники навыков (локальные, AI-Dev-System), Skill Resolver, извлечение рецептов из трасс | Поиск по каталогу AI-Dev-System (это делает сервер) | tools, models, integrations.mcp |
| `projects` | Реестр проектов, обнаружение, алиасы, среда исполнения проекта, сборка контекста проекта | Анализ кода (делает AI-Dev-System) | memory, integrations.mcp, platform |
| `agent` | Task Manager, Intake, Entity Resolver, Intent Router, Dispatcher, Planner/Executor/Verifier, Context Builder, Responder, бюджеты, фоновые задачи | Побочные эффекты (только через Tool Runtime) | всё перечисленное выше |
| `server` | Runtime API (JSON-RPC по WebSocket), аутентификация, сессии клиентов, трансляция событий | Логику агента | agent, protocol |
| `cli` | Командный клиент и TUI | Логику агента | protocol |
| `jarvis-voice` | Аудио, wake word, VAD, STT, TTS, barge-in | Понимание команд | protocol |

## 6. Правила зависимостей

Зависимости направлены только вниз. Правила проверяются в CI (`import-linter`), а не держатся на
дисциплине.

```
L7  server, cli
L6  agent
L5  skills, projects
L4  memory, computer
L3  integrations.mcp
L2  tools
L1  security, platform, models
L0  kernel, protocol
```

- Импорт «вверх» запрещён; импорт внутри слоя — только по явно разрешённым парам.
- `platform/windows` импортирует ОС-специфичные библиотеки; остальной код видит только порты.
- `jarvis-voice` зависит только от `protocol`.
- Тесты ядра используют `platform/fake` и `models/scripted` и не требуют ни Windows, ни GPU.

## 7. Потоки данных

### 7.1. Простая голосовая команда: «Джарвис, поставь громкость на 30%»

```
voice:  wake word → VAD (конец фразы) → STT → "поставь громкость на 30%" (уверенность 0.94)
  → request.submit(origin=voice)
jarvisd:
  Intake        нормализация, сессия, Task(kind=direct)
  Router L0     грамматика audio.set_volume{level=30}, уверенность 1.0      ≈ 1–5 мс
  Dispatcher    direct handler
  Tool Runtime  audio.set_volume(30): политика SAFE → allow → аудит →
                Core Audio → постусловие: громкость = 30 ✓                   < 100 мс
  Responder     шаблон "Громкость 30%" или короткий звуковой сигнал
  события → voice: speak / earcon; → UI: запись в таймлайне
```

LLM не вызывается. Если `level` не распознан или устройство вывода недоступно — эскалация: L2-роутер
или уточняющий вопрос.

### 7.2. Рецепт: «Запусти GOFRA»

```
Router L0      шаблон "запусти {target}"
Entity Resolver  target ∈ {приложения, проекты, рецепты} → проект GOFRA (алиас "гофра"),
                 у проекта есть рецепт start → route=recipe(user.gofra.start)
Recipe Engine  grant на рецепт есть, хэш совпадает → preconditions (Docker запущен)
  шаги через Tool Runtime:
    docker.compose_up(project, env=wsl:Ubuntu) → process.start(frontend) →
    http.wait_ok(/health, 60 с) → browser.open(http://localhost:3000)
  verification: GET /health = 200 ✓
при провале шага: on_failure=escalate → агентный цикл получает цель, трассу рецепта и ошибку
после: эпизод в память, статистика успешности рецепта
```

### 7.3. Сложная dev-задача: «Посмотри, почему Docker-контейнер падает, исправь и перезапусти»

```
Router         L0/L1 не сработали → L2: route=agent, profile=dev, проект = из активного окна
               (VS Code: "… — gofra — Visual Studio Code") или уточняющий вопрос
Context Builder
  профиль dev: docker.*, logs.*, fs.*, shell.run, git.*, http.probe (≈10 инструментов)
  AI-Dev-System: compile_project_context(project_path, task), recommend_skills(task, project_path)
                 → ≤3 руководства (карточки)
  Recall: похожие ошибки и эпизоды проекта, факты проекта
Lifecycle      begin_task в AI-Dev-System (задача меняет репозиторий) → критерии, baseline
Planner        цель; критерии: контейнер running ≥ 60 с, GET /health = 200, нет новых ERROR в логах
Executor loop  docker.ps → docker.logs (выжимка + артефакт) → гипотеза → fs.read(compose.yaml)
               → fs.patch (MEDIUM, бэкап; контекст заражён логами → подтверждение)
               → checkpoint_task → docker.compose_up → …
Verifier       детерминированные проверки + verify_task → passed → complete_task
Responder      отчёт с доказательствами; эпизод, запись «ошибка → решение»
```

### 7.4. GUI-задача: «Посмотри на экран и нажми кнопку подтверждения»

```
Router         route=agent, profile=gui
Observe        UIA-дерево активного окна (скриншот — только при необходимости)
Candidates     детерминированно: кнопки с именами OK / Да / Подтвердить / Confirm / Принять
Risk           подпись и окно: "Удалить", "Отправить", "Оплатить" → HIGH → подтверждение
Act            UIA InvokePattern (без мыши); нет UIA → set-of-marks + VLM → координаты → клик
Verify         окно закрылось или изменилось; иначе повтор с лимитом или вопрос пользователю
```

### 7.5. Опасное действие

```
Executor      предлагает shell.run(env=wsl:Ubuntu, "docker compose down -v")
Tool Runtime  → Policy Engine: разбор команды → down + флаг -v (удаляет volumes) → HIGH,
                необратимо; контекст заражён (логи) → решение ask
              → approval.requested → UI/CLI (origin=voice → только экран)
Пользователь  «разрешить один раз» → аудит (кто, как, когда) → исполнение
Отказ         Executor получает наблюдение "denied by user" и ищет другой путь или спрашивает
```

### 7.6. «Запомни, что этот проект я обычно запускаю через Docker Compose»

```
Router L0        шаблон "запомни, что …" → memory.remember
Entity Resolver  "этот проект" → активный проект (окно IDE, последняя задача) → GOFRA;
                 неоднозначно → уточняющий вопрос
memory           fact{scope=project:gofra, predicate=launch_method, source=user_explicit}
Skills           у проекта нет рецепта запуска → предложение: «Сделать команду "запусти GOFRA"?»
                 → черновик рецепта → показ → сохранение по согласию
```

## 8. Структура репозитория

Монорепозиторий с минимальным числом пакетов на старте. Границы внутри пакета `jarvis` проверяются
`import-linter`; отдельные пакеты выделяются, когда появляется отдельный процесс.

```
Jarvis-Agent/
├── pyproject.toml                 # uv workspace
├── packages/
│   ├── jarvis-core/src/jarvis/
│   │   ├── kernel/                # типы, ошибки, ids, bus, трассы, config, storage, blobs
│   │   ├── protocol/              # схемы API и событий (выделится в пакет в Stage 3)
│   │   ├── security/              # policy, классификаторы, approvals, grants, audit, secrets
│   │   ├── models/                # gateway, registry, providers/, decoding/, prompts/
│   │   ├── platform/              # ports.py; windows/, linux/, fake/
│   │   ├── tools/                 # spec, registry, runtime, artifacts, effects, packs/
│   │   ├── integrations/mcp/      # клиенты, транспорты, мост инструментов
│   │   ├── memory/                # facts, conversations, episodes, errors, recall
│   │   ├── computer/              # GUI-драйвер, стратегии, grounding (Stage 6)
│   │   ├── skills/                # рецепты, движок, sources/ (local, ai_dev), resolver, mining
│   │   ├── projects/              # реестр, обнаружение, контекст
│   │   ├── agent/                 # tasks, intake, entities, router, dispatcher, planner,
│   │   │                          # executor, verifier, context, responder, budgets, scheduler
│   │   ├── server/                # JSON-RPC по WebSocket, аутентификация (Stage 2)
│   │   └── cli/                   # CLI / TUI
│   └── jarvis-voice/              # отдельный процесс (Stage 3)
├── apps/desktop/                  # Tauri + React (Stage 4)
├── intents/ru/                    # грамматики команд L0 — данные, не код
├── recipes/                       # примеры рецептов
├── evals/                         # сценарии, фикстуры, кассеты, отчёты
├── docs/architecture/, docs/adr/
└── tests/                         # unit- и контрактные тесты
```

Почему так:

- **Один пакет `jarvis` на старте.** Модули внутри — с жёсткими правилами импорта. Это дешевле
  десятка пакетов и при этом не даёт границам размыться.
- **`platform/` отделён от `tools/` и `computer/`.** Инструменты описывают *что*, адаптеры — *как
  на этой ОС*. `platform/fake` — основа тестов без Windows.
- **Грамматики и рецепты — данные в репозитории**, а не код: их правят без релиза ядра, а позже
  дополняют пользовательскими.
- **`evals/` отдельно от `tests/`.** Unit-тесты детерминированы и быстрые; eval-сценарии
  используют живые модели, долгие и дают метрики, а не pass/fail.
- **`apps/desktop` и `jarvis-voice` появляются, когда появляется их стадия**, а не заранее
  пустыми каталогами.
