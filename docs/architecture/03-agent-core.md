# 03. Agent Core

Ядро агента отвечает за путь запроса от входа до проверенного результата: создание задачи,
маршрутизацию, планирование, исполнение, проверку, ответ, бюджеты, восстановление и фоновую
работу. Побочных эффектов ядро не производит — только через Tool Runtime
([04-tools-and-skills.md](04-tools-and-skills.md)).

## 1. Модель задачи

Любой запрос — даже «громкость 30%» — становится задачей (Task). Для простых команд это
дешёвая запись из нескольких строк, но она даёт единообразие: аудит, история, отмена
(«верни как было»), трасса.

Эскиз:

```python
class Task(BaseModel):
    id: TaskId
    parent_id: TaskId | None        # подзадача (глубина вложенности ≤ 1 в v1)
    session_id: SessionId
    origin: Origin                  # ui | cli | voice | schedule | proactive | recipe
    request: str                    # исходная формулировка
    route: Route | None             # direct | recipe | agent | chat | clarify
    profile: str | None             # desktop | dev | gui | general
    project_id: ProjectId | None
    lane: Lane                      # foreground | background
    status: TaskStatus
    budget: Budget                  # лимиты
    usage: Usage                    # потрачено: шаги, вызовы, токены, время
    plan: Plan | None               # текущая версия плана
    state: AgentState | None        # рабочая память: заметки, наблюдения, todo
    tainted: bool                   # в контексте есть недоверенный контент
    verification: VerificationReport | None
    outcome: Outcome | None         # verified | partially_verified | unverified | failed | cancelled
    ai_dev_task_id: str | None      # связь с жизненным циклом задачи в AI-Dev-System
```

Переходы статусов:

```
created → routing → running ⇄ waiting_approval
                      ⇅
                  waiting_user
running → verifying → completed            (outcome: verified | partially_verified | unverified)
verifying → running                        проверка не прошла, попытки остались
running | verifying → failed               бюджет, неустранимая ошибка, попытки исчерпаны
* → cancelled                              пользователь, kill switch
running → interrupted → running | abandoned   перезапуск jarvisd; решение пользователя
```

Рабочая память (Working Memory из исходной концепции) — это `AgentState`: цель, критерии приёмки,
todo-список, заметки агента, сжатая история наблюдений, открытые вопросы. Она сохраняется после
каждого шага и не является частью долговременной памяти.

## 2. Компоненты

| Компонент | Ответственность |
| --- | --- |
| Intake | Нормализация текста (пробелы, `ё`→`е` для сопоставления, числительные → числа там, где это однозначно, удаление обращения «Джарвис»), привязка к сессии, снимок окружения (активное окно, выделение, предполагаемый проект), создание Task |
| Session / dialog state | Последняя задача, последние упомянутые сущности («его», «там же», «ещё на 10»), ожидающий ответа вопрос, сводка разговора |
| Entity Resolver | Приложения, проекты, рецепты, файлы, окна, аудиоустройства; нечёткое сопоставление, транслитерация, фонетика, алиасы. Возвращает кандидатов с оценками |
| Intent Router | Каскад L0 → L1 → L2 с эскалацией (раздел 3) |
| Dispatcher | Запускает обработчик маршрута, эскалирует при неудаче |
| Direct handlers | Интент → вызов инструмента(ов) → постусловие → шаблон ответа |
| Recipe Engine | Исполнение рецептов (модуль `skills`; Dispatcher его вызывает) |
| Agent loop | Planner / Executor / Verifier (раздел 6) |
| Chat handler | Ответ без побочных эффектов; разрешены только read-only инструменты (например, `memory.recall`) |
| Clarifier | Уточняющий вопрос (шаблон или LLM), ожидание ответа, повторная маршрутизация |
| Context Builder | Сборка контекста под бюджет токенов (раздел 7) |
| Responder | Ответ под канал: для голоса — коротко и произносимо, для текста — подробнее, со ссылками на трассу |
| Task Manager | Жизненный цикл, сохранение, очереди (lanes), бюджеты, отмена, блокировки ресурсов, планировщик |

## 3. Intent Router

Задача роутера — быстро сделать **первую догадку** о том, как исполнять запрос, и честно
сказать, когда догадки нет. Это не классификатор, который обязан угадать с первого раза.

### Каскад

| Уровень | Механизм | Время | Что даёт |
| --- | --- | --- | --- |
| L0 | Грамматики команд со слотами (данные в `intents/ru/*.yaml`) + Entity Resolver | 1–5 мс | Интент и слоты; уверенность по качеству совпадения сущностей |
| L1 | Триггеры рецептов: примеры фраз и шаблоны; лексический поиск (FTS5) + эмбеддинги на CPU | 10–50 мс | Рецепт и параметры; при высокой уверенности — сразу исполнение, при средней — подсказка для L2 |
| L2 | Основная LLM в «режиме роутера»: короткий системный промпт, ответ строго по схеме `RouteDecision`, без reasoning, `temperature=0` | 0,3–1 с | Маршрут, профиль, проект, слоты или уточняющий вопрос |
| L3 | Деградированный режим, если LLM недоступна | — | «Сейчас понимаю только команды вида …» |

Пример грамматики L0 (эскиз; идея близка к шаблонному сопоставлению интентов в Home Assistant):

```yaml
# intents/ru/audio.yaml
audio.set_volume:
  templates:
    - "(поставь|сделай|установи) громкость [на] {level}"
    - "громкость {level}"
  slots:
    level: {type: percent}
  handler: {tool: audio.set_volume, args: {level: "${level}"}}

common.launch:
  templates:
    - "(открой|запусти|включи) {target}"
  slots:
    target: {type: entity, kinds: [app, project, recipe]}
  # target → приложение: app.open; проект с рецептом start: route=recipe;
  # несколько кандидатов с близкими оценками: clarify
```

Схема решения L2:

```json
{
  "route": "direct | recipe | agent | chat | clarify",
  "intent": "audio.set_volume",
  "recipe_id": null,
  "profile": "desktop | dev | gui | general",
  "project": "gofra",
  "slots": {"level": 30},
  "confidence": 0.82,
  "question": null
}
```

На вход L2 получает запрос, сводку состояния диалога и кандидатов от L0/L1 (до пяти) — модель
выбирает из известного, а не придумывает интенты.

### Порядок проверки — по уверенности, а не только по механизму

Механизмы чередуются по уровню уверенности (так устроен конвейер интентов OpenVoiceOS):

```
«стоп» / «отмена»            — всегда первыми, наивысший приоритет
продолжение диалога          — активный рецепт или вопрос агента получает реплику первым
L0 точные совпадения         → L1 рецепты с высокой уверенностью → L2 LLM
L0/L1 средней уверенности    — только как подсказки для L2 или уточняющий вопрос
chat                         — если это вопрос без действия
```

Нормализация сущностей (числа, даты, имена) — отдельная стадия до и после сопоставления, а не часть
каждого интента.

Если подходящего рецепта нет и запрос похож на повторяемую процедуру, в осторожном режиме можно
предложить выбор: «выполнить агентом / сохранить как рецепт / отмена».

### Правила эскалации

- `direct` не сработал (сущность не найдена, неповторяемая ошибка инструмента) → `agent` с
  контекстом ошибки или `clarify`.
- Рецепт упал → `agent` получает цель, трассу рецепта и ошибку.
- Агенту понадобился GUI → подзадача с профилем `gui` (глубина ≤ 1).
- **Порог уверенности зависит от риска:** для SAFE-интента ошибка дешёвая, порог ниже; для
  действий MEDIUM+ порог выше, и при сомнении — уточняющий вопрос, а не догадка.

### Диалог и короткие реплики

Шаблоны для эллиптических продолжений привязаны к последнему интенту в состоянии диалога:
«а теперь на 50» → `audio.set_volume{level=50}`; «ещё громче» → изменение на шаг;
«верни как было» / «отмени последнее» → отмена обратимых эффектов последней задачи по журналу
эффектов ([04-tools-and-skills.md](04-tools-and-skills.md#1-tool-api)).

### Метрики роутера

Точность маршрута и интента на наборе фраз (русский, смешанный русский/английский, фразы с
ошибками STT), доля запросов, закрытых на L0/L1, латентность p50/p95, доля эскалаций и уточнений.

## 4. Профили агента

Профиль — это набор «промпт + инструменты + источники контекста + бюджеты + проверки» для класса
задач. Профиль решает проблему малых моделей: вместо 50 инструментов модель видит 8–12 нужных.

| Профиль | Задачи | Инструменты | Контекст | Проверки по умолчанию |
| --- | --- | --- | --- | --- |
| `desktop` | Приложения, окна, файлы, настройки, медиа | `app.*`, `window.*`, `files.search`, `fs.read`, `audio.*`, `media.*`, `notify`, `clipboard.*` | Предпочтения, инвентарь приложений | Проверка состояния (окно существует, громкость равна) |
| `dev` | Проекты, код, Docker, git, логи | `fs.*`, `shell.run`, `git.*`, `docker.*`, `logs.extract_errors`, `http.probe`, `artifact.read` | Контекст проекта и руководства из AI-Dev-System, ошибки и эпизоды проекта | Детерминированные проверки; `verify_task` для изменений в репозитории |
| `gui` | Действия в интерфейсе по описанию | `screen.observe`, `ui.find`, `ui.invoke`, `ui.set_text`, `input.*` | UIA-дерево, скриншот | Повторное наблюдение и сравнение |
| `general` | Вопросы, анализ текста, планирование | Read-only: `fs.read`, `memory.recall`, `artifact.read` | Память | Качество ответа (без побочных эффектов) |

Профили — данные (YAML), их можно добавлять:

```yaml
id: dev
description: Работа с проектами, кодом, Docker и git
tools: [fs.read, fs.list, fs.search, fs.patch, shell.run, git.status, git.diff,
        docker.ps, docker.logs, docker.compose_up, logs.extract_errors, http.probe,
        artifact.read, ask_user]
context: [project_pack, guides, recall.errors, recall.episodes, env_snapshot]
budget: {max_steps: 30, max_model_calls: 40, max_wall_s: 900}
verification: {prefer: [checks, ai_dev.verify_task]}
```

## 5. Model Gateway (model router)

Model Gateway — детерминированный сервис, а не модель. Он отвечает на вопрос «каким endpoint
обслужить этот вызов» и скрывает от ядра всё, что специфично для моделей и рантаймов.

### Ответственность

- **Роли → endpoints:** `router`, `planner`, `executor`, `verifier`, `summarizer`, `responder`,
  `vision`, `grounder`, `embed`, `rerank`. Для профиля `rx7600-8g` все текстовые роли отображаются
  на одну основную модель.
- **Проверка возможностей:** роль требует `json_schema`, `vision`, `context ≥ N` — endpoint без них
  не выбирается.
- **Параметры по роли:** температура, лимит вывода, режим reasoning (включение и выключение
  «размышлений» у конкретной модели описано в её профиле, а не в ядре).
- **Structured output:** стратегия по endpoint (раздел ниже), валидация, ремонт, повтор.
- **Очередь с приоритетами:** интерактивные запросы впереди фоновых; на 8 ГБ сервер моделей
  работает с 1–2 слотами, и Gateway сериализует обращения.
- **Резидентность:** какие модели загружены, сколько стоит переключение, запрет «пинг-понга».
- **Отказоустойчивость:** health-check, цепочка fallback, деградированный режим.
- **Учёт:** токены, латентность, ошибки формата — в трассу и в бюджет задачи.

### Конфигурация (эскиз)

```toml
[[models.endpoints]]
id = "main"
provider = "openai_compat"            # llama.cpp server / LM Studio / Ollama
base_url = "http://127.0.0.1:8080/v1"
model = "<7–9B instruct, Q4_K_M>"
context_window = 16384
capabilities = ["chat", "json_schema"]
profile = "qwen-like"                 # профиль особенностей модели: шаблон, reasoning, стратегия действий
gpu = { resident = true, vram_mb = 6200 }

[[models.endpoints]]
id = "vl"
provider = "openai_compat"
base_url = "http://127.0.0.1:8081/v1"
model = "<VLM 7–8B>"
capabilities = ["chat", "vision", "json_schema"]
gpu = { resident = false, vram_mb = 6000, load_s = 8 }

[[models.endpoints]]
id = "embed"
provider = "onnx_local"               # в процессе jarvisd, CPU
model_path = "<multilingual embedding model>.onnx"
capabilities = ["embeddings"]

[models.roles]
router = ["main"]
planner = ["main"]
executor = ["main"]
verifier = ["main"]
vision = ["vl"]                        # или ["main"], если основная модель мультимодальная
embed = ["embed"]

[models.residency]
gpu_budget_mb = 7200
exclusive = [["main", "vl"]]           # не помещаются вместе
min_resident_s = 60                    # защита от пинг-понга
```

### Structured output и «tool calling»

Ядро описывает действие JSON-схемой; Gateway выбирает стратегию для конкретного endpoint:

| Стратегия | Когда |
| --- | --- |
| `json_schema` — ограниченное декодирование по схеме (грамматика в llama.cpp) | По умолчанию для локальных моделей |
| `native_tools` — нативный tool calling модели | Если eval показал, что для этой модели так лучше |
| `two_step` — сначала выбор инструмента (enum), потом аргументы по схеме этого инструмента | Слабые модели или большой набор инструментов |
| `prompt_parse_repair` — инструкция в промпте + разбор + ремонт | Endpoint без ограниченного декодирования |

Конвейер: схема → генерация → разбор → валидация pydantic → **семантическая валидация** (ровно одно
действие; инструмент есть в профиле; элемент или артефакт, на который ссылается действие, существует
в последнем наблюдении) → при ошибке ремонт с текстом ошибки (≤ 2 попыток) → `ModelFormatError`
(учитывается в бюджете, может вызвать эскалацию). В состояние агента попадает только прошедшее
проверку действие — невалидные ответы не засоряют историю.

### Резидентность на 8 ГБ VRAM

- В v1 загрузку и выгрузку выполняет рантайм (Ollama `keep_alive`, llama-swap, JIT-загрузка LM
  Studio); Gateway знает стоимость переключения и планирует запросы так, чтобы её минимизировать:
  vision-шаги группируются, действует минимальное время резидентности.
- Позже — собственный менеджер процессов `llama-server` (точный контроль параметров: Vulkan-устройство,
  контекст, размещение экспертов MoE на CPU). Ориентир — Leon: один дочерний `llama-server` на все
  роли, проверка готовности, выбор Vulkan-сборки по найденной GPU, KV-кэш q8_0, контекст 16k, один слот.
  Загружаемые бинарники и модели — только с проверкой хэша.
- «Размышления» модели выключаются для вызовов со structured output; вызовы инструментов внутри блока
  рассуждений не разбираются.
- Игровой режим: полноэкранное приложение → выгрузить модели, оставить fast path; при выходе из
  игры — прогреть основную модель заранее.

### Кэширование префикса

Context Builder строит промпт так, чтобы редко меняющиеся части шли первыми (раздел 7); Gateway
передаёт параметры переиспользования KV-кэша, если рантайм их поддерживает. На агентном цикле
это главный выигрыш по латентности: заново обрабатываются только новые наблюдения.

## 6. Цикл Planner / Executor / Verifier

Planner, Executor и Verifier — **роли** с разными промптами и контекстами. В v1 все три работают
на одной основной модели; разделение даёт короткие сфокусированные контексты и честную проверку.

### Planner

Получает цель и контекст, возвращает план по схеме:

```json
{
  "goal": "Backend GOFRA запущен и отвечает",
  "acceptance": [
    {"id": "c1", "text": "контейнер backend в состоянии running не меньше 60 с",
     "check": {"type": "docker.container_state", "args": {"name": "backend", "state": "running", "min_uptime_s": 60}}},
    {"id": "c2", "text": "GET /health возвращает 200",
     "check": {"type": "http.status", "args": {"url": "http://localhost:8000/health", "expect": 200}}},
    {"id": "c3", "text": "в логах за последние 2 минуты нет ERROR",
     "check": {"type": "docker.logs_clean", "args": {"name": "backend", "since_s": 120, "pattern": "ERROR"}}}
  ],
  "steps": [
    {"id": "s1", "title": "Посмотреть состояние контейнеров"},
    {"id": "s2", "title": "Найти причину в логах и конфигурации"},
    {"id": "s3", "title": "Исправить причину"},
    {"id": "s4", "title": "Перезапустить и проверить"}
  ],
  "risks": ["может потребоваться изменить compose.yaml"],
  "questions": []
}
```

Критерии ссылаются на **библиотеку проверок** — модель выбирает тип проверки и аргументы, но не
пишет код проверки:

| Проверка | Смысл |
| --- | --- |
| `process.running`, `window.exists`, `ui.element_state` | Состояние ОС и интерфейса |
| `http.status`, `http.body_contains` | Сервис отвечает |
| `docker.container_state`, `docker.logs_clean` | Контейнеры |
| `file.exists`, `file.contains`, `git.clean` | Файлы и репозиторий |
| `audio.volume_eq` и подобные | Результат системных настроек |
| `command.exit_code` | Только для read-only команд, прошедших политику |
| `ai_dev.verify_task` | Quality gate проекта через AI-Dev-System |
| `llm.judge` | «Мягкая» проверка: отдельный вызов с критерием и ссылками на доказательства |
| `user.confirm` | Субъективный результат: «так нормально?» |

**Раннее согласование.** Если в плане есть заведомо рискованные шаги («удалить volume»),
пользователь видит их один раз при утверждении плана; утверждённые действия становятся grant'ами
на эту задачу с точными аргументами. Это снижает «усталость от подтверждений» без потери контроля.

### Executor

На каждом шаге модель выбирает **одно** действие по схеме (дискриминированное объединение):

```json
{"rationale": "≤ 1–2 предложения",
 "action": {"type": "tool", "tool": "docker.logs", "args": {"name": "backend", "tail": 300}}}
```

Типы действий: `tool`, `recipe`, `ask_user`, `update_plan`, `subtask` (с ограничениями), `finish`.
Результат инструмента возвращается как наблюдение: выжимка + ссылки на артефакты + статус.

Перепланирование запускается, когда наблюдение противоречит плану, шаг провалился несколько раз
или Verifier вернул непройденные критерии. Число перепланирований ограничено бюджетом.

### Verifier

1. Детерминированные проверки из критериев — всегда первыми.
2. Для изменений в репозитории — `verify_task` в AI-Dev-System (quality gate, привязка к состоянию Git).
3. `llm.judge` — только для критериев, которые нельзя проверить иначе; отдельный вызов со свежим
   контекстом (критерий + доказательства), без истории рассуждений исполнителя — так меньше
   самоподтверждения. Результат помечается как «мягкий».
4. `user.confirm` — для субъективного результата.

Итог: `verified` (все обязательные критерии пройдены детерминированно), `partially_verified`
(есть мягкие или пропущенные), `unverified` (проверить было нечем) — и это честно попадает в ответ.
Критерий без доказательств считается непройденным, а итог задачи определяет худший обязательный
критерий, а не среднее.

### Цикл (эскиз)

```python
async def run_agent(task: Task) -> None:
    ctx = await context_builder.build(task)               # профиль, память, проект, руководства
    plan = await planner.plan(task, ctx)                  # валидированный Plan
    await approvals.preflight(task, plan)                 # раннее согласование рискованных шагов
    while True:
        budget.check(task)                                # BudgetExceeded → отчёт и остановка
        action = await executor.next_action(task, ctx)    # валидированное действие
        match action.type:
            case "finish":
                report = await verifier.verify(task, plan.acceptance)
                if report.passed:
                    return await finalize(task, report)
                if task.usage.verify_attempts >= task.budget.max_verify_attempts:
                    return await fail(task, report)
                task.state.observe(report.as_observation())
            case "update_plan":
                plan = await planner.revise(task, plan, action)
            case "ask_user":
                task.state.observe(await clarifier.ask(task, action.question))
            case _:
                result = await tool_runtime.execute(action, task)   # политика и аудит внутри
                task.state.record(action, result)                   # чекпоинт после шага
                loop_guard.observe(task, action, result)            # LoopDetected → рефлексия или стоп
```

## 7. Context Builder

Рабочий контекст на RX 7600 — 12–16k токенов. Context Builder распределяет его по секциям и
упорядочивает их так, чтобы стабильные части шли первыми и переиспользовали KV-кэш.

| # | Секция | Стабильность | Бюджет при окне 12k |
| --- | --- | --- | --- |
| 1 | Системный промпт и протокол действий | постоянна | ≈1,0k |
| 2 | Ядро памяти: профиль пользователя (снимок на сессию) | постоянна в сессии | ≈0,4k |
| 3 | Схемы инструментов профиля | в пределах профиля | ≈1,5–2k |
| 4 | Руководства (карточки; полный текст — по запросу через `skill.read`) | в пределах задачи | ≈1,5k |
| 5 | Контекст проекта | в пределах задачи | ≈2k |
| 6 | Память по задаче (Recall): факты, эпизоды, ошибки | в пределах задачи | ≈0,5k |
| 7 | Цель, критерии, план, todo | меняется при перепланировании | ≈0,6k |
| 8 | Наблюдения: последние шаги полностью, старые — сжатыми заметками | меняется каждый шаг | ≈2,8k |
| 9 | Текущий запрос к модели | каждый шаг | ≈0,2k |
| — | Резерв на вывод | — | ≈1–1,5k |

Правила:

- Большой вывод инструмента никогда не попадает в контекст целиком: выжимка + ссылка на артефакт;
  агент читает фрагмент через `artifact.read(ref, range | grep)`.
- Старые наблюдения сжимаются детерминированно (действие + однострочный итог); LLM-сжатие — только
  если заметки сами переполнили бюджет.
- Каждая секция помечена происхождением; недоверенный контент (логи, файлы, веб, импортированные
  руководства) заключён в явные разделители данных, а системный промпт говорит, что данные — не
  инструкции ([09-security.md](09-security.md#6-prompt-injection)).

## 8. Бюджеты, лимиты и защита от зацикливания

### Бюджеты по умолчанию

| Лимит | direct | recipe | agent, foreground | agent, background |
| --- | --- | --- | --- | --- |
| Действия (шаги) | 3 | шаги рецепта + 5 | 30 | 50 |
| Вызовы модели | 1 | 3 (на эскалацию) | 40 | 60 |
| Токены (вход + выход) | 2k | 10k | 300k | 500k |
| Время | 10 с | 10 мин | 15 мин | 2 ч |
| Одинаковых вызовов подряд | — | — | 2 | 2 |
| Перепланирований | — | — | 3 | 5 |
| Попыток проверки | 1 | 1 | 3 | 3 |
| Ошибок формата подряд | 1 | 1 | 3 | 3 |

Значения — стартовые, уточняются по eval. Подзадача получает долю *оставшегося* бюджета родителя.
При исчерпании бюджета задача завершается со статусом `failed (budget)`, частичным отчётом и
предложением продолжить с дополнительным бюджетом — продление делает пользователь.

### Детектор зацикливания

- одно и то же действие (инструмент + нормализованные аргументы) повторяется без изменения
  наблюдений;
- осцилляция A → B → A → B;
- K шагов без новой информации (хэши наблюдений повторяются) и без продвижения по todo;
- одна и та же сигнатура ошибки три раза подряд.

Реакция: один раз — «рефлексия» (агенту сообщается, что он повторяется, и предлагается сменить
подход или спросить пользователя); при повторе — остановка с отчётом и вопросом пользователю.
Тихо продолжать нельзя никогда.

Дополнительно, раз в K шагов (и при подозрительных сигналах), можно делать короткую проверку хода —
отдельный вызов с ответом-перечислением: `on_track` / `stuck` / `done`. Это дешевле полной
проверки и ловит зацикливание, которое не видно по хэшам наблюдений.

### Ресурсы

- Процессы команд — в Job Objects: лимит памяти, уничтожение всего дерева при отмене или таймауте.
- Вывод команд: хранится до N МБ, в выжимку — до нескольких тысяч символов.
- Артефакты и трассы: квоты на диске с очисткой старых.
- HTTP-инструменты: таймауты и лимиты тела ответа.
- Конкурентность: одна foreground-задача владеет «вниманием» (голос, ввод), до двух фоновых
  агентных задач; GPU — через очередь Gateway.

## 9. Ошибки и восстановление

| Класс | Пример | Реакция |
| --- | --- | --- |
| Ошибка формата модели | ответ не по схеме | Ремонт (≤ 2), затем ошибка шага, учёт в бюджете |
| `invalid_args` | аргументы не прошли валидацию | Наблюдение для агента с текстом ошибки |
| `not_found` | приложение или файл не найдены | Наблюдение для агента; в direct — эскалация или уточнение |
| `denied` | политика или пользователь отказали | Наблюдение «запрещено»; то же действие не повторять |
| `transient` | таймаут, занятый файл, сеть | Повтор с backoff (≤ 3) только для идемпотентных действий |
| `tool_internal` | исключение адаптера | Наблюдение + системный лог; неидемпотентное — без повтора |
| `model_unavailable` | сервер моделей упал | Fallback-endpoint → деградированный режим с сообщением |
| `mcp_unavailable` | AI-Dev-System не отвечает | Circuit breaker; работа без руководств и контекста проекта, пометка в отчёте |
| `budget_exceeded` | — | Остановка, частичный отчёт, предложение продлить |
| `cancelled` | «стоп», kill switch | Отмена дерева процессов, снятие блокировок, статус `cancelled` |
| Падение `jarvisd` | — | При старте: `running` → `interrupted`, уведомление, восстановление по чекпоинту |

### Чекпоинты и неопределённые действия

После каждого шага `AgentState` и запись шага сохраняются в одной транзакции. Журнал эффектов
пишет **намерение** до вызова инструмента и **итог** после. Если после сбоя найдено намерение без
итога, агент при возобновлении получает наблюдение «статус действия X неизвестен — проверь
состояние, прежде чем повторять». Неидемпотентные действия вслепую не повторяются.

### Отмена эффектов

Обратимые эффекты записываются с данными для отмены: запись файла — бэкап прежней версии в blob,
удаление — в Корзину, запуск процесса — остановка, изменение громкости — прежнее значение.
`undo_task` выполняет компенсации в обратном порядке (через политику); необратимые эффекты
перечисляются явно. Для изменений в репозиториях дополнительно есть снапшоты и `rollback_task`
AI-Dev-System.

### Деградированные режимы

| Что недоступно | Что продолжает работать |
| --- | --- |
| LLM | L0/L1, рецепты, direct-команды; честное сообщение о режиме |
| AI-Dev-System | Всё, кроме руководств, контекста проектов от AI-Dev-System и dev-жизненного цикла |
| Голосовой процесс | Текстовые клиенты |
| GPU занят игрой | Fast path; при необходимости — малая модель на CPU |

## 10. История задач

- **Хранение:** `tasks` (метаданные, итог, проверка), трасса (span'ы шагов, вызовов моделей и
  инструментов), артефакты, эпизоды (выжимки для памяти). Для dev-задач — ссылка на запись
  задачи в AI-Dev-System.
- **Хранение во времени:** задачи, выжимки и аудит — бессрочно (они маленькие); span'ы — 30–90 дней;
  сырые промпты — 14–30 дней; артефакты — по квоте.
- **Поиск:** полнотекстовый (FTS5) по запросу, заголовку, выжимке; фильтры по проекту, статусу,
  дате, источнику.
- **Команды:** «что ты делал сегодня», «покажи вчерашнюю задачу про GOFRA», «повтори последнюю
  задачу», «отмени последнее».
- **UI:** список задач → таймлайн шагов → дерево трассы ([11-quality.md](11-quality.md#5-логирование-и-трассировка)).

## 11. Фоновые задачи

- **Две полосы.** Foreground — интерактивная задача, владеющая «вниманием» (речь, ввод мыши и
  клавиатуры); одна за раз. Background — несколько задач с пониженным приоритетом у Gateway и
  более строгой политикой: без управления вводом, подтверждения ставятся в очередь с уведомлением,
  по умолчанию — только чтение, кроме рецептов с grant'ом.
- **Как задача попадает в фон:** явно («сделай в фоне», «следи за…»); автоматически, если
  foreground-задача длится дольше порога (например, 60 с) — пользователь может отдавать другие
  команды, а по завершении получит уведомление; по триггеру.
- **Наблюдатели (watchers):** долгоживущие лёгкие задачи без LLM — подписка на источник событий
  (события Docker, изменения файлов, завершение процесса, время) с условием. При срабатывании —
  новая задача или уведомление. Бюджет модели не расходуется, пока условие не сработало.
  Пример: «следи за контейнером backend и скажи, если упадёт» → наблюдатель на события Docker →
  при `die` уведомление «backend упал (exit 1). Разобраться?».
- **Сохранность:** фоновые задачи и триггеры сохраняются в SQLite и восстанавливаются после
  перезапуска; расписания — cron-выражения.
- **Управление:** «что ты сейчас делаешь?», «останови фоновые задачи», `task.list` в API.
- **Блокировки ресурсов:** `input` — эксклюзивно и только foreground; `project:<id>:write` — один
  пишущий; `audio.out` — у голосового процесса; GPU — очередь Gateway.

## 12. Проактивное поведение (будущее)

```
Сигналы (наблюдатели) → Правила (детерминированно) → Предложения → Менеджер внимания → Доставка → Задача
```

- **Сигналы:** события Docker и процессов, расписание, файлы, состояние системы (диск, сеть),
  привычки из эпизодов («по будням в 10:00 вы запускаете GOFRA»).
- **Предложение:** ценность × уверенность − стоимость прерывания; каждое — с объяснением
  «почему я это предлагаю».
- **Менеджер внимания:** не беспокоить в игре, в полноэкранном режиме, на звонке (микрофон занят
  другим приложением), в тихие часы; лимит непрошеных уведомлений в час; обучение на
  принятых и отклонённых предложениях.
- **Доставка:** уведомление Windows, «входящие» Jarvis, голосом — только срочное и только если
  разрешено.
- **Правило безопасности:** проактивно — только предлагать. Действие с побочными эффектами
  начинается после явного согласия или по заранее выданному постоянному grant'у на конкретный
  рецепт. Origin `proactive` получает самую строгую политику.
- **Предпосылки:** фоновые задачи, триггеры, эпизодическая память, предпочтения, канал уведомлений.
  Поэтому проактивность — последняя стадия roadmap.
