# 10. Платформа: события, хранилище, конфигурация, плагины, модели, дистрибуция, API

## 1. События

### Нужен ли event bus

Да, но **только для наблюдения**. Для локального desktop-приложения с одним пользователем
адекватны три механизма, и у каждого своя роль:

| Механизм | Роль | Гарантии |
| --- | --- | --- |
| Явные async-вызовы | Поток управления: роутер → исполнитель → Tool Runtime → … | Обычная семантика вызова и исключений |
| In-process шина событий | Уведомления: UI, голос, логи, плагины-подписчики | Не блокирует ядро; у подписчика ограниченная очередь; для чисто UI-событий допускается слияние и пропуск со счётчиком |
| Персистентная трасса (SQLite) | События задач: таймлайн, replay, обучение рецептам | Пишется в транзакции шага; не теряется |

Аудит пишется **синхронно** самим Tool Runtime, а не через шину, — чтобы никакой медленный подписчик
не мог привести к потере записи.

Внешний брокер (Kafka, Redis, NATS, ZeroMQ) не нужен: процесс один, пользователь один, а клиентам в
других процессах события доставляет WebSocket. Подписчик, на котором держится логика ядра, — ошибка
дизайна: логика должна быть в явных вызовах.

### Формат

```json
{"id": "evt_01J…", "type": "tool.call.finished", "v": 1, "ts": "2026-10-01T10:15:02.120Z",
 "task_id": "t_0042", "span_id": "sp_…", "source": "tools",
 "data": {"tool": "docker.logs", "status": "ok", "risk": "safe", "duration_ms": 412}}
```

Имена — `домен.сущность.глагол_в_прошедшем`; у схемы события есть версия `v`. Событие — факт, а не
команда; команды идут методами API.

| Домен | События |
| --- | --- |
| Запросы и задачи | `request.received`, `task.created`, `task.status_changed`, `task.plan.updated`, `task.step.started`, `task.step.finished` |
| Модели и инструменты | `model.call.started`, `model.call.finished`, `tool.call.started`, `tool.call.finished` |
| Человек в контуре | `approval.requested`, `approval.resolved`, `user.question.asked`, `user.question.answered` |
| Навыки и память | `skill.selected`, `recipe.proposed`, `memory.fact.created`, `memory.fact.deleted` |
| Голос | `voice.wake`, `voice.utterance.recognized`, `voice.speak.started`, `voice.speak.finished`, `voice.barge_in` |
| Система | `system.model.loaded`, `system.model.unloaded`, `system.mcp.connected`, `system.mcp.disconnected`, `system.degraded`, `update.available`, `update.installed` |

Клиенты подписываются по темам с курсором (идентификатор последнего полученного события) и после
переподключения дочитывают пропущенные персистентные события.

## 2. Хранилище

### Расположение на Windows

```
%LOCALAPPDATA%\Jarvis\
  config\     config.toml, policies.toml, profiles\, intents\ (пользовательские)
  data\       jarvis.db, traces.db, audit.db
  blobs\      sha256\ab\cd\…      артефакты: выводы, скриншоты, бэкапы файлов
  skills\     <id>\SKILL.md, recipe.yaml — навыки пользователя
  models\     модели, загруженные через Jarvis (по согласию)
  logs\       системные логи (JSON lines, ротация)
  updates\    загруженные обновления
  backups\    резервные копии БД (ежедневные и перед миграциями)
```

Само приложение лежит отдельно (раздел 6), поэтому обновление не трогает данные.

### SQLite

Режим WAL, три файла:

| Файл | Содержимое | Почему отдельно |
| --- | --- | --- |
| `jarvis.db` | Сессии, сообщения, задачи и чекпоинты состояния, факты, эпизоды, ошибки, проекты и алиасы, инвентарь приложений, индекс навыков, кэш навыков, grant'ы, триггеры, переопределения настроек | Основное состояние |
| `traces.db` | Span'ы, вызовы моделей, события задач | Большой объём, своя политика хранения и VACUUM |
| `audit.db` | Журнал аудита с цепочкой хэшей | Только добавление, долгое хранение, отдельные бэкапы |

- Полнотекстовый поиск — FTS5; векторы — `sqlite-vec` (с записью модели эмбеддингов и размерности).
- Доступ — через репозитории по агрегатам (`TaskRepo`, `FactRepo`, …): SQL в одном месте, остальной
  код не знает о схеме. Один пишущий поток на файл (так устроен SQLite), читателей — несколько.
- **Миграции:** пронумерованные SQL-миграции + миграции данных на Python; `schema_version`; резервная
  копия перед миграцией; **в CI миграции прогоняются на фикстурных базах предыдущих версий** — без
  этого обновления из GitHub рано или поздно сломают чью-то базу.
- **Blobs** адресуются по `sha256`, на них ссылаются строки БД; очистка — по сроку хранения и квоте.
- Навыки и рецепты лежат файлами (их можно читать, править и хранить в git), индекс в БД
  перестраивается при изменении файлов.
- Резервные копии: ежедневно `jarvis.db` и `audit.db` через backup API SQLite, с ротацией; экспорт по команде.

## 3. Конфигурация

Слои, от низшего приоритета к высшему:

1. Встроенные умолчания (в коде).
2. Умолчания в файлах приложения (`defaults\`, обновляются вместе с приложением).
3. Конфиг пользователя `%LOCALAPPDATA%\Jarvis\config\config.toml`.
4. Переменные окружения `JARVIS_*` (разработка и отладка).
5. Переопределения из UI или API — сохраняются отдельно и видны как переопределения.

- **Формат** — TOML; валидация — pydantic-settings; неизвестный ключ — предупреждение; ошибка — отказ
  стартовать с понятным сообщением и предложением безопасного режима.
- **Разделы:** `[models]`, `[voice]`, `[mcp]`, `[projects]`, `[memory]`, `[updates]`, `[privacy]`,
  `[ui]`, `[profiles.*]`; политика — в отдельном `policies.toml`.
- **Секретов в конфиге нет** — только хэндлы `secret://…`.
- **Версия схемы конфига** и миграции при обновлении.
- **Горячая перезагрузка** — только для «данных» (алиасы, интенты, рецепты, политики); смена моделей
  или MCP-серверов перезапускает компонент; остальное — перезапуск `jarvisd`.
- **Профили железа и режимы:** `rx7600-8g`, режимы `game`, `quiet`, `battery` — наборы
  переопределений ролей моделей и голосовых настроек.
- **`jarvis doctor`:** проверка конфига, доступности LLM и MCP-серверов, Vulkan-устройства, аудиоустройств.
- **Первый запуск (мастер):** определить железо и предложить профиль → выбрать рантайм моделей
  (существующий LM Studio / Ollama или управляемый llama.cpp) → загрузить модели по согласию с
  указанием размера → проверить микрофон → указать корни проектов и путь к AI-Dev-System → выбрать
  уровень автономности.

## 4. Плагины и расширяемость

| Уровень | Что | Изоляция | Для кого |
| --- | --- | --- | --- |
| Данные | Рецепты, грамматики интентов, профили агента, политики, алиасы, промпты | Это не код | Пользователь |
| MCP-серверы | Инструменты, ресурсы, промпты — на любом языке | Отдельный процесс + манифест политики | **Основной путь расширения** |
| Python entry points | Адаптеры платформы, провайдеры моделей, движки STT/TTS/wake word, grounders, источники навыков, типы проверок, источники триггеров | В процессе, доверенный код | Разработчики |

Правила:

- API плагинов версионируется (semver); плагин объявляет, какие возможности добавляет.
- Python-плагины загружаются только из явного списка в конфиге; никакой автоустановки из интернета.
- Инструменты из плагинов проходят через Tool Runtime и политику, как встроенные; ослабить политику
  плагин не может.
- В exe-сборке полностью поддерживаются данные и MCP; Python-плагины — в зависимости от способа
  упаковки (раздел 6.3).
- Позже Jarvis может сам выступать **MCP-сервером**, отдавая выбранные инструменты рабочего стола
  (под своей политикой) другим агентам — зеркальная роль по отношению к AI-Dev-System.

## 5. Независимость от моделей

### Протоколы

```python
class ChatModel(Protocol):
    info: ModelInfo                                   # id, контекст, возможности
    async def complete(self, req: ChatRequest) -> ChatResponse: ...
    def stream(self, req: ChatRequest) -> AsyncIterator[ChatDelta]: ...

class ChatRequest(BaseModel):
    messages: list[Message]                           # части: текст и изображения
    response_schema: dict | None = None               # JSON Schema → ограниченное декодирование
    tools: list[ToolSchema] | None = None             # только для стратегии native_tools
    max_tokens: int
    temperature: float = 0.0
    seed: int | None = None
    reasoning: Literal["off", "low", "high"] | None = None

class EmbeddingModel(Protocol):
    async def embed(self, texts: list[str], kind: Literal["query", "document"]) -> list[list[float]]: ...

class Reranker(Protocol):
    async def rerank(self, query: str, docs: list[str]) -> list[float]: ...
```

`SpeechToText`, `TextToSpeech`, `WakeWordDetector` и `Grounder` — такие же узкие протоколы.

### Провайдеры

| Провайдер | Покрывает |
| --- | --- |
| `openai_compat` | llama.cpp server, LM Studio, Ollama, vLLM — всё, что говорит на OpenAI-совместимом API |
| `onnx_local` | Эмбеддинги и реранкер в процессе (CPU) |
| `scripted` | Тесты: заранее заданные ответы |
| `cassette` | Воспроизведение записанных ответов из трасс ([11-quality.md](11-quality.md#4-воспроизводимость)) |
| облачный (позже, опционально) | Через тот же протокол; выключен по умолчанию |

### Профили моделей

Всё, что специфично для модели, описано в её профиле, а не в коде ядра:

```toml
[model_profiles.example]                         # пример, не рекомендация
action_strategy = "json_schema"                  # json_schema | native_tools | two_step | prompt_parse_repair
reasoning = { off = "<способ отключить размышления>", on = "<способ включить>" }
temperature = { router = 0.0, executor = 0.2, planner = 0.3 }
reliable_context = 12000                         # сколько контекста модель реально «держит»
vision_coords = "absolute_px"                    # соглашение о координатах для grounding
```

- **Пробы при старте:** поддерживается ли ограниченное декодирование по JSON Schema, скорость
  генерации, доступный контекст.
- **Промпты** — версионируемые файлы шаблонов с идентификаторами; в коде промптов нет.
  Переопределения под модель допустимы, но обязаны пройти eval.
- **Допуск модели к роли** — по таблице результатов eval-набора: точность роутера, доля валидного
  JSON, точность выбора инструмента, успешность задач, латентность. Смена модели — это изменение
  конфига плюс таблица результатов, а не правка кода.
- **Смена модели эмбеддингов** запускает фоновую переиндексацию.

## 6. Дистрибуция и обновления

Требование: Jarvis ставится как обычное Windows-приложение через `.exe`, обновляется из GitHub
Releases и скачивает обновления **только с разрешения пользователя**.

### 6.1. Что входит в поставку

| Компонент | Как доставляется | Как обновляется |
| --- | --- | --- |
| Приложение: трей/launcher, `jarvisd`, `jarvis-voice`, CLI, UI, встроенные грамматики, профили, рецепты, промпты | Установщик из GitHub Releases | Update Manager, по согласию |
| Python и зависимости | Внутри приложения (по lock-файлу) | Вместе с приложением |
| Модели (LLM, VLM, STT, TTS, эмбеддинги, wake word) | Model Manager: загрузка по согласию с указанием размера, проверка `sha256` | Отдельно, по согласию; каталог моделей с закреплёнными хэшами |
| Сервер моделей | Внешний (LM Studio / Ollama) или управляемый llama.cpp (Vulkan-сборка) | Отдельно, по согласию |
| AI-Dev-System | Отдельный продукт со своим установщиком | Своим механизмом; Jarvis проверяет совместимость версии |
| Данные пользователя | Установщик их не трогает | Миграции при первом старте новой версии, с резервной копией |

Модели в установщик не входят: это гигабайты, и у пользователя может уже быть LM Studio или Ollama.

### 6.2. Установка

- **Первая установка** — установщик для текущего пользователя (Inno Setup), без прав администратора
  и без UAC; это же позволяет обновляться без повышения прав.
- **Версии лежат рядом друг с другом**, а активную выбирает указатель. Обновление — это распаковка
  новой версии в соседний каталог и атомарное переключение указателя; откат — переключение обратно,
  без сети и без повторной установки (эту модель хорошо реализует dax-assistant, см.
  [14-prior-art.md](14-prior-art.md)).
- Автозапуск — для текущего пользователя (ключ `Run` или Планировщик заданий «при входе»), не служба.

```
%LOCALAPPDATA%\Programs\Jarvis\
  Jarvis.exe          стабильный launcher, трей и update-helper (меняется редко, через полный установщик)
  current             указатель на активную версию
  app-0.3.1\          предыдущая версия — для отката
  app-0.4.0\          активная версия:
    jarvisd\            сервер
    jarvis-voice\       голосовой процесс
    jarvis.exe          CLI
    ui\                 приложение Tauri (Stage 4)
    defaults\           встроенные грамматики, профили, рецепты, промпты
```

### 6.3. Упаковка Python

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| PyInstaller (onedir) | Быстрый старт работ; именованные exe; большое сообщество | Неподписанные сборки часто ловят ложные срабатывания антивирусов; Python-плагины неудобны |
| Nuitka (standalone) | Компиляция в C, быстрый запуск | Долгие сборки; ложные срабатывания тоже бывают |
| Официальный embeddable CPython + зависимости + небольшой launcher | Python-плагины — обычные пакеты; прозрачная структура | Свой launcher и сборочный скрипт |

Рекомендация: начать с PyInstaller (onedir) за сборочным скриптом, который скрывает выбор, и перейти
на embeddable CPython, если помешают антивирусы или понадобятся Python-плагины в exe-сборке. Когда
появится UI на Tauri, его приложение входит в тот же пакет, и механизм обновления остаётся **один**:
Update Manager в `jarvisd` проверяет, спрашивает, загружает и верифицирует, а update-helper в
стабильном launcher'е переключает версию и откатывает её. Встроенный обновлятор Tauri параллельно
не используется.

### 6.4. Обновление

```
1. Проверка     при старте и раз в N часов (настраивается и отключается): latest.json из последнего
                релиза GitHub — статический файл, без лимитов GitHub API
2. Решение      версия новее, канал совпадает (stable / beta), версия не «пропущена»
3. Уведомление  update.available → трей / UI / CLI / голос: «Вышла версия 0.4.0. Что нового: …»
                [Скачать и установить]  [Позже]  [Пропустить версию]
4. Загрузка     только после согласия: пакет приложения (архив); в фоне, с докачкой;
                на лимитной сети — отдельное согласие
5. Проверка     размер, SHA-256, подпись Ed25519, версия выше текущей, совместимость клиентов
                (api_compatibility); иначе файл удаляется
6. Распаковка   в app-0.4.0\ рядом с текущей версией — пока старая продолжает работать
7. Момент       нет foreground-задачи; фоновые — на чекпоинте и на паузе; «Перезапустить сейчас?»
8. Применение   update-helper (стабильный launcher): резервная копия БД и конфига → остановить
                jarvisd, голос и UI → атомарно переключить указатель current → запустить новую версию
9. Готовность   новая версия: миграции → health check (API отвечает, БД открыта, MCP поднялся) за N секунд
10. Итог        успех → запись в аудит «0.3.1 → 0.4.0, разрешил пользователь» и заметки о выпуске;
                хранятся 2–3 предыдущие версии для отката без сети;
                провал → указатель возвращается на app-0.3.1, БД восстанавливается из копии, отчёт
```

Манифест релиза (эскиз; по духу совместим с форматом обновлятора Tauri):

```json
{
  "version": "0.4.0",
  "channel": "stable",
  "pub_date": "2026-11-15T12:00:00Z",
  "notes": "…",
  "min_supported_from": "0.2.0",
  "api_compatibility": {"cli": ">=0.3", "ui": ">=0.4", "voice": ">=0.3"},
  "platforms": {
    "windows-x86_64": {
      "package": {
        "url": "https://github.com/BreezeAreaSay/Jarvis-Agent/releases/download/v0.4.0/Jarvis-0.4.0-win-x64.zip",
        "sha256": "…",
        "size": 123456789
      },
      "installer": {
        "url": "https://github.com/BreezeAreaSay/Jarvis-Agent/releases/download/v0.4.0/Jarvis-Setup-0.4.0.exe",
        "sha256": "…",
        "size": 125000000
      }
    }
  },
  "signature": "<Ed25519-подпись канонического JSON без этого поля>"
}
```

Принципы:

- Ничего не скачивается и не устанавливается без явного согласия.
- Обновлением управляет пользователь, а не модель: у агента нет такого инструмента
  ([09-security.md](09-security.md#12-обновления-и-цепочка-поставки)).
- Откатом руководит стабильный launcher, а не новая версия, которая может оказаться сломанной.
- Пакет обновления (архив) нужен для обычных обновлений, полный установщик — для первой установки и
  для редких обновлений самого launcher'а.

### 6.5. Релизный конвейер

1. Тег `v0.4.0` → GitHub Actions на Windows: `uv sync --frozen`, тесты, быстрый eval, тесты миграций
   на базах прошлых версий.
2. Сборка (PyInstaller) → пакет обновления (архив) и полный установщик (Inno Setup), контрольные суммы,
   `latest.json`.
3. Подпись манифеста ключом Ed25519 — в защищённом окружении с ручным подтверждением или локально
   у мейнтейнера.
4. Черновик релиза с ассетами → ручная публикация.
5. По решению Q11 — подпись exe сертификатом Authenticode.

## 7. Runtime API

- **Транспорт:** JSON-RPC 2.0 поверх WebSocket на `127.0.0.1` (случайный порт записывается в файл
  рантайма) или named pipe.
- **Аутентификация:** токен из файла, доступного только текущему пользователю; проверка заголовка
  Origin; без CORS. При рукопожатии клиент сообщает свой тип и `instance_id`; выданный токен привязан
  к ним, а совместимость версий клиента проверяется по `api_compatibility` из манифеста релиза.
- **Схемы** — в модуле `protocol` (pydantic) → JSON Schema → типы TypeScript для UI; `api_version`
  согласуется в `session.open`; совместимость назад — минимум на одну минорную версию.
- В Stage 0 CLI вызывает тот же фасад `RuntimeAPI` внутри процесса.
