# 01. Критический анализ концепции

Разбор исходного описания Jarvis: что в нём правильно, где слабые места, что преждевременно,
что слишком сложно для первой версии и какие решения могут завести проект в тупик.

## 1. Что в концепции правильно

Эти идеи сохраняются в предлагаемой архитектуре.

- **Отказ от «одной большой LLM».** Большинство провалов ассистентов — следствие того, что
  каждый запрос, включая «сделай громче», проходит через модель. Ступенчатое исполнение
  (детерминированно → навык → планирование) — верная основа.
- **Приоритет API → CLI → OS API → accessibility → vision.** Это одновременно порядок по
  надёжности, скорости, проверяемости и стоимости.
- **Разделение tool и skill** и **внешняя библиотека skills с поиском**, чтобы не тащить
  тысячи навыков в контекст.
- **Verifier как обязательный этап.** Редкая и ценная идея: «готово» только после проверки.
- **Permissions и audit log с первого дня.**
- **Local-first и заменяемые модели.**
- **AI-Dev-System как независимый продукт**, а Jarvis — один из его клиентов. Граница проведена
  правильно, и это подтверждает устройство самого AI-Dev-System: он уже обслуживает Claude Code,
  Cursor, Codex и Gemini через stdio.

## 2. Главные слабые места

### 2.1. Пятнадцать подсистем без вертикального среза

В описании около пятнадцати подсистем, каждая из которых сама по себе — проект: голос с
barge-in, GUI grounding, восемь типов памяти, skill graph, обучение на действиях, проактивность,
плагины, desktop UI. Для одного разработчика главный риск — построить фреймворк, в котором
ничего не работает целиком.

**Что делать:** «walking skeleton» — тонкий сквозной срез (запрос → маршрутизация → действие →
проверка → ответ → аудит), который потом утолщается. Каждая стадия roadmap заканчивается
работающими сценариями с измеримыми критериями ([13-roadmap.md](13-roadmap.md)).

### 2.2. Железо не учтено: роли моделей не помещаются в 8 ГБ VRAM

Схема «Router Model + Main Reasoning Model + Vision Model + Embedding Model» неявно
предполагает, что все модели загружены одновременно. На RX 7600 (8 ГБ VRAM) это невозможно:

| Компонент | Ориентировочный объём |
| --- | --- |
| LLM 8B, Q4_K_M | ≈5 ГБ весов |
| KV-кэш для 16k токенов у 8B-модели | ≈1,1 ГБ (q8_0) … ≈2,3 ГБ (fp16) |
| VLM 7–8B + проектор изображений | ≈5–6 ГБ |
| Windows/DWM, браузер с аппаратным ускорением | 0,3–1 ГБ VRAM |

Кроме того, у AMD на Windows нет CUDA, а ROCm/PyTorch для Windows ограничены: многие
Python-библиотеки (faster-whisper на GPU, sentence-transformers на GPU) здесь работают только на CPU.

**Что делать:** роль — это не отдельная загруженная модель. На GPU живёт **одна резидентная LLM**
(через llama.cpp с Vulkan-бэкендом или совместимый рантайм); STT, TTS, VAD, wake word,
эмбеддинги и реранкер работают на CPU через ONNX Runtime; vision — либо через мультимодальную
основную модель, либо подгрузкой по требованию. Model Gateway знает о резидентности и стоимости
переключений ([03-agent-core.md](03-agent-core.md#5-model-gateway-model-router)).

### 2.3. Главный технический риск — надёжность локальной модели в многошаговом tool use

Архитектура важна, но провалится проект, скорее всего, не из-за неё, а из-за того, что модель
7–9B ошибается в формате вызова, выбирает не тот инструмент, теряет цель на 15-м шаге и
зацикливается. Это нужно проверить в самом начале, а не после двух стадий инфраструктуры.

**Что делать:**

- максимум работы — детерминированно (fast path, рецепты), LLM — для того, что иначе не сделать;
- structured output с ограниченным декодированием (грамматика JSON Schema в llama.cpp);
- малые наборы инструментов на шаг (профили агента, 8–12 инструментов вместо 50);
- короткий сфокусированный контекст и выжимки вместо сырых логов;
- двухшаговое декодирование действия для слабых моделей (сначала инструмент, потом аргументы);
- eval-набор с первой стадии; опционально — сильная облачная модель *только для отладки*,
  чтобы отличать «баг архитектуры» от «не тянет модель».

### 2.4. LLM-роутер на каждый запрос — лишняя латентность и недетерминизм

«Router должен быть маленьким и быстрым» — верно; «Router — это модель» — нет. Даже модель на
1–3B добавляет сотни миллисекунд и иногда ошибается на «открой Spotify». Вторая модель на GPU
к тому же отнимает память у основной (см. 2.2).

**Что делать:** каскад. Сначала грамматики команд со слотами и резолвер сущностей (приложения,
проекты, файлы) — миллисекунды, детерминированно. Затем триггеры рецептов (лексика + эмбеддинги).
Только потом LLM-классификатор с ответом строго по схеме — и это может быть основная модель в
«режиме роутера» с коротким выводом. Отдельная маленькая модель-роутер — только если замеры
покажут, что это нужно. И главное: роутинг — первая догадка. Простая команда, которая не
сработала («приложение не найдено»), эскалируется в агентный цикл.

### 2.5. `ModelProvider` смешивает разные сервисы и фиксирует не тот уровень абстракции

```
class ModelProvider:
    async def generate(...)
    async def tool_call(...)
    async def vision(...)
    async def embeddings(...)
```

Проблемы:

- **Эмбеддинги — отдельный сервис:** другая модель, батчи, часто CPU. Им не место в одном классе
  с генерацией.
- **Vision — не отдельный метод,** а мультимодальный вход в ту же генерацию.
- **`tool_call` на уровне провайдера привязывает ядро к нативным форматам моделей.** Форматы
  вызова инструментов у Qwen, Llama, Mistral, GPT-OSS различаются, а парсеры в рантаймах
  периодически ломаются. Если ядро опирается на нативный tool calling, смена модели ломает
  агента.

**Что делать:** узкие протоколы — `ChatModel` (сообщения с текстом и изображениями, опциональная
JSON Schema ответа), `EmbeddingModel`, `Reranker`, `SpeechToText`, `TextToSpeech`. Вызов
инструментов — **протокол ядра поверх structured output**: ядро даёт схему действия, провайдер
гарантирует ответ по схеме. Нативный tool calling — оптимизация, которую включают для модели,
если eval показал, что так лучше ([10-platform.md](10-platform.md#5-независимость-от-моделей)).

### 2.6. Planner → Executor → Verifier как водопад не работает для диагностики

Для «почему Docker-контейнер падает» нельзя заранее спланировать шаг 4, не увидев логи на
шаге 2. Жёсткая схема «сначала весь план, потом исполнение» ломается на любой исследовательской
задаче.

**Что делать:** план — живой артефакт. Planner формулирует цель, **критерии приёмки** (по
возможности исполняемые проверки) и черновые шаги; Executor работает циклом
«наблюдение → действие» внутри шага; неожиданное наблюдение или провал проверки запускает
перепланирование (с лимитом). Verifier проверяет критерии, заданные *до* исполнения, а не
спрашивает модель «ну что, получилось?». Planner, Executor и Verifier — роли (разные промпты и
контексты), а не обязательно разные модели или процессы.

### 2.7. «Skill» означает две разные вещи

Пример `docker.deploy` в описании смешивает два разных артефакта:

| | Руководство (guide) | Рецепт (recipe) |
| --- | --- | --- |
| Что это | Знание: как подходить к задаче | Процедура: какие действия выполнить |
| Кто исполняет | LLM читает и применяет | Движок рецептов исполняет детерминированно |
| Формат | SKILL.md (проза + frontmatter) | YAML: параметры, шаги-инструменты, проверки |
| Переносимость | Любой агент (Claude Code, Codex, Jarvis) | Только среда, где есть эти инструменты |
| Пример | `bugfix-investigator`, `container-deployment-reviewer` | `start_gofra_project`, «громкость по профилю» |
| Где живёт | AI-Dev-System | Jarvis |

Шаги `inspect_project`, `validate_compose`, `connect_server` в YAML-примере — это имена, а не
исполняемые действия: либо каждое отображается на инструмент/рецепт (тогда это рецепт), либо
это проза для модели (тогда это руководство). Навыки в AI-Dev-System — именно руководства
(SKILL.md с frontmatter `name`/`description`), и это правильно для их задачи.

**Что делать:** ввести оба понятия явно и дать им общий формат папки навыка: `SKILL.md`
(руководство) и необязательный `recipe.yaml` (исполняемая грань). Тогда выученный workflow
становится одновременно рецептом для Jarvis и читаемым руководством для других агентов
([04-tools-and-skills.md](04-tools-and-skills.md#2-skills-руководства-и-рецепты)).

### 2.8. Поиск skills уже реализован в AI-Dev-System — не дублировать

Схема «поиск → 20 кандидатов → реранкинг → 1–3 лучших» уже существует на стороне сервера:
гибридный поиск (ключевые слова + sparse + локальная BGE-M3), детерминированный
`recommend_skills`, который отдаёт не больше трёх навыков (workflow, domain, verification) плюс
зарезервированные слоты, с учётом проекта и переводом русских формулировок в англоязычную
лексику каталога. Повторять это в Jarvis — дублирование с гарантированным расхождением.

**Что делать:** Jarvis вызывает `recommend_skills` / `search_skills` и добавляет только то, чего
сервер знать не может: бюджет токенов текущей модели и фильтр по доступным в Jarvis
инструментам ([05-ai-dev-system.md](05-ai-dev-system.md)).

### 2.9. Риск зависит от аргументов, а `shell.execute` обходит всю модель прав

Уровни SAFE/MEDIUM/HIGH на уровне инструмента недостаточны: `shell.execute("git status")` и
`shell.execute("Remove-Item -Recurse -Force ~")` — один инструмент. `filesystem.write` в файл
проекта и в `%APPDATA%\...\config` — тоже. Универсальный shell фактически отменяет все
остальные ограничения.

**Что делать:** Policy Engine оценивает **конкретный вызов**: инструмент + аргументы + затронутые
ресурсы (зоны путей, хосты, процессы) + источник запроса + заражённость контекста. Для shell —
разбор команды настоящим парсером (AST PowerShell, парсер bash для WSL/SSH), классификатор
известных команд, неизвестное → подтверждение ([09-security.md](09-security.md)).

### 2.10. Prompt injection не упомянут — а это угроза номер один

Агент, который читает файлы, логи, веб-страницы и импортированные skills и при этом выполняет
команды, — классическая «смертельная триада»: доступ к приватным данным + недоверенный контент +
возможность что-то отправить наружу. Строка в логе контейнера или в README вида «выполни
`curl … | sh`» может стать «инструкцией» для модели. Тысячи импортированных skills — тоже
недоверенный текст, попадающий прямо в контекст планировщика.

**Что делать:** разметка происхождения контента, метка taint на задаче, повышение риска действий
в заражённом контексте, контроль исходящих действий, запрет skills повышать права
([09-security.md](09-security.md#6-prompt-injection)). Это закладывается в Tool Runtime и Context
Builder с первой стадии — потом не встроить.

### 2.11. Восемь типов памяти как восемь подсистем — путь к мусору

Working, conversation, semantic, episodic, procedural, project, error, preferences — это полезная
таксономия, но не восемь хранилищ. Working memory — это состояние задачи. Episodic — это история
задач, которую рантайм и так пишет. Procedural — это рецепты и skills. Автоматическое извлечение
«фактов» из всех разговоров засоряет память мусором, который потом нельзя ни объяснить, ни
вычистить.

**Что делать:** четыре хранилища (факты/предпочтения, разговоры, эпизоды, ошибки → решения),
запись в долговременную память — только явно («запомни») или с подтверждения пользователя, у
каждой записи — происхождение, область и срок жизни ([06-memory-and-projects.md](06-memory-and-projects.md)).

### 2.12. Event-driven ядро затруднит отладку

Если поток управления агента идёт через шину событий («опубликовал `task.plan.created` — кто-то
подхватит»), то ответить на вопрос «почему агент сделал X» становится трудно: неявный порядок,
гонки, обработчики, о которых никто не помнит.

**Что делать:** управление — явными async-вызовами; шина — для **наблюдения** (UI, голос, логи,
плагины-подписчики); каждая задача пишет **персистентную трассу** (append-only), из которой
строятся аудит, UI-таймлайн, replay и данные для обучения рецептам. Никаких внешних брокеров
([10-platform.md](10-platform.md#1-события)).

### 2.13. Нет модели окружения

«Открой Telegram», «найди договор, скачанный вчера», «запусти GOFRA» требуют знания, которого в
схеме нет: инвентарь установленных приложений (на Windows — ярлыки меню «Пуск» и пакеты AppX),
индекс файлов (Everything или Windows Search; признак «скачан» и источник — в альтернативном
потоке `Zone.Identifier`), реестр проектов с алиасами и **средами исполнения** (Windows, WSL,
удалённый сервер по SSH, контейнер). Именно это знание позволяет выполнять большую часть команд
без LLM.

**Что делать:** Entity Resolver + инвентарь окружения + `ExecEnv` как явная часть модели
([08-computer-use.md](08-computer-use.md), [06-memory-and-projects.md](06-memory-and-projects.md#2-контекст-проектов)).

### 2.14. Нет управления контекстом и большими выводами

`docker logs` легко отдаёт мегабайты. У локальной модели на 8 ГБ VRAM рабочий контекст —
12–16k токенов. Если вывод инструментов идёт в контекст как есть, агент ослепнет на втором шаге.

**Что делать:** инструмент возвращает выжимку + ссылку на артефакт; агент может прочитать
фрагмент артефакта по запросу; специализированные детерминированные «сжиматели» (извлечение
ошибок из логов, сводка `docker inspect`); Context Builder с бюджетом по секциям и стабильным
префиксом для переиспользования KV-кэша ([03-agent-core.md](03-agent-core.md#7-context-builder)).

### 2.15. Не описаны отмена, конкуренция за ресурсы и undo

Пользователь говорит «стоп» посреди задачи; две задачи одновременно хотят управлять мышью;
агент переписал не тот файл. Ничего из этого не встроить потом без переписывания ядра.

**Что делать:** структурированная конкурентность с отменой (cancel scope на задачу, убийство
дерева процессов); именованные блокировки ресурсов (ввод — эксклюзивно); журнал эффектов с
бэкапами для обратимых действий; удаление — в корзину ([03-agent-core.md](03-agent-core.md#9-ошибки-и-восстановление)).

### 2.16. Нет eval-контура — а без него «независимость от модели» не проверить

Требование «модели заменяемы» имеет смысл, только если есть набор сценариев, на котором новую
модель можно прогнать и сравнить. Иначе каждая замена модели — лотерея.

**Что делать:** eval-набор — с первой стадии; модель «допускается» к роли по метрикам; трассы
записываются так, чтобы их можно было воспроизвести ([11-quality.md](11-quality.md)).

## 3. Overengineering для первой версии

| Идея | Почему рано | Когда вернуться |
| --- | --- | --- |
| Skill Graph как отдельный движок/графовая БД | Композиция решается вызовом рецепта из рецепта (дерево по построению); связи между руководствами уже есть в таксономии AI-Dev-System | Когда рецептов станут сотни и появится реальная потребность в автоматической сборке |
| Отдельная модель-роутер | Правила + основная модель в режиме роутера покрывают задачу; вторая модель отнимает VRAM | Если замеры латентности L2-роутинга окажутся неприемлемыми |
| Восемь подсистем памяти | Четыре хранилища и один Recall покрывают все сценарии | Не возвращаться; расширять типами записей |
| Внешний брокер событий | Один процесс, один пользователь | Не нужен; при выносе компонентов в другие процессы хватит WebSocket |
| Собственный plugin API до MCP | MCP уже даёт процессную изоляцию и экосистему серверов | Python entry points — только для доверенных адаптеров (ОС, модели, голос) |
| Мультиагентность (агенты-планировщик, исполнитель, критик, общающиеся между собой) | Это роли одного цикла, а не отдельные агенты; лишние вызовы модели и латентность | Субагенты с изолированным контекстом — точечно, для анализа больших данных |
| Кроссплатформенность с первого дня | Утраивает объём работы в computer use | Порты и адаптеры закладываются сразу, реализации для Linux/macOS — позже |
| Desktop UI до стабилизации API | UI будет переписываться вслед за ядром | После Stage 2, когда API рантайма устоится |
| Автоматическое извлечение памяти из всех разговоров | Засоряет память, нарушает приватность | Предложения «запомнить?» с подтверждением — можно на Stage 2 |
| Пассивное наблюдение за ручными действиями пользователя | Технически тяжело (системные хуки), шумно, инвазивно | Возможно, никогда; учиться на собственных трассах Jarvis |
| Fine-tuning моделей | Сначала нужны данные | Трассы успешных задач — будущий датасет для дообучения роутера |

## 4. Слишком сложно для первой версии (но нужно в будущем)

| Возможность | В чём сложность | Где в roadmap |
| --- | --- | --- |
| Barge-in (перебивание голосом) | Нужна эхоподавляющая обработка (AEC) с опорным сигналом динамиков; без неё Jarvis «слышит сам себя» | Stage 3 — упрощённый вариант (wake word поверх TTS), полный — позже |
| Wake word «Джарвис» на русском | Обучение своей модели, баланс ложных срабатываний и пропусков | Stage 3: сначала push-to-talk, затем готовая модель «hey jarvis», затем своя |
| GUI через vision | Медленно на 8 ГБ (секунды на шаг), ненадёжно, трудно проверять | Stage 6, после UIA и браузера через DOM |
| Песочница для shell-команд | На Windows нет простого аналога bubblewrap | Сначала Job Objects + политика; для dev-команд — WSL/Docker как песочница |
| Проактивность с хорошей точностью | Нужен богатый контекст и обратная связь, иначе раздражает | Stage 7, на базе триггеров и фоновых задач |
| Семантический индекс содержимого всех документов | Объём, извлечение текста из PDF/DOCX, переиндексация | Сначала метаданные + Everything/Windows Search |
| Автоматическая композиция workflow из графа навыков | По сути HTN-планирование; с LLM нестабильно | Не планируется в обозримых стадиях |

## 5. Решения, которые загонят проект в тупик

1. **Опора на нативный tool calling одной модели или API одного рантайма** (например, только
   Ollama). Смена модели ломает агента.
2. **Shell, доступный модели в обход единой точки политики.** Безопасность потом не встроить:
   каждое новое место исполнения — новая дыра.
3. **Шина событий как основной поток управления.** Отладка умирает первой.
4. **Память как неструктурированные заметки, написанные LLM, без происхождения.** Её нельзя ни
   почистить, ни объяснить, ни доверять ей.
5. **Исполняемые навыки как проза, которую LLM интерпретирует на лету** — недетерминированно и
   непроверяемо. Или наоборот: все навыки как код — тогда ими не поделиться с другими агентами.
6. **Монолитный процесс «UI + голос + агент».** Реальное время аудио, паузы сборщика мусора и
   блокирующие вызовы дают заикания; падение одного компонента роняет всё.
7. **Отсутствие трасс с первого дня.** Без трасс нет replay, нет eval, нет обучения рецептам —
   а обучение на workflow целиком построено на трассах.
8. **ОС-специфичные вызовы, размазанные по инструментам.** Без портов и адаптеров нельзя ни
   тестировать на фейках, ни переносить на другую ОС.
9. **Тяжёлый агентный фреймворк как фундамент** (LangChain, CrewAI, AutoGen). Агентный цикл —
   сердце продукта; чужие абстракции, их изменения и протечки станут вашими проблемами.
10. **Чтение внутренних файлов AI-Dev-System (vault, SQLite, JSON) в обход MCP API.** Первая же
    перестройка хранилища на его стороне сломает Jarvis.
11. **Все инструменты MCP-серверов в контексте модели.** У AI-Dev-System 133 инструмента в 8
    профилях: только схемы — десятки килобайт, а точность выбора инструмента у малой модели
    падает с ростом их числа.
12. **Vision-first управление компьютером.** Медленно, ненадёжно, плохо проверяемо.
13. **Права, которые навык выдаёт себе сам** («allow always for this skill» для импортированного
    навыка). Разрешения привязываются к локальному, проверенному пользователем рецепту и его хэшу.
14. **Роутер как одно решение без эскалации.** Любая ошибка классификации становится ошибкой
    задачи.
15. **Запуск рантайма как службы Windows.** Служба работает в сессии 0 и не видит рабочий стол
    пользователя: ни UI Automation, ни скриншотов, ни ввода. `jarvisd` — фоновый процесс в
    сессии пользователя.

## 6. Критика предложенной структуры каталогов

Исходный набросок:

```
jarvis/
  apps/ desktop/ cli/
  core/ agent/ planner/ executor/ verifier/ router/
  models/ providers/ router/ embeddings/
  voice/ wake_word/ vad/ stt/ tts/
  computer/ filesystem/ shell/ process/ windows/ input/ screen/
  skills/ engine/ resolver/ registry/
  mcp/ client/
  memory/ working/ episodic/ semantic/ projects/ errors/
  vision/ capture/ grounding/
  security/ permissions/ policies/ audit/
  events/ storage/ config/ tests/
```

Что не так:

1. **Много мелких пакетов по техническим категориям.** Десятки почти пустых каталогов на старте
   создают преждевременные границы, которые потом дорого переносить. Границы появляются, когда
   появляется код, который им подчиняется.
2. **`core/planner`, `core/executor`, `core/verifier`, `core/router` — отдельные пакеты** при том,
   что они делят одну модель состояния задачи и меняются вместе. Это один пакет `agent` с
   модулями.
3. **Коллизия имён `core/router` и `models/router`.** Это два разных роутера (маршрутизация
   запросов и выбор модели), и названия должны это отражать: Intent Router и Model Gateway.
4. **`mcp/` как доменная сущность верхнего уровня.** MCP — транспорт и протокол интеграции. Он
   используется и слоем инструментов (внешние MCP-инструменты), и слоем навыков (AI-Dev-System
   как источник руководств). Его место — `integrations/mcp`.
5. **`vision/` отдельно от `computer/screen`.** UI grounding — стратегия слоя управления
   компьютером; vision-модель — часть слоя моделей. Отдельный пакет `vision` разрывает и то, и
   другое.
6. **`memory/working` и `memory/projects`.** Рабочая память — это состояние задачи в `agent`;
   проекты — отдельный доменный сервис, использующий память и AI-Dev-System.
7. **Нет слоя платформы.** `computer/filesystem`, `computer/windows` смешивают «что делает
   инструмент» и «как это сделать на конкретной ОС». Нужны порты (`platform/ports`) и адаптеры
   (`platform/windows`, `platform/fake`).
8. **Нет границы API рантайма** (сервер, протокол, аутентификация) — а именно она делает
   клиентов независимыми от ядра.
9. **Нет `evals/`** — набора сценариев, отдельного от unit-тестов.
10. **`voice` внутри основного пакета.** Голос — отдельный процесс со своими зависимостями
    (аудио, ONNX-модели); он должен зависеть только от протокола, а не от всего ядра.

Предлагаемая структура — в [02-overview.md](02-overview.md#8-структура-репозитория).

## 7. Что меняется по сравнению с исходной схемой

| Было | Стало |
| --- | --- |
| Intent Router = маленькая LLM | Каскад: грамматики и резолвер сущностей → триггеры рецептов → LLM; эскалация при неудаче |
| Task Classification: simple / skill / complex / vision | Route: `direct` / `recipe` / `agent` / `chat` / `clarify`; vision — возможность внутри исполнения, а не класс запроса |
| Planner → Executor → Verifier линейно | Цикл с живым планом, критериями приёмки и ограниченным перепланированием |
| `ModelProvider` с `tool_call` | Узкие протоколы + Model Gateway; вызов инструментов — протокол ядра поверх structured output |
| Skill = YAML-процедура | Руководство (SKILL.md, AI-Dev-System) + рецепт (YAML, Jarvis) в общем формате папки навыка |
| Поиск и реранкинг skills в Jarvis | `recommend_skills` в AI-Dev-System; Jarvis добавляет только бюджет и фильтр по инструментам |
| Риск — свойство инструмента | Риск — свойство конкретного вызова в контексте (аргументы, зоны, источник, taint) |
| Восемь типов памяти | Четыре хранилища + Recall; procedural = рецепты и skills |
| Event-driven core | Явные вызовы + шина наблюдения + персистентная трасса |
| Memory в конце конвейера | Память и контекст проекта читаются **до** планирования, пишутся после проверки |
| Нет политики между Executor и ОС | Tool Runtime с Policy Engine — обязательное звено |
| Один процесс | `jarvisd` + отдельные процессы голоса, UI, моделей и MCP-серверов |
| Поставка не продумана | `.exe`-установщик, обновления из GitHub Releases по согласию, версионированные миграции данных с первого дня |

## 8. Продуктовый фокус

«Local Agent Operating Layer» — хорошее видение, но для приоритизации нужен узкий клин: первый
сценарий, в котором Jarvis незаменим. Для вас это **ассистент разработчика на собственном ПК**:
проекты, Docker, логи, репозитории плюс базовое управление компьютером голосом. Здесь у вас есть
преимущество, которого нет у универсальных ассистентов: AI-Dev-System с навыками, контекстом
проектов и проверяемым жизненным циклом задач, а у самих задач — **детерминированная проверка**
(тесты, healthcheck, статус контейнера). В общих задачах рабочего стола проверка размыта — там
агент заведомо слабее.
