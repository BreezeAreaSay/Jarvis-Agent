# ADR 0021. Аренды задач и оптимистическая единица работы

- **Статус:** Принято
- **Дата:** 2026-10-01
- **Уточняет:** [ADR 0003](0003-sqlite-storage.md), [ADR 0010](0010-task-state-machine.md); заменяет эскиз порта
  `TaskLeases` из [03-contracts.md](../stage0/03-contracts.md)

## Контекст

В эскизе Stage 0 аренда была отдельным портом `TaskLeases` с `acquire` / `renew` / `release`, вне
единицы работы. При реализации M2 выяснилось, что так нельзя защититься от гонок между процессами:

- восстановление решает «аренда истекла — задача прервана», а владелец в это время продлевает аренду;
  без проверки аренды в той же транзакции задача живого процесса становится FAILED;
- процесс, потерявший аренду (завис дольше срока), может записать контрольную точку поверх решения
  другого процесса, если проверяется только версия задачи, а продление аренды версию не меняет;
- событие ошибки, записанное отдельно от перехода, оставляет трассу, которая расходится с задачей.

## Решение

- **Единица работы оптимистическая.** Чтения идут в одном снимке; записи копятся и применяются на
  `commit()` одной короткой транзакцией (`BEGIN IMMEDIATE` в SQLite), где каждое ожидание — версия
  задачи, строка аренды, отсутствие дубликата — условие самого запроса. Расхождение —
  `ConcurrentModification`, ничего не записано. InMemory ведёт себя так же; общий набор контрактных
  тестов это проверяет.
- **Аренда — репозиторий внутри единицы работы** со сравнением-и-записью (`put(lease, expected=…)`,
  `delete(task_id, expected=…)`). Правила (срок, чья аренда, живая ли) — в `core.leases`.
- **Жизненный цикл аренды:** `submit` пишет задачу, событие создания и аренду одной транзакцией;
  каждая контрольная точка активной задачи продлевает аренду сравнением-и-записью (это и есть
  ограждение записи); фоновый heartbeat продлевает её каждую треть срока во время долгого такта;
  контрольная точка, выводящая задачу из активных состояний (WAITING_CONFIRMATION или терминальное),
  удаляет аренду. Срок — `runtime.lease_ttl_s` (по умолчанию 30 с).
- **Чужая живая аренда** — `TaskBusy` и для прогона, и для отмены; флага отмены в базе нет.
- **Активная задача без живой аренды** принадлежала процессу, который завершился. Её не продолжают
  (неизвестно, что сделал прерванный такт): восстановление при старте команд CLI и попытка прогона
  переводят её в FAILED с ошибкой категории `interrupted`. Так же завершается прогон, остановленный
  посреди такта (выход процесса), если клиент не успел запросить отмену.
- **Контрольная точка** — строка задачи, событие перехода, события, которые его объясняют (`error`,
  `budget.exceeded`, `task.finished`), и операция с арендой — одна транзакция. Отдельно пишутся только
  выдача ID (сразу, вне контрольной точки) и продление аренды heartbeat'ом.

## Альтернативы

- Порт `TaskLeases` вне единицы работы — гонки выше; закрыть их можно только блокировками между
  процессами.
- Пессимистические транзакции на весь такт — долгие блокировки записи на время работы стадии (вызова
  модели, инструмента); второй процесс не прочитает даже список задач.
- Продолжать прерванную задачу с контрольной точки — повтор действия, которое уже могло произойти.
- Флаг отмены в строке задачи, который опрашивает владелец, — конфликт с версией задачи и опрос базы.

## Последствия

- Задача и трасса не расходятся: всё, что объясняет переход, записано вместе с ним.
- Процесс, потерявший аренду, ничего не запишет: его контрольная точка не пройдёт сравнение.
- После падения процесса его задача до истечения аренды считается занятой (`TaskBusy`), затем
  становится FAILED (`interrupted`).
- Возобновление с контрольной точки возможно только из WAITING_CONFIRMATION (в M5) — аренды там нет.
