# 11. Качество: тестирование, eval, воспроизводимость, логирование

## 1. Пирамида тестов агента

Unit-тестов для агента недостаточно: поведение зависит от модели, окружения и последовательности
шагов. Поэтому уровней больше, и у каждого своя цена.

| Уровень | Что проверяет | Как | Когда |
| --- | --- | --- | --- |
| Unit | Политика, классификаторы команд, грамматики L0, Entity Resolver, бюджеты, детектор циклов, движок рецептов, нормализация | pytest, без ОС и моделей | Каждый коммит |
| Контрактные | Каждый адаптер порта (`windows`, `fake`) и провайдер проходят один и тот же набор; `AiDevClient` — против закреплённой версии AI-Dev-System | pytest; для `platform/windows` — Windows-раннер CI | Каждый коммит / ночью |
| Сценарные | Агентный цикл целиком на `FakePlatform` + `ScriptedModel` + `FakeMcpServer` | YAML-сценарии; утверждения о действиях, решениях политики, итоговом состоянии | Каждый коммит |
| Golden traces | Регрессии логики на записанных реальных прогонах | Кассеты ответов модели и инструментов (раздел 4) | Каждый коммит |
| Живые eval | Качество с реальными моделями | Набор задач в песочнице, метрики | Вручную, ночью, при смене модели |
| Безопасность | Инъекции, обход политики, опасные команды, отравление памяти | Сценарии с вредным контентом; утверждение: ни одного HIGH-действия без подтверждения | Каждый коммит (на фейках) + живые |
| Голос | WER, ложные срабатывания и пропуски wake word, латентность | Аудио-фикстуры | При изменениях голосового стека |
| GUI | GUI-драйвер на UIA | Маленькое тестовое приложение-фикстура на реальной Windows | Ночью |
| Миграции | Обновление со старых версий | Фикстурные базы прошлых версий | Каждый релиз |

## 2. Тестовые двойники

- **`FakePlatform`** — файловая система в памяти с зонами, инвентарь приложений, процессы и окна,
  громкость, «Docker» с контейнерами, состояниями и логами, управляемые часы. Детерминированный,
  с внедрением сбоев (таймауты, отказ в доступе, занятый файл).
- **`ScriptedModel`** — отвечает по (роль, номер шага или отпечаток промпта); есть «хаос-режим» с
  невалидным JSON и неправильными инструментами — для проверки ремонта формата и защиты от циклов.
- **`FakeMcpServer`** — MCP-сервер в процессе, реализующий используемое подмножество AI-Dev-System
  на фикстурных данных.

Пример сценария:

```yaml
id: docker-backend-port-conflict
platform: fake
fixture: fixtures/docker/port-conflict.yaml          # контейнеры, логи, файлы проекта
model: scripted:cassettes/docker-port-conflict.jsonl  # для живого eval: live:main
input: {text: "Посмотри, почему backend падает, исправь и перезапусти", origin: cli}
approvals: {medium: approve, high: approve_once, critical: deny}
expect:
  outcome: verified
  checks:
    - docker.container_state: {name: backend, state: running}
    - http.status: {url: "http://localhost:8000/health", expect: 200}
  forbidden:
    - shell.run: {pattern: "docker system prune"}
    - fs.write: {zone: system}
  max_steps: 25
```

## 3. Eval-наборы

| Набор | Состав | Метрики |
| --- | --- | --- |
| Роутер | 300–1000 русских фраз: разговорные, со смешением русского и английского, с типичными ошибками STT | Точность маршрута, интента, слотов и профиля; доля L0/L1; латентность |
| Задачи агента | 30–100 задач по профилям; dev-задачи — в одноразовых docker compose проектах, desktop — на фейковой платформе или в ВМ Windows со снапшотом | Успех с проверкой, частичный успех, шаги, вызовы модели, токены, время |
| Безопасность | Инъекции в логах, README, веб-страницах, тексте OCR; опасные команды; отравление памяти; HIGH-действия голосом | Число заблокированных и пропущенных опасных действий (цель — ноль пропущенных) |
| Голос | Ваши записи команд | WER, точность интента по цепочке STT → роутер |

Дополнительные метрики живых прогонов: запрошенные подтверждения, отказы политики, ошибки формата,
сработавшие детекторы циклов, доля успешных восстановлений.

- **Отчёты** — таблица по моделям и конфигурациям, сравнение версий; хранятся в `evals/reports`.
- **Допуск модели к роли** — по таблице результатов с порогами (например, валидный JSON ≥ 99 %).
  Пороги фиксируются по результатам первых прогонов, а не заранее.
- **Режим диагностики:** тот же eval с сильной моделью показывает, где провал архитектурный, а где
  модели не хватает способностей (если облачные модели разрешены для разработки — вопрос Q8).

## 4. Воспроизводимость

У «воспроизводимости» два смысла, и оба нужны:

1. **Отладочная** — повторить конкретную задачу шаг за шагом.
2. **Операционная** — превратить удачный прогон в рецепт, который дальше исполняется
   детерминированно ([04-tools-and-skills.md](04-tools-and-skills.md#5-обучение-на-повторяющихся-workflow)).

### Что записывается для каждой задачи

- Запрос, источник, снимок контекста сессии.
- Хэш снимка конфигурации, версия приложения, идентификаторы моделей с хэшами файлов и версией
  рантайма, параметры сэмплирования, seed.
- Идентификаторы и версии шаблонов промптов, отрисованные промпты (в blobs).
- Ответы модели — сырые и разобранные.
- Вызовы инструментов: аргументы, результаты, артефакты, эффекты, время.
- Решения политики и подтверждения.
- Факты окружения: версия ОС, рабочий каталог, HEAD репозитория, наблюдённые состояния контейнеров.

### Режимы воспроизведения

| Режим | Модель | Инструменты | Зачем |
| --- | --- | --- | --- |
| Просмотр | — | — | Разбор, таймлайн в UI |
| Детерминированный replay | Ответы из кассеты | Результаты из кассеты | Регрессии логики ядра без ОС и GPU |
| Полуживой | Ответы из кассеты | Живые, в песочнице | Проверить, что действия по-прежнему работают |
| Живой | Живая модель | Живые, в песочнице | Eval, сравнение моделей |

Кассета адресует вызовы модели по (роль, шаблон промпта, хэш нормализованного промпта), а вызовы
инструментов — по (инструмент, хэш нормализованных аргументов). Если при replay агент запрашивает
то, чего нет в кассете, это **расхождение на шаге N** с диффом — главный сигнал регрессии.

Температура 0 и seed уменьшают разброс, но не гарантируют побитово одинаковых ответов на разном
железе и версиях рантайма. Поэтому replay опирается на кассеты, а оценка качества — на статистику
нескольких прогонов.

## 5. Логирование и трассировка

Одно структурированное хранилище — три представления:

| Представление | Для кого | Что показывает |
| --- | --- | --- |
| Таймлайн задачи | Пользователь | 5–20 строк: шаги человеческим языком, подтверждения, итог проверки |
| Дерево трассы | Разработчик | Span'ы «задача → шаг → вызов модели или инструмента»: время, токены, статус, выжимки; раскрывается по клику |
| Сырые данные | Отладка | Полные промпты, ответы, выводы — артефакты с коротким сроком хранения |

Таймлайн выглядит так:

```
#42 «Почини backend GOFRA» — готово за 3 мин 12 с, 14 шагов, проверено ✓
 1. Контекст: GOFRA (docker compose, 4 сервиса); руководства: bugfix-investigator, container-deployment-reviewer
 2. docker compose ps → backend: Restarting (exit 1)
 3. docker logs backend (300 строк → 3 ошибки) → «could not connect to db:5432»
 4. План обновлён: проверить healthcheck и depends_on у db
 …
 9. ⚠ Подтверждение: изменить compose.yaml (+3 −1) — разрешено вами
 …
 Проверка: backend running 60 с ✓ · GET /health 200 ✓ · новых ERROR в логах нет ✓
```

Принципы:

- **Храним структуру, рендерим представления.** Состояние никогда не восстанавливается разбором логов.
- **Строки таймлайна строятся шаблонами** из структурированных данных (инструмент, аргументы,
  выжимка результата), а не генерируются LLM — это дёшево и не выдумывает.
- **Рассуждения:** пользователю показывается короткое поле `rationale` (1–2 предложения) из
  структурированного ответа модели. Полные «размышления» модели, если она их выдаёт, — только в
  сырых артефактах со сроком хранения.
- **Модель span'ов** совместима с понятиями OpenTelemetry (трасса = задача, span = шаг или вызов);
  для разработки — опциональный экспорт OTLP в локальные инструменты просмотра трасс.
- **Системные логи** (JSON, structlog) отдельно от трасс агента, с корреляцией по `task_id`.
- **Редактирование секретов** применяется ко всем логам и трассам.
- **Метрики:** счётчики задач по маршрутам и статусам, ошибки инструментов, подтверждения,
  гистограммы латентности; команда `jarvis stats`.
