# 08. Milestones Stage 0 и Definition of Done

Реализация идёт строго по одному milestone: следующий начинается, когда DoD предыдущего выполнен.
Граф ниже показывает только зависимости, а не параллельную работу.

```
M1 → M2 → M3 ─┬─► M4 (часть 1)
              └─► M5 → M6 → M7 → M8 ─┬─► M4 (часть 2)
                                      └─► M9 → M10 (необязательно)
```

## Общий DoD для каждого milestone

- ruff, pyright (strict для `domain`, `ports`, `core`), import-linter и архитектурные тесты — без нарушений.
- Новый код покрыт тестами нужного уровня; CI зелёный на Windows и Linux.
- Новое поведение проверяется сценариями eval этого milestone
  ([07-evals-and-benchmarks.md §2](07-evals-and-benchmarks.md#2-eval-задачи), колонка «M»).
- Нет кода, нужного только будущим milestone (пункт чек-листа ревью); поля моделей и порты появляются
  вместе с первым потребителем.
- Отклонение от ADR оформлено явно (какой ADR, почему, что меняется); изменения команд отражены в
  `docs/development.md`.
- Работа закоммичена небольшими коммитами и отправлена; рабочее дерево чистое.

## M1 — Core Domain + Task Runtime

**Входит:** каркас репозитория (`pyproject.toml` с uv и Python ≥ 3.12, ruff, pyright, pytest с плагином
anyio, контракты import-linter, AST-тест архитектуры, GitHub Actions для Linux и Windows,
`docs/development.md`); доменные модели задачи, ID, таблица переходов, бюджеты, таксономия ошибок,
события трассы, схема настроек; порты `Clock`, `UnitOfWork`, `TaskRepository`, `TraceRepository`,
`IdAllocator`; `adapters.memory`; `TaskRunner`, протокол `StageHandler`, `BudgetMeter`, `Tracer`,
`TaskService` (`submit`, `run_until_blocked`, `cancel`, `get`, `trace`); загрузчик слоёв конфига
(умолчания → пользовательский файл → параметры запуска); `app/composition.py`; минимальный движок eval
со scripted-стадиями и сценарии `runtime.*`; CLI `jarvis --version`, `jarvis config check`,
`jarvis config show --sources`, `jarvis eval`.

**Не входит:** LLM, MCP, shell, файловые эффекты, SQLite, GUI, голос.

**DoD:**

- На Linux и Windows (CI) работает последовательность из `docs/development.md`: `uv sync` →
  `uv run pytest` → `uv run jarvis --version`.
- `jarvis.domain`, `jarvis.ports`, `jarvis.core` импортируются без llama.cpp, MCP SDK, sqlite3, httpx,
  psutil, Windows API, Ollama, Docker, Tauri и голосовых библиотек (тест в отдельном процессе проверяет
  `sys.modules`); AST-тест ловит запрещённый импорт, чтение окружения и файловый ввод-вывод — это
  проверено на образцах нарушений.
- Табличный тест по всем парам статусов: разрешённые переходы проходят, остальные дают
  `InvalidTransition`; из терминальных состояний переходов нет.
- Со scripted-стадиями задача проходит пути: agent (CREATED → ROUTING → PLANNING → EXECUTING → VERIFYING
  → COMPLETED), direct, clarify, перепланирование из EXECUTING и из VERIFYING, ожидание подтверждения
  (`run_until_blocked` возвращается в WAITING_CONFIRMATION), FAILED, CANCELLED, BUDGET_EXCEEDED.
- Стадия, вернувшая недопустимый переход, приводит задачу в FAILED с категорией `invalid_transition`;
  неизвестное исключение — в FAILED с категорией `internal`.
- Каждый лимит бюджета приводит к BUDGET_EXCEEDED с событием `budget.exceeded`; лимит времени
  проверяется перед тактом и прерывает долгий такт.
- Отмена: до запуска, во время такта (такт прерывается) и в WAITING_CONFIRMATION — задача в CANCELLED;
  отмена завершённой задачи ничего не меняет.
- Контрольная точка атомарна: сбой при записи не оставляет ни нового состояния задачи, ни его события
  `task.transition`; журнальные события остаются; ID после сбоя не повторяются.
- ID уникальны и имеют формат `task_<n>` / `task_<n>.<вид>_<k>`; события задачи упорядочены по `seq`.
- Детерминизм: два прогона одного сценария с управляемыми часами дают одинаковые события и итог.
- Задача, сохранённая в хранилище, восстанавливается без потерь (JSON туда и обратно), а новый
  `TaskService` над тем же хранилищем продолжает её с последней контрольной точки.
- Конфиг: пустой конфиг валиден; пользовательский файл сливается глубоко; параметры запуска сильнее;
  неизвестный ключ — `ConfigError` с путём ключа; `config show --sources` показывает слой каждого значения.
- `jarvis eval` проходит все сценарии `runtime.*` в CI и пишет отчёт.

## M2 — SQLite, аренды, восстановление, трасса в CLI

**Входит:** `adapters.sqlite` (Unit of Work, репозитории задач и трассы, `IdAllocator`, миграции);
аренды задач в единице работы и их правила в ядре ([ADR 0021](../adr/0021-task-leases-and-optimistic-unit-of-work.md)); восстановление при старте (активная задача с истёкшей арендой →
FAILED `interrupted`); `TaskService.cancel` с проверкой аренды (`TaskBusy`); метрики задачи из событий;
человекочитаемый рендер трассы; CLI `jarvis tasks`, `jarvis trace [--raw]`, `jarvis cancel`.

**DoD:**

- Один набор контрактных тестов хранилища проходят `adapters.memory` и `adapters.sqlite`.
- Сбой между записью строки задачи и события `task.transition` в SQLite не оставляет ни того, ни другого.
- Приложение, пересозданное из БД, видит задачу в том же состоянии и продолжает её.
- Два владельца не ведут одну задачу одновременно; задача с истёкшей арендой при старте становится
  FAILED (`interrupted`); `jarvis cancel` из другого процесса отменяет задачу без живой аренды и
  отвечает `TaskBusy` для чужой живой.
- Миграции проходят на пустой и на фикстурной базе; перед применением делается копия.
- `jarvis trace` рендерит таймлайн; снапшот-тесты рендера.

## M3 — Model Gateway

**Входит:** порт `ModelBackend`; адаптер `llm_openai` (httpx, потоковый режим для времени до первого
токена, structured output по профилю, тайминги сервера); `scripted` и `recorded` бэкенды; `ModelGateway`
(роли, требования ролей, матрица возможностей, профили, конвейер structured output с ремонтом,
семантическая валидация, подсчёт токенов, учёт в `BudgetMeter`, запись `model_calls` с хэшем
нормализованного промпта); секции промпта с тремя уровнями доверия и отрисовка DATA-блоков;
`jarvis model check`; раздел «Настройка модели» в `docs/development.md`; сценарии `model.invalid_output`
и `budget.wall_time`.

**DoD:**

- Контрактные тесты `ModelBackend` проходят для scripted и для `llm_openai` на записанных ответах
  llama.cpp server и LM Studio (httpx MockTransport).
- В `core` нет модельно-специфичных настроек (архитектурный тест: ни температуры, ни стоп-токенов, ни имён моделей).
- Невалидный ответ ремонтируется; после исчерпания попыток — `InvalidModelOutput`; каждая попытка записана
  и учтена в бюджете.
- Модель, не удовлетворяющая требованиям роли, — `ConfigError` с объяснением.
- Property-тест: содержимое данных не может закрыть DATA-блок или открыть новый.
- `jarvis model check` проходит на ПК пользователя с локальным `llama-server` по инструкции из
  `docs/development.md`.

## M4 — Аппаратный бенчмарк

**Входит:** `jarvis bench hardware`, `benchmarks/hardware/candidates.toml`, отчёт
([07-evals-and-benchmarks.md §4](07-evals-and-benchmarks.md#4-аппаратный-бенчмарк)). Часть 1 — после M3,
часть 2 — после M8.

**DoD:**

- Часть 1: отчёт по трём классам моделей (загрузка, VRAM, RAM, скорость, время до первого токена,
  надёжность structured output) воспроизводится одной командой; предварительный выбор модели.
- Часть 2: отчёт дополнен успехом агентных задач и точностью L2-роутера; основная модель выбрана по
  правилу из §4 и зафиксирована ADR с цифрами.

## M5 — Tool Runtime, политика, подтверждения, dry run, реестр проектов

**Входит:** контракт инструмента и явный реестр; конвейер `ToolRuntime` с `ToolInvoker`; `PolicyEngine`
(зоны, уровни, модификаторы); порты `AuditLog`, `ArtifactStore`, `FileSystem`, `ProcessRunner`,
`KnownFolders`, `ProjectStore`; жизненный цикл `ApprovalRequest`, `TaskService.pending_approval` и
`resolve_approval`; CLI-карточка подтверждения, `jarvis approvals | approve | deny | resume`; артефакты
(маскирование секретов, метка недоверенного содержимого); журнал эффектов; корзина Jarvis с манифестом;
dry run; таймауты и отмена с убийством дерева процессов; `ExecutionTarget`, `TargetPath`, `convert_path`;
адаптеры `local_fs`, `local_process`, `known_folders`, `project_files`; `core.projects`, проектный слой
конфига, `jarvis projects list | validate`; инструменты `fs.*`, `process.list`, `project.list`,
`project.get`, `artifact.read`, `logs.extract_errors`; сценарии `policy.*`, `resume.waiting`,
`cancel.long_tool` со scripted-действиями. Адаптер WSL — только если ответ на Q2 «проекты в WSL».

**DoD:**

- Property-тесты политики: модификаторы никогда не снижают риск; CRITICAL — всегда отказ; запись в зону
  `system` — всегда отказ; заражённая задача никогда не получает ALLOW для вызова с эффектами.
- Каждый инструмент проходит контрактные тесты на реальной ФС во временной папке, в том числе на Windows
  CI; удаление попадает в корзину с манифестом; запись идемпотентна.
- Dry run: снимок дерева файлов до и после совпадает побайтно; в трассе — `simulated`.
- Одобренный вызов исполняется ровно один раз; несовпадение `arguments_hash` отклоняется; истёкший запрос
  считается отказом; задача продолжается после пересоздания приложения.
- Если между подтверждением и исполнением изменился набор затронутых файлов, запрашивается новое подтверждение (тест).
- Таймаут и отмена убивают дерево процессов (тест запускает процесс с дочерним процессом).
- Таблица преобразований путей Windows ↔ WSL покрыта тестами.
- Реестр: ошибка в одной записи не ломает остальные; проектный слой принимает только разрешённые ключи.

## M6 — Shell как escape hatch

**Входит:** порт `ShellParser`; адаптер `shell_pwsh` (долгоживущий `pwsh`, встроенный парсер, ответ в JSON);
`shell_posix` (консервативный разбор); раскрытие алиасов; каталог команд с примерами-тестами;
инструмент `shell.execute` с классом эффектов вызова из класса команды; режимы доступа модели;
сценарии `shell.*`.

**DoD:**

- Корпус из 150+ команд PowerShell и POSIX (алиасы, `-EncodedCommand`, `iex`, конвейеры, перенаправления,
  динамические вызовы) классифицируется ожидаемо на 100 %.
- Dry run и заражённая задача никогда не исполняют команду классов `mutating_known`, `destructive`,
  `unknown`, `unparseable` (тест).
- Примеры каталога проверяются при загрузке; противоречивая запись не загружается.
- Если `pwsh` недоступен, `shell.execute` отключается с понятным сообщением — небезопасного запасного пути нет.
- Тесты проходят на Windows CI и на Linux CI с установленным `pwsh`.

## M7 — Intake, Router, direct-маршрут

**Входит:** токенизатор, нормализация (pymorphy3), транслитерация, `EntityIndex` (известные папки,
проекты, типы файлов, латинские названия), грамматика L0 для интентов `fs.show_cwd`, `fs.list_dir`,
`fs.find_by_extension`, `project.show`; LLM-роутер со схемой `RouteDecision`; clarify; обработчик
direct-маршрута и минимальная стадия VERIFYING для него (постусловие инструмента); `jarvis run` для
direct-команд; набор фраз роутера; сценарии `direct.*`, `clarify.ambiguous`.

**DoD:**

- Набор фраз роутера (60+): подмножество L0 — 100 %; точность L2 измерена и записана в отчёт.
- `direct.cwd`, `direct.find_pdf`, `direct.find_in_project` проходят в scripted и live режимах без вызова
  модели для L0.
- На ПК пользователя p50 «запрос → действие» для L0 меньше 300 мс.

## M8 — Planner / Executor / Verifier

**Входит:** `ContextBuilder` (секции, бюджеты, стабильный префикс), промпты v1, профили `workspace` и
`dev`, Planner (схема и семантическая проверка плана), Executor (`ProposedAction`), библиотека проверок
(`file.exists`, `file.contains`, `dir.exists`, `path.absent`, `evidence.present`), детерминированный
Verifier, перепланирование, детектор зацикливания, маршрут chat, `SkillResolver` с `NullSkillProvider`
и `StaticSkillProvider`, инструменты `docker.*` только для чтения и фикстуры `fake_process`; все
сценарии eval, кроме replay.

**DoD:**

- Все сценарии из [07-evals-and-benchmarks.md §2](07-evals-and-benchmarks.md#2-eval-задачи), кроме
  `replay.simulated`, проходят в scripted-режиме в CI.
- Live-прогон на ПК пользователя даёт отчёт: доля успехов по сценариям и категориям, метрики.
- Сценарии с инъекциями: ноль неодобренных эффектов во всех live-прогонах.
- Сценарии бюджета и зацикливания всегда завершаются в пределах лимитов.

## M9 — Replay и golden traces

**Входит:** `jarvis replay --mode simulated|live`, записанный `ToolInvoker` в `app/replay.py`, отчёт о
расхождениях, golden-файлы свойств, `jarvis eval --check-golden`.

**DoD:**

- Simulated replay записанных live-прогонов ключевых сценариев — без расхождений.
- Тест с намеренно изменённой политикой — расхождение обнаружено и показано.
- Live replay никогда не исполняет HIGH и CRITICAL (тест).

## M10 — Адаптер AI-Dev-System (необязательно в Stage 0)

**Входит:** `adapters.ai_dev_mcp`: MCP по stdio, allowlist вызовов, таймауты, закреплённая версия,
проверка возможностей; `recommend_skills` → `SkillSummary`, `read_skill_card` / `read_skill` → `Skill`,
`compile_project_context` → `ProjectContextPack`; контрактные тесты против закреплённой версии AI-Dev-System
(Node в CI).

**DoD:**

- Один и тот же набор контрактных тестов `SkillProvider` проходят Null, Static и AI-Dev.
- Сервер выключен — результаты eval такие же, как с `NullSkillProvider`.
- Сервер включён — навыки попадают в промпт только как недоверенные секции; инструменты AI-Dev-System
  модели не показываются.

## Критерии завершения Stage 0

1. Выполнен DoD M1–M9 (M10 — по возможности).
2. Есть live-отчёт на RX 7600 с выбранной моделью: успех по категориям, задержки, токены; ноль
   неодобренных эффектов в сценариях безопасности.
3. Сформулирован ответ на главный вопрос Stage 0 с цифрами и рекомендация для Stage 1 (модель, бюджеты,
   промпты, что упростить).
4. `docs/development.md` проверен на чистой машине с Windows 11.
