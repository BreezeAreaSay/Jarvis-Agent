# ADR 0003. SQLite: один файл, WAL, синхронный sqlite3, Unit of Work

- **Статус:** Предложено
- **Дата:** 2026-10-01

## Контекст

В архитектуре предлагались три файла SQLite (core, traces, audit). Stage 0 требует, чтобы переход состояния
и событие трассы записывались атомарно. Пользователь один, процесс один (плюс иногда второй CLI для отмены
или подтверждения).

## Решение

- Один файл `jarvis.db` в режиме WAL; стандартный `sqlite3`, синхронно, за портом `UnitOfWork`.
- Пронумерованные SQL-миграции с резервной копией перед применением.
- Оптимистическая блокировка задачи (`tasks.version`).
- Большие данные — в blobs по sha256 (gzip); в БД — ссылки.
- Реестр проектов остаётся YAML-файлами пользователя.

## Альтернативы

- Три файла — нет атомарности между файлами.
- ORM (SQLAlchemy) — лишний слой для десятка таблиц.
- aiosqlite — асинхронность без необходимости.
- Postgres — администрирование ради одного пользователя.

## Последствия

- Простая и атомарная запись.
- При росте объёма трасс их можно вынести в отдельный файл со своей политикой хранения.
- Синхронные вызовы занимают миллисекунды и не мешают CLI.
