# ADR 0023. Model Gateway v1 и первый агент на модели

- **Статус:** Принято
- **Дата:** 2026-10-03
- **Уточняет:** [ADR 0008](0008-model-gateway.md), [ADR 0009](0009-structured-model-output.md),
  [ADR 0015](0015-trace-without-chain-of-thought.md); **отступает от** эскизов Model Gateway и
  конфигурации моделей в [03-contracts.md §3](../stage0/03-contracts.md#3-model-gateway),
  [02-domain.md §2](../stage0/02-domain.md#проекты-навыки-модели) и
  [06-errors-and-config.md §2](../stage0/06-errors-and-config.md#2-конфигурация); откладывает признак
  `tainted` из [ADR 0006](0006-untrusted-content-is-data.md)

## Контекст

Session 4 подключает первую локальную модель и впервые даёт ей вести задачу:

```
запрос → модель → проверенное решение (JSON) → ToolCall → Tool Runtime → политика → исполнение
       → проверка → наблюдение для модели → … → ответ модели → детерминированная проверка ответа
```

Модель не получает никаких системных возможностей: её единственный выход — JSON, который ядро
проверяет и передаёт в Tool Runtime (ADR 0004, ADR 0022). Эскиз Stage 0 рассчитан на четыре роли,
планировщик, роутер и бенчмарк; у большей части его полей пока нет потребителя, а часть при
реализации оказалась лишней или неточной.

## Решение

**Роли.** Есть одна роль — `executor`: выбирает следующее действие и формулирует ответ (ответ — это
действие `finish`, поэтому `responder` не нужен). `router` (M7) и `planner` (M8) появятся со своими
стадиями. Требования ролей объявлены в ядре (`ROLE_REQUIREMENTS`): executor — окно контекста не
меньше 8192 токенов и 1024 токена на ответ. Длина ответа — свойство роли, а не модели: ядро
резервирует её в окне и передаёт как `max_tokens`. Модель, не подходящая роли, — `ConfigError` при
сборке приложения.

**Возможности** (`ModelCapabilities`) — только те, по которым ядро сейчас решает:
`structured_output` (сервер ограничивает ответ JSON Schema — грамматикой) и `context_window`.
`structured_output` объединяет `structured_output` и `constrained_decoding` эскиза: умение «отвечать
JSON» есть у любой инструктивной модели, а решение ядра зависит только от того, применяет ли схему
сервер. Если применяет — схема уходит в запрос, иначе описывается в промпте; ремонт работает в обоих
случаях. `native_tools`, `vision`, `embeddings`, `max_output_tokens` появятся с потребителем.
Возможности объявляются в конфиге и сверяются с сервером командой `jarvis model check`.

**Model Gateway** (`core.models.gateway`) — конкретный класс с одним методом генерации
`generate(role, prompt, StructuredOutput) → Generation`: отрисовать промпт → бюджет (вызов, остаток
токенов) → бэкенд → JSON → модель pydantic → семантическая проверка вызывающего → ошибка: повтор с
объяснением и укороченным непринятым ответом (не больше `models.repair_attempts`) → `InvalidModelOutput`.
Обрезанный по лимиту ответ называется в объяснении. `ModelUnavailable` повторяется один раз через
секунду, остальные ошибки модели не повторяются. Каждая попытка, включая сбой связи и отмену, —
запись `model_calls` (промпт, ответ, токены, тайминги, хеш промпта без ID задачи) и событие
`model.called` (без текста) одной транзакцией. `generate_text`, `count_tokens` и `context_budget` из
эскиза не нужны: ответ всегда структурирован, токены оцениваются сверху (`байты UTF-8 / 3`), окно для
промпта — `prompt_budget(role)`.

**Порт `ModelBackend`**: `info` (эндпоинт, имя модели — только для журналов, возможности),
`complete(BackendRequest) → BackendResponse`, `describe() → BackendStatus` (модели, окно контекста,
сборка сервера — для `jarvis model check`; заменяет `health`). Запрос — отрисованные сообщения,
JSON Schema или None, `max_tokens`. Сэмплирование, имя модели, формат `response_format` и
особенности сервера добавляет адаптер.

**Один провайдер — OpenAI-совместимый, проверен на llama.cpp `llama-server`**
(`adapters.models.OpenAICompatibleBackend`, httpx): `POST /v1/chat/completions`, structured output —
`response_format: {type: json_schema, …}`, блок `<think>` отбрасывается, тайминги и окно контекста
llama.cpp (`timings`, `/props`, `meta.n_ctx` в `/v1/models`) читаются, когда есть. Ошибки HTTP и
связи — `ModelUnavailable` (нет соединения, 5xx), `ModelTimeout`, `ModelRequestRejected` (4xx, ответ
не по протоколу). Причин менять выбор рантайма реализация не нашла: llama-server собран из исходников
(коммит `b92761a`, CPU), адаптер и `jarvis model check` проверены на нём; записанные ответы — фикстуры
контрактных тестов. Запросы не потоковые: время до первого токена и скорость — забота бенчмарка (M4).

**Только этот компьютер.** `base_url` эндпоинта — только loopback (`localhost`, `127.0.0.0/8`,
`[::1]`): промпт содержит файлы пользователя, в том числе прочитанные с его разрешения. httpx создаётся
с `trust_env=False` (ни прокси, ни сертификатов из окружения — и правило «окружение читает только
`jarvis.config`» соблюдено) и без следования перенаправлениям.

**Конфигурация** — раздел `models` одной схемы (ADR 0018): `endpoints.<id>` (таблица по ID, а не
список `[[models.endpoints]]` — так работает послойное слияние и `config show --sources`) с `base_url`,
`model`, `request_timeout_s`, `capabilities`, `sampling` (temperature, top_p, seed, stop) и
`extra_body`; `roles` (роль → эндпоинт); `repair_attempts`. Профиль модели не отделён от эндпоинта и
сэмплирование не разбито по ролям: роль одна. Модели не назначены — пустой конфиг валиден, а
`jarvis run` объясняет, что настроить.

**Агент** (`core.agent`). ROUTING и PLANNING пока переходят дальше без модели (маршрут `agent`;
причина в трассе — «маршрутизатора/планировщика ещё нет»). Такт EXECUTING: один шаг бюджета → промпт
`executor.v1` → решение `ProposedAction{decision ≤ 280, action: tool | finish}`. Действий `step_done`
и `replan` нет, пока нет плана. Схема решения строится из реестра: у каждого инструмента своя ветвь с
`const` ID и его схемой аргументов, `evidence` в `finish` — только из исполненных вызовов задачи;
семантическая проверка повторяет это после разбора, а Tool Runtime всё равно проверяет аргументы.
Вызов — `ToolRuntime.call`; ожидание человека — переход в WAITING_CONFIRMATION, после решения такт
доводит вызов `ToolRuntime.resume` без нового вопроса модели. Итог вызова — наблюдение в рабочей
памяти: `summary` пишет Jarvis, а вывод инструмента, текст ошибки и причина отказа (в ней пути из
аргументов) — `data`, которое модель видит только блоком DATA. Отказ, сбой инструмента и ответ,
не прошедший ремонт, засчитываются в `failures` (диспозиция FEEDBACK); `ModelError` и `ConfigError`
завершают задачу. VERIFYING без модели: ответ может ссылаться только на исполненные и проверенные
вызовы этой задачи, иначе `VerificationFailed` → FAILED (перепланирования пока нет).

**Рабочая память в задаче.** `Task.state: AgentState` (шаги: решение, ID вызова, наблюдение или
отвергнутый ответ) сохраняется runner'ом вместе с контрольной точкой (`tasks.state_json`, миграция
003): задачу после подтверждения может продолжить другой процесс. Вывод инструмента в памяти — до
6000 байт; если промпт не помещается в окно, данные старых вызовов заменяются пометкой «опущено».

**Промпт.** Секции с доверием: правила — системное сообщение (правило про инструменты выводится из
объявленных эффектов); запрос и описания инструментов — `trusted`; решения модели — `derived` с
пометкой «текст модели»; данные — блок `<<<DATA id=… source=… trust=untrusted>>> … <<<END DATA id=…>>>`.
Во всех секциях, кроме системной, любые `<<` и `>>` разбиваются невидимым разделителем, поэтому
данные не могут ни закрыть блок, ни открыть новый (property-тест).

**Заражённость задачи отложена.** ADR 0006 требует подтверждения для любого вызова с побочным эффектом
в задаче, где модель видела недоверенные данные. В Policy v1 ни один побочный эффект не разрешается
без человека (запрет или подтверждение), и это закреплено property-тестом — поэтому признак `tainted`
сейчас ничего бы не изменил. Первое правило политики, разрешающее побочный эффект без человека,
обязано прийти вместе с `tainted`.

## Альтернативы

- Нативный tool calling (`tools` в запросе) — формат зависит от шаблона чата модели; JSON Schema с
  ветвью на инструмент даёт ту же строгость через грамматику на любом сервере llama.cpp (ADR 0009).
- Ollama или LM Studio первым рантаймом — тот же OpenAI-совместимый адаптер должен работать и с ними,
  но проверен только llama-server; поддерживать несколько рантаймов сразу не стали.
- Поток (stream) для времени до первого токена — нужен бенчмарку, а не агенту; отложен до M4.
- Хранить историю агента в памяти процесса — задача, ждущая человека, не пережила бы перезапуск.
- Разрешить удалённый `base_url` — утечка файлов пользователя; появится вместе с явной настройкой,
  если понадобится.

## Последствия

- Смена модели — изменение конфига, `jarvis model check` и прогон eval; ядро не меняется
  (архитектурный тест запрещает в `core` и `ports` имена моделей и рантаймов, параметры сэмплирования
  и детали API).
- Промпты и ответы модели лежат в `model_calls` (в данных Jarvis, недоступных инструментам), в том
  числе прочитанное с разрешения пользователя; трасса текста не содержит. Отключение записи
  промптов (`trace.keep_prompts`) — когда появится настройка трассы.
- Выбор основной модели — по-прежнему после бенчмарка M4 (ADR о модели).
