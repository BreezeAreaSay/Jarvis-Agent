# ADR 0022. Tool Runtime v1: эффекты вызова, политика по зонам, подтверждение по отпечатку preview

- **Статус:** Принято
- **Дата:** 2026-10-01
- **Уточняет:** [ADR 0004](0004-tool-runtime-security-boundary.md),
  [ADR 0011](0011-human-approval-as-task-state.md), [ADR 0017](0017-windows-first-execution-target.md);
  **отступает от** [ADR 0016](0016-dry-run-and-replay.md) (dry run) и эскиза Tool contract в
  [03-contracts.md §2](../stage0/03-contracts.md#2-tool-contract)

## Контекст

Session 3 реализует первую настоящую границу исполнения: только инструменты чтения на HOST, без модели.
Эскиз Stage 0 рассчитан на полный набор (уровни риска, заражённость задачи, `simulate`, профили модели).
Часть его полей сейчас некому потреблять, а часть при реализации оказалась неверной:

- `normalize` «без ввода-вывода» не может раскрыть символическую ссылку, а политика должна судить о
  настоящей цели (ссылка из рабочей папки в данные Jarvis — это данные Jarvis);
- класс эффектов инструмента (`SideEffects`: NONE / LOCAL_REVERSIBLE / …) не говорит, *какой ресурс*
  затронут, а решение по зонам нужно принимать по ресурсу;
- подтверждение по `arguments_hash` не ловит подмену: аргументы те же, а файл по пути уже другой;
- требование Session 3 к dry run строже ADR 0016: `execute()` не вызывается вовсе.

## Решение

**Контракт инструмента** (`jarvis.ports.tools.Tool`): `definition` (`ToolDefinition`: id, описание,
`input_model` / `output_model` → JSON Schema, возможные виды эффектов, цели, таймаут,
`untrusted_output`), `preview`, `execute`, `verify`. Статического уровня риска нет. Нормализация
аргументов — часть `preview` (канонические пути с раскрытыми ссылками); исполняются нормализованные
аргументы, которые видели политика и человек. Полей `version`, `idempotent`, `exposure` и метода
`simulate` нет, пока нет их потребителей (повторы, профили модели, симуляция эффектов).

**Эффекты — свойство вызова.** `preview` возвращает список `ToolEffect(kind, resource)`; `kind` —
READ, WRITE, CREATE, DELETE, PROCESS_CONTROL, NETWORK, SYSTEM_CHANGE; READ — единственный вид без
побочного эффекта. Эффект вне объявленных в определении — `ToolPreviewFailed`, вызов не исполняется.

**Tool Runtime** — единственный, кто исполняет инструменты, пишет их трассу и аудит:
реестр → цель → схема аргументов → preview → решение политики (трасса и аудит **до** исполнения) →
отказ / запрос подтверждения / dry run → бюджет → для вызова с побочными эффектами повторный preview и
сверка отпечатка (TOCTOU) → `execute` с таймаутом и отменой → схема результата → `verify` → трасса и
аудит → `ToolOutcome`. Ожидаемые исходы (EXECUTED, DENIED, NEEDS_APPROVAL, DRY_RUN) — значения;
сбои — исключения `ToolError` (InvalidToolArguments, ToolPreviewFailed, ToolTimeout, …).
Инструменты лежат в `jarvis.adapters.tools`, а не в `core/tools/builtin`, как в эскизе 01: они делают
ввод-вывод, а ядру он запрещён. Создаёт их только composition root, держит только реестр, который
видит только runtime; стадии получают runtime.

**Policy Engine v1** — чистая функция `(ToolCall, ToolPreview, зоны) → ALLOW | DENY | REQUIRE_APPROVAL`
с перечнем сработавших правил; самое строгое правило среди эффектов вызова побеждает. Зоны — канонические
пути: данные Jarvis (`internal`: ни чтения, ни записи), секреты (папки `~/.ssh`, `~/.gnupg`, … и шаблоны
имён `*.pem`, `id_rsa*`, `.env`, …: чтение — подтверждение, запись — запрет), рабочие папки из
`policy.workspace_roots` (запись — подтверждение; вне их — запрет). DELETE, PROCESS_CONTROL, NETWORK,
SYSTEM_CHANGE — запрет. Не-HOST цель — запрет. Уровни риска SAFE…CRITICAL, заражённость задачи и
модификаторы из 04 §2 откладываются до инструментов с эффектами и модели.

**Подтверждение** привязано к вызову и к **отпечатку preview** (нормализованные аргументы, эффекты с
ресурсами, цель). Статусы: PENDING → APPROVED / DENIED (человек) или EXPIRED (срок) → USED (решение
применено); WITHDRAWN — задача завершилась раньше, чем решение применили. Каждая смена статуса —
сравнение-и-запись: решение применяется ровно один раз, решение и отмена задачи не проходят обе.
`TaskService.resolve_approval` только записывает решение (и аудит); продолжает задачу
`run_until_blocked`: переход WAITING_CONFIRMATION → EXECUTING берёт аренду, стадия доводит тот же
вызов. Одобренный вызов перед исполнением проходит preview снова: другой отпечаток — новый запрос.
Отказ и истёкший срок — отказ-значение, построенный из того, что видел человек, без нового preview.
Стадия не может перевести задачу в WAITING_CONFIRMATION без ждущего запроса (`InvalidTransition`).
Решения v1 — `approve` и `deny`; «отказать и остановить» — это `cancel`.

**Dry run** проходит preview и политику (решения пишутся в трассу и аудит с пометкой `dry_run`), но
`execute` не вызывает ни для одного вызова, включая чтение; запросов подтверждения не создаёт
(`would_execute=false` показывает, что понадобился бы человек).

**Владение задачей.** Runtime не верит объекту задачи от стадии: в начале вызова и в тех же
транзакциях, что пишут решение и `tool.started`, задача в хранилище должна быть той же версии,
активной и под живой арендой этого процесса — иначе `LeaseLost`, ничего не исполняется. Режим dry run и
рабочая папка берутся из хранилища. Итог уже начатого вызова записывается и после потери задачи:
честная запись того, что произошло, важнее порядка событий.

**Формы путей.** Зоны сравниваются по строкам канонических путей, поэтому на Windows пути вида
`\\?\…`, `\\.\…`, UNC (в том числе `\\localhost\C$`) и потоки NTFS (`файл::$DATA`) инструменты не
принимают, а политика запрещает (`path.unsupported_form`) — как и любой путь, который не абсолютный.

**Цели исполнения:** HOST, WSL, DOCKER, SSH (имя DOCKER — по ADR 0017); исполняется только HOST,
остальные — `UnsupportedTarget` в runtime и `target.unsupported` в политике. Фейковых адаптеров нет.

**Аудит** отделён от трассы: решение, итог исполнения, решение по подтверждению. Аргументы — только
хешем нормализованных аргументов, ресурсы — первые пять, укороченные. В трассе у результата всегда размер
и sha256, а сам он — только если не больше 2 КБ и прочитан не из зоны секретов; вся выдача возвращается
стадии и помечена недоверенной.

## Альтернативы

- Уровни риска SAFE…CRITICAL сразу — без инструментов с эффектами их нечем проверить; зоны и виды
  эффектов дают ту же защиту для чтения и закладывают место для записи.
- Подтверждение по хешу аргументов — пропускает подмену файла по тому же пути.
- Dry run с настоящим чтением (ADR 0016) — противоречит требованию Session 3; вернуть его — отдельное
  решение, когда появится `simulate`.
- Инструменты в ядре — нарушают правило «ядро без ввода-вывода» и AST-проверку архитектуры.

## Последствия

- Каждое новое действие — новый инструмент с preview, объявленными эффектами и `verify`; запись и
  удаление потребуют правил зон для WRITE/DELETE и, вероятно, уровней риска.
- Подтверждение через CLI (`jarvis approvals`, `approve`, `deny`, `resume`) ещё не сделано: есть API
  сервиса, eval отвечает через него же (`via="eval-auto"`).
- Между проверкой «путь не изменился» и открытием у list/stat/search остаётся узкое окно (метаданные);
  у `read_text` его закрывает проверка открытого дескриптора.
