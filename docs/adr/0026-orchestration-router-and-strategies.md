# ADR 0026. Router ядра решает стратегию исполнения: DIRECT, RECIPE, AGENT, DELEGATE, CLARIFY

- **Статус:** Предложено (Architecture V2)
- **Дата:** 2026-10-04
- **Уточняет:** [ADR 0007](0007-skills-vs-recipes.md) (рецепты — раньше), [ADR 0008](0008-model-gateway.md)
  (роли модели), [ADR 0009](0009-structured-model-output.md) (действия исполнителя),
  [ADR 0023](0023-model-gateway-v1.md) (ROUTING и PLANNING без модели); **заменяет** план LLM-роутера и
  цикла Planner/Executor/Verifier в [03-agent-core.md §3, §6](../architecture/03-agent-core.md) и
  M7–M8 в [08-milestones.md](../stage0/08-milestones.md)

## Контекст

Сейчас любой запрос ведёт агент на локальной модели: стадия ROUTING — заглушка (маршрут всегда
`agent`), PLANNING — проходная. План Stage 0 предполагал L2-роутер на основной LLM и цикл с живым планом
от LLM-планировщика. Бенчмарк (ADR 0025) показал, что 8B надёжна в коротком и ненадёжна в длинном
(55,3 % успеха на 47 задачах), а облако и внешние агенты становятся нормальной частью Jarvis. Нужно
явно решить, **кто** выбирает способ исполнения, — иначе система скатывается в «пользователь → LLM →
LLM решает всё».

## Решение

**Router — детерминированная стадия ROUTING ядра** (`core/routing`). По запросу, режиму пользователя,
инвентарю сущностей, каталогу рецептов, состоянию провайдеров и политике приватности он выбирает
стратегию и уровень и записывает `RouteDecision` (стратегия, уровень, режим, интент / рецепт /
специалист, классы данных запроса, ID сработавших правил) в задачу (`tasks.routing_json`) и в трассу
(`route.decided`). Вызова модели Router по умолчанию не делает (бюджет `routing` без вызовов модели).

**Стратегии** (`Route`, уже существующий маршрут задачи):

| Стратегия | Исполнитель | Модель |
| --- | --- | --- |
| `DIRECT` | прямой обработчик: интент L0 → вызов(ы) инструмента → шаблон ответа | нет (бюджет `direct` = 0 вызовов модели) |
| `RECIPE` | Recipe Engine: детерминированный workflow через Tool Runtime | нет или точечно |
| `AGENT` | агентный цикл: Model Gateway ⇄ Tool Runtime, проверка ответа | уровня `fast` / `local` / `smart` / `coding` |
| `DELEGATE` | передача задачи внешнему агенту через Tool Runtime (ADR 0029) | своя у агента |
| `CLARIFY` | уточняющий вопрос по шаблону | нет |

`CHAT` сливается с `AGENT` без инструментов; `RECIPE` и `DELEGATE` добавляются вместе с исполнителями.

**Порядок решения:** режим и подсказки (только ужесточение: «офлайн» → `local_only`) → L0 (грамматика
команд, Entity Resolver, триггеры рецептов; порог уверенности по риску) → признаки задачи (расширяемые
правила с ID: операция над кодом, вставленный код, анализ, масштаб, объём; слова языков
программирования признаком не являются) → таблица «класс × режим × доступность × приватность».
Неоднозначный запрос идёт в `AGENT(local)` без отдельного вызова классификации.

**Модель внутри стратегии `AGENT`** выбирает только следующее действие по схеме из реестра видимых ей
инструментов. Позже она может *попросить* эскалацию (`escalate`): решение снова принимает Router по тем
же правилам. Модель не выбирает стратегию, провайдера и не решает, что уходит в облако.

**LLM-планировщика нет.** Длинные и повторяемые процессы — рецепты (ADR 0007: рецепт — детерминированный
workflow; навык — знание для модели). Состояния `PLANNING` и `REPLANNING` остаются в машине состояний
проходными/спящими: удалять их — миграция таблицы переходов без выгоды.

**Бюджет агента по уровню:** `fast` и `local` — короткий (архитектура B), значение — по распределению
шагов в успешных задачах бенчмарка; `smart`/`coding` — свой.

## Альтернативы

- **LLM-роутер на каждый запрос** (план Stage 0) — лишний вызов 8B до работы; решение о приватности и
  провайдере нельзя доверять модели.
- **Отдельные слои Intent Router → Task Classifier → Execution Strategy** — одно решение в трёх местах.
- **LOCAL_AGENT и REMOTE_AGENT как разные стратегии** — одинаковый цикл; fallback облако → локальная
  внутри задачи потребовал бы перезапуска.
- **Отдельная быстрая модель-классификатор** — на 8 GB не помещается рядом с 8B (ADR 0027).

## Последствия

- Частые команды исполняются без модели; всё нераспознанное — агентом, как сейчас: поведение
  ухудшиться не может.
- Нужны: грамматика L0 и набор фраз роутера в eval (точность L0 — 100 % на его подмножестве), порт
  инвентаря, прямые обработчики, `jarvis route` для объяснения решения.
- Router — единственное место решения: тестируется таблицей случаев без модели.
- M7 (Intake, Router, direct) и M8 (Planner/Executor/Verifier) Stage 0 заменяются планом
  `docs/architecture-v2/04-plan.md`.
