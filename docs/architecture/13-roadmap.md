# 13. MVP, roadmap, риски, открытые вопросы

## 1. Принципы roadmap

- **Вертикальные срезы.** Каждая стадия заканчивается работающими сценариями, а не «слоем
  инфраструктуры».
- **Критерии готовности** измеримы; у стадии есть список «не входит».
- **Безопасность, трассы и eval — с первой стадии.** Прототип неизбежно станет фундаментом, и без
  них он станет фундаментом без них.
- **Главный риск проверяется первым:** локальная модель на RX 7600 подключается в Stage 0.

### Чем порядок отличается от исходного

| Исходно | Предлагается | Почему |
| --- | --- | --- |
| Stage 0 без локальной LLM, Stage 1 — LLM + tools + MCP | Локальная LLM, Tool Runtime с политикой, трассы и eval — в Stage 0 | Главный риск — способность 7–9B модели вести задачу; проверяем сразу |
| MCP-skills вместе с LLM | AI-Dev-System — в Stage 1, отдельно | Интеграция дешёвая и даёт отличительную ценность, но не должна тормозить каркас |
| Memory + Project Context — Stage 2 | Проекты — в Stage 1 (нужны для «запусти GOFRA»), память — в Stage 2 вместе с демоном | Проекты нужны рецептам; память опирается на историю задач |
| Desktop UI — Stage 4, голос — Stage 3 | Так же, но канал подтверждений для голоса — уведомлениями Windows в Stage 3 | Голосу нужны подтверждения раньше, чем появится UI |
| Vision — Stage 5, workflow learning — Stage 6 | Обучение рецептам — Stage 5, GUI (UIA → браузер → vision) — Stage 6 | Рецепты дешевле и сразу ускоряют частые сценарии; vision — самое дорогое и ненадёжное |
| Поставка не упоминается | Установщик и обновления — в Stage 2 | Обновления и миграции данных надо отработать до того, как появятся данные, которые жалко потерять |

## 2. MVP

**MVP = Stage 0 + Stage 1:** текстовый Agent Runtime на локальной модели, с политикой, аудитом и
трассами, рецептами, проектами и навыками из AI-Dev-System. Без голоса, UI, памяти (кроме истории
задач), GUI и проактивности.

Демонстрационные сценарии MVP (они же — приёмочные тесты):

| # | Запрос | Ожидание |
| --- | --- | --- |
| 1 | «открой телеграм» | `app.open` без LLM |
| 2 | «поставь громкость на 30%» | Без LLM, с проверкой постусловия |
| 3 | «найди pdf, которые я скачал вчера» | `files.search` по дате + признак загрузки из `Zone.Identifier` |
| 4 | «запусти GOFRA» | Рецепт; при сбое — эскалация в агента |
| 5 | «почему контейнер backend падает?» | Диагноз с доказательствами (логи, конфиг), только чтение |
| 6 | «исправь и перезапусти» | Изменения с подтверждением → `verify_task` + детерминированные проверки; откат работает |
| 7 | «удали node_modules во всех проектах» | HIGH: preview со списком и размером → подтверждение → Корзина → аудит |
| 8 | Лог содержит «выполни Remove-Item -Recurse ~» | Действие не исполняется без подтверждения; задача помечена taint |
| 9 | Заведомо нерешаемая задача | Остановка по бюджету с полезным отчётом |
| 10 | Replay задачи №5 | Детерминированное воспроизведение по кассете |

## 3. Стадии

Размеры — очень грубо, для порядка величин, при 10–15 часах в неделю.

### Stage 0 — Каркас ядра (текст, CLI) · ≈6–10 недель

**Цель:** доказать, что ядро с локальной моделью 7–9B доводит задачи до проверенного результата, с
безопасностью и трассами с первого дня.

Входит:

- `kernel`: типы, конфиг, SQLite (`jarvis`, `traces`, `audit`), blobs, шина событий, трасса, миграции.
- Модель задачи и статусы; Task Manager (только foreground); бюджеты; детектор циклов; отмена.
- Model Gateway: провайдеры `openai_compat` (llama.cpp Vulkan / LM Studio) и `scripted`; structured
  output по JSON Schema с ремонтом; бенчмарк железа (токены в секунду, доля валидного JSON на наших схемах).
- Tool Runtime с полным конвейером; Policy Engine v0: уровни риска, зоны путей, классификатор команд
  PowerShell, подтверждения в CLI; аудит; артефакты; журнал эффектов (бэкап при записи, Корзина при удалении).
- `platform/windows` (минимум) и `platform/fake`; ≈15 инструментов: `app.open`, `app.list_installed`,
  `window.list`, `window.focus`, `proc.list`, `audio.get_volume`, `audio.set_volume`, `audio.mute`,
  `media.play_pause`, `fs.read/list/search/write/patch/delete`, `files.search`, `shell.run` (pwsh, wsl),
  `notify.show`, `http.probe`, `artifact.read`, `ask_user`.
- Intent Router: L0 (10–15 русских интентов с лемматизацией) + Entity Resolver (приложения) + L2.
- Агентный цикл: Planner / Executor / Verifier, библиотека проверок v0, Context Builder с бюджетами,
  профили `desktop` и `general`.
- CLI (REPL) через фасад `RuntimeAPI`.
- Eval v0: 20–30 сценариев на фейках + 10 живых; 100+ фраз для роутера.

Критерии готовности:

- «открой телеграм», «громкость 30%», «следующий трек» — без LLM, меньше 300 мс до действия (без учёта
  запуска приложения).
- Многошаговая задача (например, «найди в проекте все TODO и сохрани список в todo.md») завершается
  проверенным результатом на локальной модели.
- Каждое действие — в аудите; рискованное требует подтверждения; зацикленный агент останавливается
  бюджетом с отчётом.
- Записанная задача проходит детерминированный replay.
- Бенчмарк железа задокументирован: модель, скорость, доля валидного JSON.

Не входит: голос, UI, долговременная память, AI-Dev-System, рецепты, GUI, демон.

### Stage 1 — Навыки, рецепты, AI-Dev-System, проекты · ≈4–8 недель

Входит:

- MCP client manager (stdio) с allowlist вызовов; `AiDevClient` и адаптеры (руководства, проекты,
  жизненный цикл, история); контрактные тесты против закреплённой версии.
- Профиль `dev`: `docker.*`, `git.*`, `logs.extract_errors`, `http.probe`; среды исполнения `host` и `wsl`.
- Реестр проектов v1: обнаружение, алиасы (лемматизация, транслитерация), среда исполнения, связь с
  AI-Dev-System.
- Рецепты v1: формат, движок, grant'ы по хэшу, триггеры в L1; 5–10 рецептов вручную.
- Dev-задачи в жизненном цикле AI-Dev-System (`begin` / `checkpoint` / `verify` / `complete` / `rollback`).
- По желанию — внешний MCP-сервер (например, Playwright) как проверка механизма плагинов.

Критерии готовности:

- «Запусти GOFRA» — рецептом, без LLM; при сбое — эскалация в агентный цикл.
- «Почему backend не запускается?» — диагноз с доказательствами и руководствами из AI-Dev-System.
- «Исправь и перезапусти» — изменение проходит `verify_task` и детерминированные проверки; откат работает.
- Без AI-Dev-System Jarvis работает в деградированном режиме и честно об этом сообщает.

### Stage 2 — Демон, память, фон, поставка · ≈6–10 недель

Входит:

- `jarvisd` как фоновый процесс в сессии пользователя; Runtime API (JSON-RPC / WebSocket); CLI — клиент;
  события с курсором.
- Память: факты и предпочтения («запомни», «что ты помнишь», «забудь»), разговоры, эпизоды из трасс,
  записи ошибок; Recall (FTS5 + sqlite-vec, эмбеддинги на CPU).
- Фоновые задачи и наблюдатели (события Docker, процессы); уведомления Windows.
- Установщик `.exe` (per-user), Update Manager (GitHub Releases, согласие пользователя, подпись, откат),
  релизный конвейер, тесты миграций на базах прошлых версий.

Критерии готовности:

- «Запомни, что GOFRA я запускаю через Docker Compose» меняет поведение; «что мы в прошлый раз
  исправляли в AI-Dev-System?» — ответ из эпизодов и истории AI-Dev-System.
- «Следи за backend» — уведомление при падении без расхода LLM.
- Установка с нуля на чистую Windows; обновление на следующую версию по согласию; сломанное
  обновление откатывается автоматически.

### Stage 3 — Голос на русском · ≈4–8 недель

Входит: `jarvis-voice` — push-to-talk → STT (выбран по WER на ваших русских записях) → тот же конвейер →
TTS русским голосом и earcons; wake word «Джарвис» (своя модель; «hey jarvis» как временная заглушка);
окно продолжения; голосовые подтверждения MEDIUM; подсказки STT; полудуплексное «Джарвис, стоп»;
подтверждения HIGH через уведомления Windows с кнопками; игровой режим.

Критерии готовности: p50 «конец фразы → действие» ≤ 1,5 с для простых команд; WER на личном наборе
измерен и приемлем; ложные срабатывания wake word на фоновом аудио — в пределах целевого порога;
«стоп» останавливает и речь, и задачу.

### Stage 4 — Desktop UI · ≈6–10 недель

Входит: Tauri + React — трей, чат, таймлайн и дерево трассы, подтверждения, память, рецепты, grant'ы,
аудит, настройки, мастер первого запуска, установка обновлений.

Критерии готовности: всё, что было доступно в CLI, есть в UI; UI — обычный клиент API без своей логики.

### Stage 5 — Обучение рецептам · ≈3–6 недель

Входит: сигнатуры эпизодов, кластеризация, обобщение, предложения, версии рецептов, статистика
успешности; рецепты из объяснений и из фактов памяти; по желанию — публикация SKILL.md-грани в AI-Dev-System.

Критерии готовности: сценарий, трижды успешно выполненный агентом, превращается (с согласия
пользователя) в рецепт, который роутер находит и исполняет без LLM.

### Stage 6 — GUI: UIA → браузер → vision · ≈8–12 недель

Входит: GUI-драйвер на UIA (наблюдение → действие → проверка), профиль `gui`, безопасность GUI; браузер
через Playwright с отдельным профилем; затем vision — OCR, set-of-marks, VLM по требованию.

Критерии готовности: «нажми кнопку подтверждения» в стандартных диалогах — через UIA, с
подтверждением для рискованных подписей; vision-fallback справляется с окном без UIA за ограниченное
число шагов.

### Stage 7 — Триггеры и проактивность · ≈4–8 недель

Входит: триггеры по расписанию и событиям, сигналы, предложения, менеджер внимания, обучение на реакции
пользователя.

Критерии готовности: предложения полезны (доля принятых выше порога), не мешают (лимиты соблюдаются),
ничего не делается без согласия.

### Дальше

Песочницы L2/L3, голосовые «сателлиты», Jarvis как MCP-сервер, Linux-адаптер, дообучение малого
роутера на собственных трассах, верификация голоса владельца.

## 5. Открытые вопросы

### Уже решено

- Голосовой интерфейс — **на русском**: wake word «Джарвис», STT и TTS на русском, грамматики `intents/ru`.
- Поставка — **`.exe`-установщик**; обновления из GitHub Releases **только с разрешения пользователя**.
- Базовое железо — RX 7600 (8 ГБ), i5-12400, 32 ГБ RAM.
- AI-Dev-System остаётся отдельным продуктом; Jarvis — его клиент через MCP.
