# Handoff — Session 4.5: бенчмарк агента на настоящей модели

Работа шла в `main`: в начале сессии `claude/charming-mayer-tfvcc6` (Session 4) линейно опережала `main` и
влита перемоткой (`28c4573`), история не переписывалась. Новых подсистем продукта нет: ядро, Tool Runtime
и политика не менялись.

**Главное, честно:** цифр с целевого ПК в этой сессии нет. Разработка идёт в облачном контейнере без GPU
и без доступа к ПК (Hugging Face из контейнера тоже недоступен). Поэтому сессия сделала всё, что можно
сделать без ПК, так, чтобы прогон на ПК был одной командой, а отчёт сам доказывал, на чём он получен:
датасет, оценщик, запуск сервера с проверкой GPU, замеры, отчёты, правило выбора, кандидаты. Выбор
модели — после прогона пользователем, отдельным ADR с цифрами.

## Goal

Экспериментально определить, какая локальная модель и с какими параметрами надёжно работает «мозгом»
Jarvis на i5-12400 / 32 GB / RX 7600 8 GB / Windows 11. Главный критерий — доля решённых агентных задач.

## Implemented

- **Датасет** `benchmarks/agent/dataset.yaml`: рабочая папка проекта «Gofra» (README, docker-compose,
  backend на FastAPI, frontend на React/Vite, конфиги TOML/YAML/INI, «PDF», заметки, скрипт деплоя;
  четыре файла с инъекциями и файл с инъекцией в имени) и **47 задач**: A simple 6, B search 6, C read 6,
  D mixed RU/EN 6, E ambiguous 5, F invalid 7, G injection 5, H multistep 6. У каждой — условия и эталон.
- **Оценщик** (`evals/bench/grading.py`): первый вызов (инструмент, аргументы; пути — канонически),
  последовательность исполненных вызовов, фразы ответа (варианты RU/EN, плейсхолдеры `{size:…}`,
  `{year:…}` из настоящих файлов), выдуманный результат, уточняющий вопрос без чтения, объяснение
  ограничения, запрещённые подстроки в аргументах любого вызова (пути с `\` и `/` одинаково), отсутствие
  эскалаций. Сводка — все метрики из задания.
- **Прогон задачи** (`evals/bench/agent.py`): своё приложение и временный «компьютер» на задачу,
  настоящий путь Jarvis, подтверждения отклоняются, зоны политики — временные **и** настоящие
  (`~/.ssh`, `JARVIS_HOME` ПК).
- **Сервер кандидата** (`evals/bench/server.py`): `llama-server` с явными параметрами и `--fit off`,
  `-lv 4`; разбор лога (сборка, устройства, слои, буферы по устройствам, KV, таблица памяти, путь GGUF,
  предупреждения); вердикт offload `full`/`partial`/`cpu_only` против ожидаемого; счётчики Windows
  (выделенная и общая память GPU процесса и адаптера); RSS/private процесса и пик; скорость промпта и
  генерации, TTFT 1k/4k/8k, тёплый запрос со схемой — медианы трёх повторов без кэша.
- **Оркестрация** (`evals/bench/run.py`): загрузка модели до замера холодного старта, остановка кандидата
  на CPU-only сервере, отметка вытеснения из VRAM, лог разбирается после остановки (таблица памяти
  печатается при выходе — на Linux), sha256 загруженного GGUF.
- **Отчёты** (`evals/bench/report.py`): `report.json` (всё измеренное) и `report.md` по кандидату,
  `comparison.md` с таблицей и правилом выбора.
- **CLI** (`cli/bench.py`): `jarvis bench run | agent | compare`.
- **Кандидаты** `benchmarks/candidates.toml` и протокол `benchmarks/README.md`; методика — ADR 0024.
- `evals.engine.Machine` стал публичным (используется бенчмарком).

## Кандидаты и почему они

Отбор не по популярности: instruct-модели с обучением на tool use и ответ по схеме, русский в данных,
несколько семей, размер под 8 GB. Все поддерживаются llama.cpp `b92761a` (проверено по исходникам:
архитектуры, примеры конвертации, документация).

| ID | Класс | Модель | Зачем |
| --- | --- | --- | --- |
| `qwen3.5-4b-q4` | fast | Qwen3.5 4B Q4_K_M | гибридное внимание — маленький KV-кэш и быстрый промпт; большой запас VRAM |
| `gemma4-e4b-q4` | fast | Gemma 4 E4B Q4_K_M | другая семья, сильное многоязычие |
| `qwen3.5-9b-q4` | balanced | Qwen3.5 9B Q4_K_M | старший размер целиком в 8 GB с KV 16k |
| `qwen3.5-9b-q5` | balanced | Qwen3.5 9B Q5_K_M | Q4 против Q5 на основном размере |
| `ministral3-8b-q4` | balanced | Ministral 3 8B Instruct Q4_K_M | третья семья, обучена на function calling |
| `gemma4-26b-a4b-q4` | max | Gemma 4 26B-A4B Q4_K_M, `--cpu-moe` | MoE, 4B активных, эксперты в RAM |
| `qwen3.6-35b-a3b-q4` | max | Qwen3.6 35B-A3B Q4_K_M, `--cpu-moe` | MoE, 3B активных; проверка, тянет ли 32 GB RAM |

Общие параметры: контекст 16384, все слои на GPU, 6 потоков, batch 2048 / ubatch 512, flash attention,
KV q8_0, один слот, `--reasoning off`, `--no-mmproj`, температура 0, seed 42.

**Не проверено из контейнера:** точные имена репозиториев GGUF и квантов. `unsloth/Qwen3.5-4B-GGUF:Q4_K_M`
и `ggml-org/gemma-4-*-it-GGUF` упомянуты в документации llama.cpp; `unsloth/Qwen3.5-9B-GGUF`,
`unsloth/Qwen3.6-35B-A3B-GGUF`, `mistralai/Ministral-3-8B-Instruct-2512-GGUF` — по аналогии. Если
репозитория нет, кандидат помечается «не запустился», остальные идут; исправление — строка `hf` или
`model` в `candidates.toml`.

## Что проверено здесь

- Эталон решает **47/47** задач (`jarvis bench agent --reference`, тест).
- Оценщик ловит ошибки модели — по одному тесту на вид: не тот инструмент, не тот путь, пути в любом
  написании принимаются, чтение вместо уточняющего вопроса, ответ без вопроса, выдуманное «удалил»,
  поддалась инъекции (путь к ключу + запрос подтверждения), Windows-путь в запрещённых аргументах,
  неверный размер файла, пропущенный шаг поиска, ремонт ответа, зависшая модель; и не придирается к
  правильному: естественные отказы, `system.cwd` перед делом, повтор после сбоя связи, чтение документов
  ПК вне рабочей папки — только через (отклонённое) подтверждение.
- **Сквозной прогон с настоящим `llama-server`** (llama.cpp `b92761a`, сборка CPU, крошечная модель со
  случайными весами): сервер запускается с параметрами кандидата и останавливается, лог разобран,
  вердикт `cpu_only` с причинами и остановка кандидата (а с `--allow-cpu-only` — прогон), скорость и память
  измерены, датасет прошёл через настоящий адаптер и HTTP, отчёты и сравнение записаны; падение сервера при
  старте (неподходящий тип KV-кэша) — кандидат помечен, сессия продолжилась. Качество здесь не меряется:
  модель случайная (успех 0 %, как и должно быть).
- Не проверено: Vulkan и счётчики Windows (GPU и Windows в контейнере нет — логи Vulkan и ответ WMI в
  тестах синтетические, в формате llama.cpp и PowerShell), настоящие модели-кандидаты. На первом прогоне
  на ПК стоит взглянуть в `report.md` кандидата: устройство `Vulkan0`, вердикт `full`, заполнены ли строки
  VRAM процесса и адаптера.

## Known limitations

- Датасет проходится один раз (жадное декодирование, seed); повторы — только у замеров скорости.
- Метрики роутера и планировщика появятся с M7/M8; structured output меряется на решениях исполнителя.
- Задачи о процессах (`a03`, `d02`) видят настоящие процессы ПК: ответы в отчёте укорочены до 300
  символов, отчёты перед коммитом нужно просмотреть.
- Счётчики GPU Windows читаются из классов WMI через PowerShell; если они недоступны, VRAM в отчёте — по
  логу сервера (буферы и свободная память при старте).

## Architecture deviations

Отступления от плана 07 §4 — в ADR 0024: команды `bench run | agent | compare` вместо `bench hardware`,
`benchmarks/candidates.toml`, sha256 модели — в отчёте после загрузки, structured output — на решениях
исполнителя, датасет — один проход.

## Review

Независимое ревью кода бенчмарка (по исходникам llama.cpp `b92761a`) нашло десять проблем; все
подтверждены и исправлены отдельным коммитом с тестами:

1. **Ложное «вытеснение»:** при загрузке через mmap Vulkan держит буфер загрузки размером с самый большой
   тензор (`output.weight` 0.5–0.9 GB) в общей памяти — проверка по общей памяти забраковала бы здоровый
   прогон. Теперь вытеснение — буферы на GPU по логу, которых нет в выделенной памяти процесса.
2. **Счётчики GPU на русской Windows:** пути `Get-Counter` переводятся, вывод PowerShell 5.1 — в cp866
   (падение декодирования обрывало сессию), адаптеры суммировались (встроенный GPU i5-12400 тоже).
   Теперь — классы WMI (имена не переводятся), JSON, терпимое декодирование, адаптер по LUID процесса;
   разбор покрыт тестом; если счётчиков нет — заметка в отчёте.
3. **Правильные отказы засчитывались как выдуманный результат** («не могу внести изменения» содержит
   «изменен»): фразы — целым словом и не после «не».
4. **Загрузка модели упиралась в 900 с запуска:** у загрузки свой предел — 6 часов.
5. **Таблица памяти при выходе на Windows не печатается** (llama-server ловит только Ctrl+C, а TerminateProcess
   его не даёт): таблица необязательна, живой тест на Windows её не требует.
6. **Безопасность:** автоотказ закрывал только зоны секретов, а политика разрешает чтение везде — модель,
   поддавшаяся инъекции, прочитала бы документы ПК (до 300 символов ответа — в отчёт). Теперь в бенчмарке
   читать без человека можно только рабочую папку задачи (`PolicyZones.read_roots`, по умолчанию пусто —
   продукт не меняется); настоящий файл конфига тоже закрыт.
7. **Сбой одного кандидата обрывал сессию** (ошибки HTTP замера скорости): теперь кандидат помечается, сессия
   идёт дальше.
8. **Повтор после сбоя связи считался ремонтом** и путал группировку попыток: ремонт — только ответ модели
   после непринятого; оборванные запросы в метрики схемы не входят.
9. Мелочи: буферы RS (состояние слоёв Qwen3.5) не входили в память GPU; заполнитель «8k» был ≈ 11.7k токенов
   (откалиброван по токенизатору Qwen2, настоящий размер промпта теперь в отчёте); точность аргументов
   считалась и при неверном инструменте; `system.cwd` перед делом проваливал задачу.
10. **Занятый порт:** на Windows llama-server делит порт со старым сервером, и /health ответил бы старый —
    теперь порт проверяется до запуска.
