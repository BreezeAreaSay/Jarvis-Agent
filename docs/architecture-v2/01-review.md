# 01. Architecture Review: Jarvis после бенчмарка

Ревью кода `main` (`5b9fe79`, конец Session 4.5), документов Stage 0, ADR 0001–0024, handoff'ов
Sessions 2–4.5 и результатов прогона бенчмарка на целевом ПК (из описания PR #1 и отчёта владельца).

## 1. Что показал бенчмарк и почему это меняет архитектуру

| Модель | Итог | Решение |
| --- | --- | --- |
| Qwen3-8B Q4_K_M, llama.cpp Vulkan, 37/37 слоёв на GPU, ≈48–49 ток/с | 47 задач: успех 55,3 %; выбор инструмента 85,7 %; аргументы 100 %; схема 100 %; ремонтов 0 %; многошаговые 83,3 %; инъекции 100 %; тёплый запрос 238 мс | **основная локальная** |
| Qwen3-8B Q5_K_M | coding 47,6 %; ≈9 ток/с (буферы вне VRAM) | удалена |
| Qwen3-30B-A3B-Instruct-2507 Q4_K_M, эксперты в RAM | coding 38,1 %; ≈15 ток/с; ≈29 с на задачу | удалена |
| Qwen3-Coder-30B-A3B Q4_K_M, эксперты в RAM | coding 28,6 %; ≈15 ток/с | удалена |
| Ollama qwen3:4b / qwen3:4b-jarvis | работает; рассуждения расходуют ответ и делают его менее предсказуемым | кандидат FAST, не по умолчанию |

Выводы, которые меняют архитектуру:

1. **Локальная 8B хороша в коротком:** понимает запрос, выбирает инструмент, держит схему ответа и
   не поддаётся инъекциям. Но каждая вторая задача из 47 не доводится до правильного результата —
   значит, длинное автономное планирование на ней строить нельзя (**архитектура B**).
2. **Больше локальных параметров не помогает** на этом железе: MoE 30B с экспертами в RAM медленнее
   и хуже 8B на агентных задачах. Тяжёлая локальная модель — не путь к интеллекту Jarvis.
3. **Интеллект для сложного — снаружи** (облачные модели и специализированные агенты), а скорость и
   приватность простого — в детерминированном коде и локальной модели.
4. **VRAM занята одной моделью.** 8B с окном 16k на RX 7600 8 GB занимает ≈7,5 GiB, и около
   967 MiB буферов уже вышли за выделенную VRAM. Вторая резидентная модель на GPU не помещается:
   «держать 4B рядом с 8B» на этом ПК означает переключение моделей (секунды), а не ускорение.

Замечание к выбору: правило ADR 0024 браковало вытеснение > 512 MiB, а у Qwen3-8B Q4 при 16k —
967 MiB. Владелец оставил модель по скорости и качеству; это отступление записано в ADR 0025 вместе
с проверкой (окно 12k или меньший `-ub`, повторный замер).

## 2. Что сейчас хорошо (оставляем)

Фундамент Stage 0 оказался правильным и пережил бенчмарк без изменений:

- **Task Runtime:** явная машина состояний (ADR 0010), runner с контрольными точками, бюджеты на
  фазу маршрута, отмена, `interrupted` для умерших процессов.
- **Persistence и восстановление:** SQLite + WAL, оптимистическая единица работы, аренды задач со
  сравнением-и-записью (ADR 0021), миграции с эталонной схемой, контрактные тесты двух хранилищ.
- **Tool Runtime как единственная граница исполнения** (ADR 0004, 0022): preview с каноническими
  путями, эффекты вызова, политика до исполнения, повторный preview против подмены, verify, аудит.
- **Policy v1:** чистая функция по зонам; property-тест «побочный эффект модели никогда не ALLOW».
- **Подтверждения как состояние задачи** (ADR 0011) с привязкой к отпечатку preview.
- **Трасса без chain-of-thought** (ADR 0015), таймлайн шаблонами, метрики из событий.
- **Таксономия ошибок** с диспозициями (ADR 0014).
- **Model Gateway как граница модели:** решения по возможностям, structured output по схеме из реестра,
  ремонт, бюджет на каждую попытку, журнал `model_calls`, секреты не оседают в журналах (ADR 0023).
- **Промпт с уровнями доверия и блоками DATA** — инъекции 100 % в бенчмарке подтверждают подход.
- **Eval-first:** scripted-сценарии в CI, scripted-модель через тот же конвейер, бенчмарк с
  доказательствами GPU и детерминированным оценщиком (ADR 0020, 0024).
- **Правило зависимостей проверяется автоматически** (import-linter + AST-тесты): ядро без
  ввода-вывода и без модельной специфики.

## 3. Что стало неправильным после бенчмарка

| Предпосылка V1 | Где | Почему неверна теперь |
| --- | --- | --- |
| Основная локальная LLM — главный интеллект; цикл Planner ⇄ Executor ⇄ Verifier с живым планом | 03-agent-core §6, M8 | 55,3 % на 47 задачах: свободный длинный план на 8B ненадёжен |
| L2-роутер = основная LLM в «режиме роутера» на каждый неоднозначный запрос | 03-agent-core §3, 02-overview | лишний вызов 8B до основной работы; маршрут дешевле решать правилами, а неоднозначность — первым шагом агента |
| Все текстовые роли — на одной локальной модели | 03-agent-core §5 | для сложного нужны внешние провайдеры; роли уступают место маршрутам и уровням |
| `base_url` — только loopback, облако — «когда-нибудь опция» | ADR 0023, 0008 | облако — нормальная часть Jarvis за явной границей приватности |
| Одна модель на роль, один бэкенд | ADR 0023 | нужны цепочки провайдеров, состояние провайдеров и fallback |
| Резидентность нескольких моделей, «пинг-понг» с VLM | 03-agent-core §5 | на 8 GB помещается одна модель; менеджер резидентности не нужен |
| Coding-задачи решает свой агентный цикл на локальной модели | 05-ai-dev-system, M8 | внешние coding-агенты делают это лучше; Jarvis должен их оркестровать, а не повторять |
| Профили агента как YAML с десятками инструментов | 03-agent-core §4 | для 8B важнее узкий набор инструментов на маршрут, чем система профилей |

## 4. Лишняя сложность (в планах, не в коде)

Код Stage 0 почти не содержит лишнего — правило «без заготовок на будущее» работало. Лишнее — в
документах-эскизах, которые ещё не реализованы:

- десять ролей Model Gateway (`router`, `planner`, `verifier`, `summarizer`, `responder`, `grounder`…);
- менеджер резидентности моделей, очередь приоритетов вызовов и запрет «пинг-понга»;
- LLM-планировщик с библиотекой проверок как основа исполнения (M8);
- отдельные слои «Intent Router → Task Classifier → Execution Strategy → Model Router» — это одно
  детерминированное решение, а не четыре компонента;
- live replay с эффектами (ADR 0016) — до появления инструментов с эффектами;
- workspace из нескольких пакетов, IPC и демон как предпосылка (ADR 0001, 0019) — пока один процесс.

Небольшое лишнее в коде: состояния `PLANNING` и `REPLANNING` и маршрут `CHAT` без потребителя.
Удалять их не нужно (стоимость нулевая, удаление — миграция таблицы переходов); они помечаются как
спящие.

## 5. Чего не хватает

| Чего нет | Зачем | Где в V2 |
| --- | --- | --- |
| Детерминированный роутер и решение о способе исполнения | сейчас каждый запрос ведёт агент на 8B | Router, `RouteDecision` (02 §3) |
| Прямые команды без модели (L0) и инвентарь приложений | «открой браузер» за миллисекунды | Direct path (02 §4.2) |
| Эффект «запустить приложение / открыть URL» и политика по исполнителю | сейчас PROCESS_CONTROL — запрет | ADR 0030 |
| Удалённые провайдеры, цепочки, состояние провайдеров, fallback | облако без зависимости от одного поставщика | ADR 0027 |
| Граница приватности облака: классы данных, согласие, аудит выхода данных | секреты и закрытый код не уходят наружу | ADR 0028 |
| Порт внешнего агента и его модель угроз | Codex CLI и аналоги — специалисты, а не модели | ADR 0029 |
| Рецепты | длинные и повторяемые процессы детерминированно (архитектура B) | Recipe Engine, после V2.1 |
| Режим `local_only` как гарантия | «ничего не отправляй в облако» | ADR 0027, 0028 |
| Команды подтверждения для оставленных задач | `jarvis approvals/approve/deny/resume` (ADR 0011) | CLI, вместе с делегированием |
| Резидентный процесс | холодный старт CLI ≈ 0,5–0,7 с в контейнере, на Windows больше | открытый вопрос (04 §6) |
| Работающий CI | все прогоны GitHub Actions — `startup_failure`, PR-прогоны ждут одобрения | действие владельца (04 §5) |

## 9. PR #1 «improve Windows support and local model benchmarking»

PR из форка `stonebridgeway/Jarvis-Agent`, ветка `codex/local-model-benchmark`, 7 коммитов, не влит.
Ревью и CI нет: прогоны ждут одобрения (`action_required`), а все прогоны в `main` падают на старте
(`startup_failure`) — CI репозитория сейчас не работает вообще.

Что исправлено и как это сделать лучше:

| Недочёт | Как исправлено в PR | Проблема исправления | Как лучше |
| --- | --- | --- | --- |
| На Windows тест изоляции ядра падает: интерпретатор или окружение загружают модуль из списка запрещённых ещё до импорта ядра (вероятно, `winreg`; точную причину PR не называет) | из итогового списка модулей вычитается всё, что было загружено до импорта ядра | любой запрещённый модуль, загруженный до ядра (`.pth`, sitecustomize), перестаёт ловиться — тест молча ослаблен | перед импортом ядра **выгрузить** уже загруженные запрещённые модули из `sys.modules` и проверять полный список: если ядро их импортирует, они появятся снова |
| `FakeTool` с путями `/keys/a.pem` на Windows-хосте: политика видит не-абсолютный путь и отказывает | фейк переписывает путь в `C:\fake\…` на Windows; тест таймлайна ждёт разную строку по ОС | тестовый код подстраивается под ОС хоста, ожидания зависят от платформы | unit-тесты ядра не должны зависеть от хоста: `make_app` собирает приложение с фиксированной POSIX-целью и POSIX-зонами (`build_app` получает `target`); фейк и ожидания не меняются |
